# Canonical Source/File intake after external preservation

**User outcome:** one ordinary request “Archivalie lokal und im Repository sichern – optional Zotero.” The user should not need to call this skill manually after an archive-specific acquisition skill. A repository skill file does not prove host discovery or automatic invocation; the executing acquisition context must explicitly continue into this bounded step and verify it actually ran.

## Before action

Freshly read `GOVERNING_OBJECTIVE.md`, `AGENTS.md`, `methodology/historical-source-workflow.md`, `methodology/source-and-provenance.md`, `methodology/project-lifecycle.md`, `methodology/workflow.md` and current Source/File/project-routing owners from the **online authorized GitHub connection**. Resolve current branch/PR, user-selected archival unit and evidence. Do not rely on old chat, local repository mirrors, filenames or neighbouring projects. **Status-only** questions (`Fertig?`, `Status?`) must not trigger download, resume, GitHub mutation or Zotero mutation.

## Run (provider-independent)

1. **Preservation first.** Use the *already produced* archive-specific verified external package; do not start a second acquisition. Accept its provider-specific acquisition metadata and real original bytes, not only a `complete` text, a list of URLs, CI artifacts, a sample image or a download count. For the current SStA provider, the package sidecars are `QUELLENINFO.json`, `QUELLENINFO.txt`, `SHA256SUMS.txt`, `ACQUISITION_STATE.json`; do not universalize these exact filenames to another archive. Other providers must supply equivalent independently validated facts.
2. **Verify locally, read only.** If the package is in the supported SStA sidecar format and the authorized runtime can open it, run `python tools/archival_package_intake.py <actual-package-directory>` (no new download) and inspect its result. The helper checks all original byte SHA-256s, all manifests, completed progress-plan identity and canonical exact File SHA ownership. It **does not** prove long-term external durability or perform any GitHub write. For another provider, use equivalent evidence and the existing `tools/source_intake.py` SHA-first tool.
   **Legacy manifest-versus-plan naming discrepancy (Nr. 632 test finding):** The verified read-only helper can recognize only a hyphen/underscore *separator-equivalent* alias where the actual folder matches `QUELLENINFO.json` and the source GUID, acquisition route, file-list checksum, filenames and individual byte hashes independently agree. The output `package_naming.status: LEGACY_SEPARATOR_ALIAS` means **byte-level read-only reconciliation with a known metadata discrepancy**, *not* safe resume. `resume_safety: UNVERIFIED_DO_NOT_RESUME` is binding. Never rewrite `ACQUISITION_STATE.json`, rename OneDrive folders or trigger acquisition merely to normalize an old name. If the actual exact names are not equivalent, stop and report the identity conflict; do not infer equivalence from a short verbal summary.
3. **Confirm external custody separately.** Verify the actual selected controlled external destination persists and is recoverable, and distinguish temporary staging, OneDrive/external files, repo mirror and provider URL. Never infer that `/tmp`, CI, a file name, an archive GUID or this helper's successful SHA check proves durable external storage. Preserve the actual destination/evidence in the existing relevant acquisition evidence owner without publishing private mount paths or credentials.
4. **Resolve canonical Source identity.** Read `corpus/sources.tsv`, `corpus/files.tsv`, `corpus/source-contract.json` and current `source-entry/routes.tsv` through GitHub. Match an exact archive/fonds/signature/provider identifier and its real granularity, not just title, date, filename or an unrelated source selected in chat. Reuse canonical source IDs (e.g. Dresden Nr. 01739 is distinct from Leipzig Nr. 632). If a new Source row is needed, derive its defensible identity from verified catalogue evidence; if evidence is ambiguous, stop that write instead of guessing.
5. **Write only to existing canonical owners via authorized online GitHub tools.** Once the user has authorized the full acquisition+repo registration and you have verified preserved originals, create/reconcile `corpus/sources.tsv` and one `corpus/files.tsv` row per exact original SHA, if missing. Use the *existing* headers and `source_contract.py` semantics, correct unique File ID, original filename, Source binding, provider-image coverage (never infer archival folio, manuscript side, hand or internal document), truthful `storage_status`, `rights_status` and evidence basis. Do not commit original restricted images/PDF bytes to the public repo. Do not use an unadmitted new canonical schema or an offline repo clone as a writer. If no GitHub writing capability exists, report that action-local failure and leave the external package intact.
6. **Source-entry routing remains its own owner.** Reuse a current route (including `UNRESOLVED`) without manufacturing `CORPUS_ONLY / NO_PROJECT_YET`, `EXISTING_PROJECT`, a new Project, Source use, research function, scholarly scope/priority or `NEXT ACTION`. Do not create visual-inspection/coverage rows merely because each JPEG passed byte verification. Relations and folio/PDF/image crosswalks require distinct direct evidence.
7. **Validate and persist.** Re-run owner-local contract validation and suitable tests on the exact candidate branch; verify remote GitHub write commit(s), Source/File identifiers and eventual merge separately. Idempotent repeat must reuse rows; conflicts, partial GitHub writes, rights uncertainty, missing images, mismatched SHA or wrong source mapping fail closed. Resume **repository reconciliation only**, without a new image download unless separately requested.
8. **Independent extension boundary.** This core skill has **no Zotero task or acceptance requirement**. When a Human separately requests a Zotero bibliographic entry, use the independent optional owner [#337](https://github.com/esany/paleo-type/issues/337), only after core Source/File completion and actual connector authorization. Do not perform implicit Zotero writes or upload JPEG/PDF originals. This skill's success and closure cannot depend on #337 or general bibliography issue #13.
9. **One core user-facing result:** report the verified source, actual external package, number of byte-verified originals, Source ID and File rows persisted in online GitHub, and any read-only/partial/failed facets. Never report the mandatory core flow `complete` solely because the acquisition sidecar says `complete` or CI passed; optional Zotero is an independent later action and cannot block this core result.

## Hard boundaries

- No bulk acquisition, Project creation, corpus mutation, Zotero write or other side effect for a pure read/status request.
- Never substitute a historic already-complete Nr. 632 package for a new Dresden Nr. 01739 request.
- Do not describe a provider URL or checksum inventory as preserved *bytes*, or technical file verification as manuscript inspection.
- Do not make an archive-specific skill cover another archive branch merely because the host/domain matches.
- Generic Source/File writes must follow the **existing** authoritative contract. Material ownership/schema/routing changes return to the D-016 decision owner; this skill is not approval for such a change.
