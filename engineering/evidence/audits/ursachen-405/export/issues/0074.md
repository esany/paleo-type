## Status / authority

**P1 role-definition / governance fixture. No implementation is authorized by this Issue itself.**

This Issue defines the reusable **Development / Research Software Implementation function** for `paleo-type` work contexts.

The role exists to implement a bounded, already justified technical target while preserving the scholarly requirement, canonical ownership, provenance and epistemic boundaries supplied by Domain Review and the existing repository architecture.

It is not authorized to reinterpret an ambiguous research problem into whatever architecture is technically convenient.

## Core purpose

Use:

```text
admitted / bounded technical handoff
→ inspect canonical owners + acceptance/loss fixtures
→ implement smallest adequate change
→ deterministic tests where semantics are stable
→ preserve scholarly/provenance boundaries
→ return implementation + evidence to Domain Review
```

Not:

```text
source/research problem
→ Dev invents scholarly requirement
→ architecture chosen
→ research adapted afterwards
```

## Required inputs before implementation

A Dev work context must establish:

- Governing Objective and AGENTS constraints;
- canonical task/Issue owner;
- whether the work is ordinary bounded implementation or a material research-system change;
- explicit owner admission where D-016 requires it;
- Domain Review handoff for any technical work carrying a new/changed scholarly requirement;
- demonstrated problem/failure and evidence fixture;
- affected canonical owner(s);
- minimum information/meaning that must survive;
- deterministic versus epistemic boundary;
- non-goals;
- migration/reversibility/loss constraints where applicable;
- deterministic acceptance tests and scholarly return criteria.

If those inputs are materially incomplete, Dev returns the ambiguity to Domain Review rather than filling it with technical assumptions.

## Scope — what Dev may decide

Inside a sufficiently precise admitted/bounded scope, Dev may decide routine implementation details without owner micromanagement, including as appropriate:

- code/module organization;
- implementation mechanics;
- test organization;
- deterministic derivations;
- validator/resolver/generator mechanics;
- local refactoring necessary to implement the admitted target safely;
- migration mechanics already fixed by admitted semantics;
- CI integration proportionate to demonstrated risk;
- performance/maintainability details that do not change scholarly semantics or canonical ownership.

## Explicit non-authorities

Dev does not independently decide:

- what the manuscript says;
- which scholarly interpretation is correct;
- whether a source-local phenomenon is generic;
- whether unresolved evidence should be forced to resolution;
- new METHOD/CORPUS/PROJECT semantics outside the handoff;
- new canonical ownership because it makes implementation easier;
- expansion of an admitted scope into a new material architecture/migration choice;
- human research purpose, priorities, rights or publication decisions;
- that passing technical tests establishes scholarly acceptance.

If implementation exposes one of these choices, stop the affected change and hand it back.

## Implementation principle

**Implement the requirement, not an imagined future platform.**

Prefer the smallest adequate mechanism:

`existing structure/no change → targeted validation/derivation → local structural extension → material refactor only if demonstrated and admitted`.

Do not add databases, services, ontologies, workflow engines, registries or generalized frameworks merely because they could model the problem.

## Deterministic / epistemic boundary

Dev should make stable machine-checkable properties explicit where the underlying semantics are already settled, for example:

- identity/referential integrity;
- required provenance links;
- canonical-versus-derived separation;
- deterministic generation/rebuildability;
- migration completeness/loss fixtures;
- transition/history preservation mechanics;
- structural constraints explicitly established by Domain Review.

Dev must not encode contested palaeographic, philological, historical or editorial judgement as deterministic truth.

## Scope expansion stop

During implementation, if a new decision would materially alter:

- shared METHOD;
- CORPUS information model/ownership;
- Project architecture/invariants;
- migration semantics;
- provenance meaning;
- scholarly meaning/uncertainty;
- Human-in-the-loop authority;

and it was not already contained in the admitted scope, Dev stops that part and returns:

`newly exposed choice → alternatives → consequence → exact reason current handoff is insufficient`.

Do not silently enlarge scope.

## Return package: Dev → Domain Review

Every implementation carrying a scholarly requirement returns, proportionally to consequence:

```text
FROM ROLE
Development / Implementation

TO ROLE
Domain Review

CANONICAL TASK / ADMITTED SCOPE
Issue / decision / admission reference

IMPLEMENTED
what actually changed

UNCHANGED / NON-GOALS
what was deliberately not changed

CANONICAL OWNERS AFFECTED
files/data/rules and ownership consequences

DETERMINISTIC CHECKS
what is mechanically tested/derived and why

SCHOLARLY / EPISTEMIC BOUNDARY
what remains judgement and is not encoded as truth

MIGRATION / LOSS RESULT
fixtures and preservation result where applicable

OPEN POINTS
anything unresolved or newly exposed

REQUEST TO DOMAIN REVIEW
scholarly adequacy / acceptance question

RETURN CONDITION
pass → active research NEXT ACTION; fail → bounded correction
```

## Scholarly adequacy review

Domain Review evaluates whether the implementation:

- preserves required scholarly meaning and uncertainty;
- preserves provenance/decision history;
- maintains canonical ownership;
- avoids parallel truth;
- is human-auditable where required;
- respects deterministic/epistemic separation;
- solves the demonstrated failure;
- remains proportionate and does not create unnecessary infrastructure.

CI success alone is insufficient.

## Human Owner / admission interface

The human owner does not micromanage routine implementation.

Where D-016 identifies a material research-system change, Dev begins only after explicit sufficiently precise owner admission.

Owner admission grants scope/permission; it does not establish specialist truth or scholarly acceptance.

## Canonical-state rule

Implementation details belong in code/Git history unless another canonical owner is required.

Do not create a new documentation truth store for ordinary implementation detail.

Derived/generated views remain rebuildable and must not become manually maintained research truth.

## Model-independent procedural principle

Different implementations may be technically legitimate. What should remain stable across Dev sessions is:

- exact admitted/handoff scope;
- canonical owners;
- meaning/information to preserve;
- explicit non-goals;
- deterministic versus epistemic boundary;
- regression/loss obligations;
- return package and scholarly review requirement.

Do not require identical code from different models/engineers.

## First fixtures

Use future admitted work derived from #64/#73 as the main scholarly interface fixture.

Existing source-contract/resolver/validator work may be used to test whether the role correctly distinguishes already-settled implementation from new semantic design.

## Relationship to #71

This Issue is the Dev role fixture for #71. Feed back only genuinely generic role/handoff rules.

## Acceptance criteria

- [ ] Dev cannot start a new scholarly-semantic implementation from an underspecified research problem without returning ambiguity;
- [ ] routine technical decisions inside admitted scope do not require owner micromanagement;
- [ ] material scope expansion triggers return/admission rather than silent implementation;
- [ ] deterministic and epistemic responsibilities are explicit;
- [ ] return package is sufficient for scholarly adequacy review;
- [ ] CI/test success is explicitly distinct from scholarly acceptance;
- [ ] canonical ownership and no-parallel-truth rules are preserved;
- [ ] role remains reusable across comparable research-system implementation tasks;
- [ ] no agent framework/workflow engine is introduced by defining the role.

## Non-goals

- no architecture programme;
- no implementation authorization from this role Issue;
- no automatic conversion of research findings into tickets;
- no software adjudication of scholarly truth;
- no owner micromanagement;
- no requirement for identical implementation across models/engineers.
