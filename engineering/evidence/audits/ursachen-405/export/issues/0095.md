# Issue #95: Deterministic artifact-ownership preflight before research-data refactors

## Text

## Finding

The current methodology contains the right principles (`one fact, one canonical home`, derived views must not become parallel truth, Project state belongs to `project.yml`/`STATUS.md`, diplomatic representation is locus/folio/line-addressable), but these principles are not yet strong enough as a **deterministic pre-mutation process rule**.

The Reg. Ii 4 Bd. II Knau first-reading work exposed the gap:

1. a range-named file `transcription/fol306v-309r-first-reading.tsv` was created for the whole research locus although only fol. 306v had actually been inspected;
2. the file initially mixed stable provenance/scope metadata with changing scholarly row content;
3. after splitting to folio-local children, an additional `first-reading/README.md` was introduced as a semantic “parent” and began to duplicate scope/progress/cursor/gate information already owned by Project/status/evidence files;
4. only after re-reading the canonical method was it clear that the **scholarly parent already existed** as Project + Source + relevant locus/task, while folio files are storage/work partitions, not automatically new canonical entities.

No pre-existing Reg. Ii 4 transcription artifact was overwritten; Git history shows the range file itself was introduced during this work. The defect is therefore not historical-data loss but **AI/system structure drift during multi-step refactoring**.

## Why existing rules did not prevent it

Current rules are strong at the level of principles and post-change maintenance:

- `methodology/maintenance.md`: one fact / one canonical home; derived views must not become parallel truth stores;
- `methodology/project-lifecycle.md`: Project purpose/scope/status/readings have canonical owners;
- `methodology/historical-source-workflow.md` + `research-gates.md`: S3/G2 require locus/folio/physical-line-addressable diplomatic representation and a derivable human-readable witness view.

But the operational sequence still allows an agent to mutate files first and only afterwards notice that it created a second owner or confused a semantic hierarchy with a filesystem hierarchy.

## Required generic safeguard

Before creating, renaming, moving, splitting, merging or deleting a research-data/documentation artifact, require an explicit **artifact-ownership preflight**:

1. **Resolve the scholarly object** being represented (Project state, Source/File truth, relevant locus, transcription row data, comparison result, derived view, navigation, etc.).
2. **Resolve its existing canonical owner** from METHOD/CORPUS/PROJECT ownership rules and Git history.
3. **Classify the proposed artifact** as exactly one of:
   - canonical owner/state;
   - partition of canonical data;
   - derived/rebuildable view;
   - navigation/explanation;
   - transient working artifact.
4. **Do not infer file hierarchy from scholarly hierarchy.** A parent→child research relation does not itself justify a new parent file/entity or duplicated parent state.
5. **Check history before destructive/refactoring writes** to establish whether the apparent target is pre-existing canonical work, a derived artifact, or newly introduced work from the current change sequence.
6. **State changed truth vs unchanged truth before mutation.** Stable provenance/scope facts must not be recopied into every child merely for convenience.
7. **Define aggregation/derivation direction.** If a whole-section view can be reconstructed losslessly from folio children plus canonical scope metadata, it should be generated/derived rather than maintained as a second manually edited text truth.
8. **Run a post-mutation duplicate-owner check** against the declared ownership map and volatile Project state (`project.yml`, `STATUS.md`, evidence/gate owners).

## Candidate deterministic checks

Explore whether part of the safeguard can become machine-checkable rather than prose-only, for example:

- artifact manifest/schema declaring `role = canonical | partition | derived | navigation | transient` and `owner`/`derived_from` where useful;
- lint against manually duplicated volatile Project fields in known navigation/derived surfaces;
- validation that a range-named transcription artifact cannot imply completion when only a subset of archival units is represented, unless partial state is explicit;
- migration/refactor checks that compare pre/post artifact ownership and detect creation of parallel truth stores;
- a reusable preflight command that reports canonical owner, existing/history state and proposed artifact role before write operations.

The exact executable design remains open; do not introduce a new ontology merely to satisfy this issue.

## Acceptance criteria

A future agent handling the same task should deterministically discover **before writing** that:

- the project-level research locus `306v–309r` is already owned by Project scope/status;
- folio-local TSVs may be partitions of the diplomatic first-reading data;
- a human-readable whole-section view should be derived from ordered folio data rather than maintained as a second transcription truth;
- a navigation README may explain the structure but must not become a second owner of progress/cursor/gate state;
- Git history must be inspected before a refactor is described as preservation, overwrite, migration or deletion of older work.

## Non-goals

- no new Project/Source ontology;
- no assumption that every scholarly parent requires a filesystem parent artifact;
- no duplication of Source/File/crosswalk metadata into transcription rows;
- no automatic inference of scholarly semantics from filenames/directories;
- no implementation until the material method/process change passes the repository’s normal change-admission workflow.
