## Status
**Planning issue only. No implementation is authorized by this Issue.**

This Issue records the bounded target semantics for a later, separately admitted Project/Source/Research-Use normalization. It is subordinate to `GOVERNING_OBJECTIVE.md`, D-014, the canonical Requirements and the partial GOV-M4 checkpoint in #25.

## Already canonical and retained
The current `main` already establishes:
- `project.yml: project_source_id` as the defining historical project boundary anchor;
- `SOURCE --part_of--> SOURCE` as the canonical structural relation;
- `root | internal | external` as values derived from `project_source_id + part_of*`, never copied as project truth;
- stable Source identity independently of project use/function;
- Project→Project relations as explicit relations only, never an automatic consequence of Source use.

No new Parent-/Source-hierarchy system is part of this plan.

## Demonstrated gaps to normalize later
Current Project→Source representation still has three problems:
1. a single `project_role` per Project/Source pair cannot represent multiple transdisciplinary research functions without collapsing them into a coarse label;
2. `principal_source_id` in `project.yml` duplicates the same current Principal meaning already represented by `project_role=principal` in the Project Source register;
3. `primary_file_id` currently combines Project→Source research use with the concrete digital instantiation selected for that use.

## Target Project→Source use semantics
Planned association:

`source-uses.tsv`

`use_id | source_id | research_function | relevant_locus | status | evidence_basis | notes`

Semantics:
- one row = one concrete Project→Source research function;
- `research_function` is project-relative and never a Source property;
- the same Source may have multiple use rows/functions in one Project when the research genuinely requires them;
- `relevant_locus` is the source-relative scholarly scope of that use;
- the function vocabulary remains open and lean; no closed ontology and no automatic function inference;
- examples such as `principal`, `textual-comparison`, `palaeographic-comparison`, `notation-control` and `historical-context` are descriptive examples, not a frozen universal vocabulary;
- `PROJECT uses SOURCE` is derivable from existence of one or more use rows.

This target operationalizes REQ-ARCH-007 while preserving distinctions required by editing/textual criticism, palaeography, historical source criticism, philology and historical metrology/accounting analysis.

## Principal
`project_source_id` remains the structural Project invariant.

`principal` is planned as a `research_function`, not as a second Project identity/boundary field. A later admitted migration therefore needs to eliminate the current duplicate Principal truth without changing the current scholarly meaning.

This Issue does not alter `project.yml` now.

## Owner decision: Variant B — separate use and concrete digital evidence
The owner has explicitly selected the following planning target.

Project→Source research function and concrete File/Image evidence are separate associations.

Planned use-evidence record, only where real evidence requires it:

`research/use-evidence.tsv`

`evidence_id | use_id | file_id | evidence_locator | status | evidence_basis | notes`

Semantics:
- `corpus/files.tsv` remains the sole canonical owner of file identity, filename, checksum, coverage, preservation and rights provenance;
- use-evidence records only that a concrete Project→Source use actually used a concrete file/instantiation;
- `evidence_locator` is a locator inside that used digital instantiation when needed;
- `source-uses.relevant_locus` remains the source-relative scholarly scope and is not the same datum;
- one use may have `0..n` evidence records;
- the same file may support multiple uses;
- no evidence binding is inferred from Source membership or `part_of`;
- `source_id` is not repeated in use-evidence when it is deterministically resolvable from `use_id`.

### Mandatory migration invariant
Every current `primary_file_id` must remain traceable after any later migration as:

`old project-source row → new use_id → use-evidence → same file_id`

No existing exact-file selection may disappear merely because the Project→Source association is normalized.

## Later resolver/design expectations
A later admitted Contract/Resolver design should be able to expose, without fabricating relations:
- defining Project root;
- derived structural status;
- valid `part_of` ancestry paths;
- all Project→Source uses and `research_functions[]`;
- each use's explicit use-evidence records and canonical file provenance;
- Project(s) structurally containing the Source, if that information is actually useful and derivable.

This is a design requirement, not authorization to change code now.

## Explicitly not decided here
- no duplicate-exact-root hard-fail rule is established; no current demonstrated case requires it;
- no ancestor/descendant Project-root prohibition;
- no closed `research_function` vocabulary;
- no universal claim/evidence ontology;
- no Project→Project relation generated from Source use;
- no Source-work path architecture;
- no G2 Line/Span/Phenomenon representation.
