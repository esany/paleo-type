## Demonstrated failure / trigger

The current model can represent:

- canonical Source/File identity in `corpus/`;
- Source→Source structure in `corpus/relationships.tsv`;
- one purpose-established Project with one `project_source_id`;
- Project→Source research use in `source-uses.tsv`;
- exact use→File evidence in `research/use-evidence.tsv`.

It does **not** currently expose a canonical owner for a different fact:

> a bounded research corpus / Project set selected by one archival finding-aid path across several independent archival units.

The current Wolkenburg fixture makes this real rather than hypothetical:

`Sächsisches Staatsarchiv → Bestand 20578 Rittergut Wolkenburg mit Kaufungen → 10 → 10.5 → 10.5.3 Oppurg, Knau, Grunau, Gröbitz`

Human-Owner input is that the independent Archivalien within this group are intended as independent durable Projects, each with its own documentary root. The catalogue path therefore selects a **set of Projects/Sources**; it is not itself the documentary root of any one Project.

## Why this is a bug

`methodology/maintenance.md` gives canonical owners for Source/File truth and for individual Project purpose/root/scope, but no owner for a reproducible catalogue-defined selection spanning several Projects.

Without an explicit owner, a future agent is pushed toward one of several wrong substitutes:

1. repeat the selection prose in every `project.yml`;
2. use `projects/relationships.tsv` as a collection registry although it owns explicit Project→Project relations;
3. manufacture catalogue hierarchy as documentary `part_of` Source structure;
4. use fonds / catalogue group as `project_source_id`;
5. keep the corpus boundary only in chat, README or an Issue;
6. rely on the current set of created Projects as an implicit completeness claim.

Each option either duplicates truth, changes semantics, or destroys restartability.

## Scholarly / archival consequence

Catalogue arrangement/context and documentary provenance/containment are not identical. A finding-aid hierarchy may truthfully define the **selection boundary** while the selected Archivalien remain independent historical/documentary roots.

The model therefore needs to preserve at least these distinct questions:

- what documentary Source is one Project anchored to? → existing `project_source_id`;
- which Sources/Projects are selected by a declared catalogue boundary? → currently no canonical owner;
- is the selected catalogue set complete at a stated access/snapshot state? → coverage question, not Project structure.

## Kommentar 5984967291 · 2026-10-04T22:09:24Z · esany

## Analysis result — existing owners are insufficient; the missing object is a Source-set selection, not a Project hierarchy

Fresh comparison of `maintenance.md`, `project-lifecycle.md`, `source-and-provenance.md`, current corpus tables and the Wolkenburg owner decision rules out the “no new owner” option for this case.

### Why current owners cannot carry the fact truthfully

- `corpus/sources.tsv` owns historical/documentary Source identity. The finding-aid path `20578 / 10 / 10.5 / 10.5.3` is an archival arrangement/selection boundary, not itself demonstrated as one historical/documentary Source.
- `corpus/relationships.tsv: part_of` owns historical/documentary containment, not catalogue classification membership.
- `projects/<id>/project.yml` owns one Project's purpose/root/current scope. Repeating the shared catalogue selector in every Project would duplicate truth.
- `projects/relationships.tsv` would falsely turn set membership into Project→Project relations.
- Files cannot define membership because non-digitised/unavailable Archivalien may still belong to the selected catalogue set.

Therefore a durable cross-Project/source selection cannot be derived losslessly from the current owners without semantic abuse.

### Smallest conceptual owner

Introduce a lean **CORPUS-level Source-set selection object** (name/physical format not decided here) with two responsibilities only:

1. **selection definition** — stable selection identity, archive/fonds/finding-aid selector/path, human research-selection basis, catalogue snapshot/access basis and explicit inclusion rule;
2. **membership** — references to the canonical Source IDs of the independent Archivalien currently evidenced as members of that selection.

Membership should be Source-based, not Project-based. This is essential because:

- Source membership can be established before Project materialization;
- unavailable/not-digitised material can belong without a File;
- Project creation remains a separate Human-Owner decision even though the current Wolkenburg owner decision intends the relevant independent Archivalien to become Projects;
- existing Projects, when present, can be related/derived through their `project_source_id` rather than being the primary corpus-selection truth.

### Keep boundary, membership and completeness separate

The selection owner states **what boundary/set is being represented** and its observed members. It must not by itself assert that the enumeration is complete.

Completeness/discovery coverage requires a separate evidence record under the #12 requirement:

- catalogue/repository searched;
- snapshot/access date;
- inclusion/exclusion logic;
- known unavailable/not-digitised/not-found states;
- bounded completeness conclusion and evidence basis.

The selection may reference that coverage result, but must not duplicate its evidential contents.

### Wolkenburg application

Conceptually:

```text
selection: SStA 20578 / 10 / 10.5 / 10.5.3
  member Source: archival unit Nr. 632
  member Source: archival unit Nr. 754
  member Source: ... as evidenced at the documented catalogue snapshot
```

Each member Source remains an independent documentary root. A later Project for Nr. 632 or Nr. 754 uses that Source as its own `project_source_id`. No catalogue-root Project and no catalogue `part_of` chain are created.

### Generic-Fit boundary

This is not a Saxon-archive special hierarchy. The generic requirement is only:

> when a research corpus is bounded by an externally defined catalogue/finding-aid selection spanning independent Sources, the selection and membership need a canonical owner distinct from Source identity, documentary containment and Project identity.

A non-Wolkenburg fixture should confirm the representation before implementation is accepted.

### Admission classification

This adds a new shared CORPUS information owner. It is therefore **material under D-016**. Analysis/requirements are now sufficiently narrow; exact file/table/YAML representation must be chosen during admitted design, not in this Issue comment.

**Disposition:** “no new owner” rejected; minimal CORPUS Source-set selection owner is the preferred concept. #12 supplies completeness evidence; #270 remains the Wolkenburg synthesis surface.
