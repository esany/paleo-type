- `id`;

`tools/source_contract.py` validates the executable contract. A Project can therefore pass deterministic validation while omitting fields that the canonical bootstrap template says are required.

## Why this matters

This is a direct contract/template drift failure:

```text
template says REQUIRED
≠
validator says optional / does not check
```

The risk is not cosmetic. `title` and `repository_role` are part of the human-readable Project identity/purpose surface. A formally valid but semantically underdescribed Project weakens restartability and makes future agents decide which rule is authoritative by interpretation.

Wolkenburg will potentially materialize several new Projects. Repeating the current ambiguity across a larger Project set increases the chance of structurally inconsistent bootstrap state.

## Analysis result — required Project metadata

Fresh check against `main@e18906c4d3f09645aca84d4c2fe17c37387c1109` resolves the ambiguity more narrowly than the Issue body initially states.

### 1. `title` is already a normative Project requirement

`methodology/project-lifecycle.md` explicitly requires a **unique Project ID and human-readable title** at Project creation. Current Project YAMLs also carry titles. The executable contract/test fixtures, however, permit a Project without `title`.

**Conclusion:** `title` is genuine template↔contract drift. The smallest repair is to make the executable Project contract enforce the already-accepted title requirement and add a negative regression fixture. This does not create a new Project semantic; it propagates an existing normative rule into its deterministic enforcement surface.

### 2. `repository_role` is different

The template currently says `repository_role` is REQUIRED, but `project-lifecycle.md` does not list it as a separate creation requirement. Its current content is useful explanatory material (why the work container/path exists, compatibility/boundary nuance), but much of the durable Project purpose is already owned by `research_object`, while the documentary boundary is owned by `project_source_id`.

**Conclusion:** do **not** promote `repository_role` into the executable required-key set merely because the template currently says REQUIRED. The lean correction is to make it optional/conditional explanatory metadata unless a distinct non-duplicative semantic requirement is separately demonstrated.

### 3. `active_scope` is intentionally not resolved here

The current non-empty `active_scope` requirement conflicts with the methodology's allowed “no current scope” state and is addressed in #265/#267. #264 must not accidentally lock that bug in while repairing `title`.

### Smallest repair target

- executable required Project keys gain `title`;
- template wording for `repository_role` becomes optional/conditional rather than REQUIRED;
- tests include a missing-title failure and no longer normalize the current drift by constructing valid fixtures without a title;
- no new YAML/schema framework;
- no Wolkenburg-specific metadata;
- #265 determines the later `active_scope` contract consequence.

### Admission classification

This analysis does not authorize implementation. The `title` change is best classified as **routine consistency propagation of an already-canonical Project requirement**, not a new architecture decision, if implementation is strictly limited to aligning template/contract/tests with the existing lifecycle rule. Any broader change to Project scope/state semantics remains material and goes through D-016 with #265/#267.

**Disposition:** analysis resolved / repair-ready; keep Issue open until the executable/template/test drift is actually repaired and verified.
