## Governing requirement
The repository must support source criticism at archival/record level before any transcription or interpretation can be treated as reliable. Software structure is acceptable only if it preserves provenance, transmission and recoverability without flattening archival distinctions.

## Review criteria
At a future structural refactor verify that the system can represent and keep distinct:
- archival unit / fonds / series / signature;
- record/document unit and record stage where supported;
- witness role in a concrete research question;
- archival locus (folio/page/region);
- digital/physical instantiation actually inspected;
- portal image, export/PDF page and working identifiers as separate mappings;
- catalogue assertions versus direct source observations;
- creation/administrative context and provenance;
- source relationships such as extract/copy/parallel/correspondence as evidence-bearing claims rather than identity shortcuts;
- incomplete, unavailable or only metadata-inspected material;
- archival boundary/completeness claims and their search/access limits.

Review whether current source IDs, `corpus/sources.tsv`, `corpus/files.tsv`, `corpus/relationships.tsv`, `corpus/events.tsv` and project crosswalks still provide one unambiguous provenance path without duplicate truth.

## Standards / expertise check
At review time re-check the then-current archival standards and guidance, including ICA Records in Contexts concepts/application guidance where applicable. Use standards to test conceptual adequacy, not to force RDF or a particular software stack.

## Measures if a gap is demonstrated
Choose the smallest sufficient action, for example:
- repair canonical ownership or identifiers;
- make record/witness/locus/instantiation distinctions explicit where currently collapsed;
- improve crosswalk/recoverability fields;
- add evidence/status to relationship claims;
- add deterministic referential checks if repeated structural errors exist;
- introduce formal RiC mapping only if interoperability/query requirements actually trigger #2;
- split or merge corpus records only when archival evidence, not convenience, requires it.

## Trigger
Review before a material data-model migration, when multiple archives/record systems create ambiguity, when source/file/folio identity errors recur, when transmission claims become consequential, or when external archival interoperability becomes an actual requirement.

## Definition of Done
- a third party can independently identify and recover every consequential source/locus/instantiation;
- catalogue metadata, archival inference and direct manuscript observation are distinguishable;
- source relationships expose evidence and uncertainty;
- no research claim depends on portal/export numbering being mistaken for archival structure;
- corpus completeness is stated only within documented boundaries;
- any new structure is demonstrably simpler or more reliable for archival source work than the one it replaces.

## Do not
Do not implement RiC-O/RDF, an archival database or a new hierarchy merely because it is standards-compatible. Do not let digital convenience redefine archival identity.

## Domain audit result — archival science / diplomatics

Audit basis: `GOVERNING_OBJECTIVE.md`; #38 reference frame; current `methodology/source-and-provenance.md`, corpus source/file/relationship records, project source register/inspection log, and real Knau crosswalk data. No repository structure was changed during this audit.

### Current external reference frame

- ICA **Records in Contexts – Foundations of Archival Description (RiC-FAD) 1.0** and **RiC-CM 1.0** (2023) are the current stable conceptual archival-description baseline.
- ICA states that RiC-CM integrates/develops/supersedes the older ISAD(G), ISAAR(CPF), ISDF and ISDIAH standards; those remain useful historical/reference material but are not the current target model.
- **RiC-AG 0.1** is now available as application guidance but remains explicitly preliminary/community-review guidance, so it must not be treated as a frozen implementation mandate.
- **RiC-O** is an optional formal RDF implementation layer; this audit finds no current research requirement that justifies adopting it.

### Concrete evidence from the current repository

**Strong existing support**
- `corpus/sources.tsv` preserves four distinct archival records, including the two Reg. Ii 3 records despite their shared volume/signature.
- `corpus/files.tsv` separately identifies exact archive exports by file ID, filename, SHA-256, coverage and preservation/rights state.
- source-data crosswalks explicitly separate export image, PDF page and archival folio and record whether the mapping is observed or inferred.
- the project source register correctly treats `principal`, `comparison`, `control`, `context` as project-relative functions.
- `inspection-log.tsv` distinguishes metadata (`K`) from primary image inspection (`P`) and records what each inspection can and cannot support.
- `corpus/relationships.tsv` correctly keeps the archival catalogue's extract assertion at `metadata-supported` while the observed Knau passage correspondence is a separate, weaker textual claim.

### Demonstrated weaknesses to hand off — do not fix here

#### A. Locus references are not yet canonical/referentially typed
`REL008` currently uses compound endpoint strings such as `THHSTAW-...:306v-309r` and `THHSTAW-...:61v-63r`, whereas other relation endpoints are canonical source/event/entity IDs. This is understandable to a human but cannot currently be validated as a canonical locus object/address. This is a real input for #36 and the Knau loss/integration test, not justification to create a locus table now.

Handoff:
`REQ-ARCH-009 → observed failure: mixed canonical IDs and ad-hoc source:locus endpoint strings → information requirement: canonical/typed locus addressability → candidate enforcement to be decided later: data model + referential validation`.

#### B. `document_type` partially mixes documentary form and record stage
For Reg. Ii 5 the value `Visitationsprotokoll / Auszug` combines a genre/form label with the consequential stage/relationship notion `Auszug`; the extract relationship is also separately represented as metadata-supported. The current state is not false, but the generic information ownership is not fully clean if later sources require original/copy/draft/extract distinctions.

Handoff:
`REQ-ARCH-010 → observed risk: form/stage semantics can be overloaded in one field or notes → information requirement: distinguish documentary form from consequential record stage when evidenced → enforcement mode deferred to #36 after other domain audits`.

#### C. Archival hierarchy is sufficient now but should not be over-read as a universal model
Current `archive`, `fonds`, `signature`, `record_id` fields recover the active sources unambiguously. RiC's richer network/context model shows that future heterogeneous archives may require more contextual entities/relations, but **no current failure demonstrates a need for a generic hierarchy refactor**. Status: `adequate now / future trigger`, not a gap.

### Specialist-review boundary
Independent archival/diplomatic review becomes material when identity/stage/provenance or transmission cannot be resolved from authoritative archival metadata plus direct inspection, when a strong original/copy/extract relationship becomes historically consequential, or when arrangement/provenance interpretation itself carries the historical claim. Ordinary ID/file/crosswalk integrity does not require specialist adjudication once the archival facts are established.

### Architecture consequence
This audit **does not justify** RiC-O/RDF, a graph database, a new archival hierarchy or a wholesale source-schema rewrite. It yields two concrete information-model risks for later synthesis: canonical locus addressability (REQ-ARCH-009) and clean form-vs-stage semantics where needed (REQ-ARCH-010). Everything else is adequately supported for the present project or remains trigger-bound.

### Definition-of-Done assessment
PASS for the domain audit: the requirements, current support, real failures/risks, evidence/judgement boundary and minimal handoff are explicit. No architecture has been pre-authorized and no research truth was changed.
