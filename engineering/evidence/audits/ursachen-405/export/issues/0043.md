## Text

## Motivation
The previous milestone rule was too narrow: it treated GitHub Milestones as governance/architecture-only and explicitly prohibited G1–G6 mirrors. That conflicted with the useful distinction already implicit in the repository: GitHub can organize both system-level work and project-specific scholarly Issues, as long as planning metadata never becomes canonical research truth.

This PR makes the distinction explicit and removes the contradiction between `MILESTONES.md`/README/D-010 and `methodology/maintenance.md`.

## Core model
GitHub metadata now has three orthogonal meanings:

- **Milestone = target / work phase**
- **Label = scholarly/technical domain or kind**
- **Issue = discrete work package**

Canonical scholarly state remains outside GitHub metadata:

- generic G1–G6 requirements → `methodology/research-gates.md`
- actual project gate state/gaps/next action → project `STATUS.md`
- source evidence/readings/decisions → canonical corpus/project records

## Milestone families

### Governance / architecture
Renames the structural sequence to an explicit family:

`GOV-M1 → GOV-M2 → GOV-M3 → GOV-M4 → conditional GOV-M5`

Existing planned mappings remain:
- GOV-M1: #41
- GOV-M2: #38, #26–#35
- GOV-M3: #36, #37, #39
- GOV-M4: #25
- GOV-M5: only if GOV-M4 authorizes implementation

### Project scholarly work
Allows project-scoped GitHub Milestones such as:

`ega-reg-ii-5-knau / G2 — Diplomatic representation`

These group discrete scholarly Issues contributing to a generic research gate. **Milestone completion does not establish gate completion.** `STATUS.md` remains authoritative for the evidence-based gate claim.

Milestone descriptions must not duplicate/redefine the generic gate requirements.

## Backlog semantics
- open Issue with Milestone = admitted/scheduled work
- open Issue without Milestone = backlog/deferred
- this applies to Issue-tracked work only; routine current research does not need an Issue solely to fit GitHub

Trigger-based future Issues (#1, #2, #3, #4, #6, #11, #12, #13, #22, etc.) therefore remain unmilestoned until deliberately scheduled or triggered.

## Files changed
- `MILESTONES.md` — generalized into milestone families, project-gate naming/lifecycle, labels vs milestones, backlog semantics
- `README.md` — removes the prohibition on G1–G6 mirrors and explains the two families
- `DECISIONS.md` — revises D-010 and records that it supersedes the initial narrower rule
- `methodology/maintenance.md` — aligns maintenance/trigger audits and STATUS-first synchronization
- `methodology/research-gates.md` — explicitly permits GitHub work-planning mirrors without changing scholarly gate ownership
- `AGENTS.md` — hard stop against treating Milestone progress/closure as evidence of gate attainment

## Deliberate non-changes
- no generic G1–G6 requirements are moved into GitHub
- no project `STATUS.md` state is changed
- no research reading/source claim is changed
- no new research Issues are created merely to populate Milestones
- no native GitHub Milestone objects are created by this PR; the connected tool does not expose Milestone creation, and the repository must not pretend those UI objects exist
- no new technical infrastructure

## Integrity check
- METHOD/CORPUS/PROJECT ownership unchanged
- GitHub remains navigation/planning only
- one Issue can have one primary target Milestone and multiple domain labels
- project-gate Milestone closure and scholarly gate attainment are explicitly different claims
- no-Milestone backlog semantics remain intact
- governance and project-research Milestones can coexist without collision because their naming families are explicit
