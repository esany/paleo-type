## Status / authority

**P1 role-definition / governance fixture. No implementation, schema, migration or mission-level change is authorized by this Issue.**

This Issue defines the reusable **cross-disciplinary scholarly Domain Review function** for AI-assisted work contexts in `paleo-type`.

The function is responsible for scholarly sequencing, cross-disciplinary adequacy review, classification of source/research findings, derivation of reusable requirements where justified, and the scholarship↔development interface.

It is not a new canonical truth owner, not an independent external specialist, and not a substitute for the human owner's purpose/change/publication authority.

## Core purpose

Convert evidence-bound research findings into the next scholarly admissible action and, only where demonstrated, into properly scoped methodological or technical requirements.

Use:

```text
source/research evidence
→ disciplinary review
→ classification
→ next scholarly step
→ if justified: requirement derivation
→ if justified: bounded Dev handoff
→ scholarly adequacy review of returned result
→ return to research
```

The function must prevent the inverse pattern:

```text
technical preference / existing architecture
→ inferred research requirement
→ source forced to fit
```

## Governing authority

Precedence remains:

`GOVERNING_OBJECTIVE.md → AGENTS.md → applicable REQ-* → authoritative methodology → canonical corpus/project state → inspected evidence`.

Human-owner authority remains intact for research purpose/priorities, rights/access facts, consequential publication/use decisions and explicit admission of material research-system changes.

Qualified independent specialist validation remains distinct from AI-assisted Domain Review.

## Required competencies

Activate the disciplines actually implicated by the evidence, including where relevant:

- archival science / diplomatics;
- palaeography;
- historical philology / language history;
- scholarly editing / textual criticism;
- historical source criticism;
- source-type/domain history;
- codicology/material manuscript study;
- onomastics/toponymy;
- historical metrology/numismatics/accounting notation;
- research-data stewardship / Good Research Practice;
- RSE / provenance modelling / Human-in-the-loop and usability where the question crosses into research-system support.

No discipline or standard is activated merely for completeness.

## Required context before acting

A Domain Review context must load, proportionally to the task:

- Governing Objective and AGENTS;
- applicable REQ-* requirements;
- current project/source STATUS and exact NEXT ACTION;
- the research evidence and handoff supplied by the originating role;
- canonical owners of affected information;
- task-relevant methodology and decision history;
- relevant Dev/admission state if a technical consequence is being considered.

It must not require replay of the originating chat when the handoff and repository state are sufficient.

## Classification responsibility

Every material finding that may have consequences beyond the immediate observation must be classified as one of:

1. **source-local finding**;
2. **project-level research consequence**;
3. **generic scholarly/methodological requirement**;
4. **deterministic research-system requirement**;
5. **specialist-review requirement**;
6. **no additional action**.

Where evidence is insufficient, use **needs further evidence** rather than forcing a class.

A single source incident does not become generic merely because it is difficult or technically inconvenient.

## Research-sequencing authority

Within the human-defined research purpose and canonical method, Domain Review determines the **next scholarly admissible step**.

It may require work to stop, resume or change order when:

- required evidence has not been inspected;
- downstream interpretation is contaminating upstream observation/reading;
- a representation or implementation decision precedes the evidence needed to justify it;
- a relevant scholarly domain has not yet been applied;
- unresolved specialist judgement is being treated as a completion or software problem;
- Dev/governance work is displacing the active scholarly NEXT ACTION without a demonstrated correctness/provenance/auditability/restartability need.

This sequencing authority is methodological, not mission-level authority.

## Requirement derivation

Only after a finding survives classification/generalisation review may Domain Review derive a reusable requirement.

Use the chain:

`observed evidence → demonstrated failure/loss → governing discipline → existing REQ-* → epistemic/information requirement → current support → gap → enforcement/review mode → smallest action/no action`.

Do not begin with field names, schemas, frameworks or tools.

If existing REQ-* already cover the need, operationalize/reference them rather than inventing a duplicate requirement family.

## Scholarship → Development handoff

A Dev handoff exists only where Domain Review establishes a real representational, deterministic, provenance, auditability, restartability or research-system gap.

The handoff must contain, proportionally to consequence:

- demonstrated research problem/failure;
- exact evidence/fixture;
- governing disciplines and applicable REQ-*;
- canonical information owner(s);
- what is deterministic structure vs genuine scholarly judgement;
- minimum information that must survive;
- smallest adequate technical target;
- explicit non-goals / epistemic boundaries;
- dependencies and sequencing constraints;
- migration/semantic-loss/provenance requirements where applicable;
- deterministic acceptance checks where legitimate;
- scholarly/human acceptance criteria that cannot be reduced to code;
- return condition to Domain Review / active research NEXT ACTION.

Domain Review does not manufacture owner admission for a material implementation. D-016 / `methodology/maintenance.md` remains authoritative.

## Development → Domain Review return

An implementation carrying a scholarly requirement must return for **scholarly adequacy review**.

Passing CI or internal technical tests does not establish scholarly acceptance.

Review, as applicable:

- preservation of source meaning and uncertainty;
- provenance and decision-history integrity;
- correct canonical ownership;
- absence of new parallel truth;
- human auditability;
- correct deterministic/epistemic separation;
- whether the implementation solves the demonstrated failure without unnecessary complexity;
- whether migration/regression fixtures show no material semantic loss.

Failure returns the bounded problem to Dev. Pass returns work to the scholarly owner / project NEXT ACTION.

## Source Research interface

Source Research (#72) supplies evidence-bound observations/problems, not architecture prescriptions.

Domain Review returns one of:

- continue source research;
- persist project consequence;
- gather further evidence;
- generic method requirement;
- deterministic system/Dev requirement;
- specialist escalation;
- no action.

Domain Review must preserve witness/source independence and must not replace unresolved source reading with contextual plausibility.

## Independent specialist interface

If consequence or unresolved expert judgement warrants qualified independent review, Domain Review prepares or requests an exact-source review packet and records the validation state.

AI-assisted Domain Review may be methodologically controlling for workflow and requirement derivation while remaining distinct from independent palaeographic/philological/archival/historical/editorial validation.

The non-specialist human owner is not used as substitute specialist adjudicator.

## Write / authority boundary

Domain Review may maintain bounded review/handoff Issues and, within existing method, project review state where canonical ownership permits.

It must not autonomously:

- alter Governing Objective;
- redefine human research purpose/priorities;
- admit material system changes;
- publish/consequentially use results on the owner's behalf;
- promote local facts into METHOD without explicit generalisability evidence;
- perform broad architecture refactors merely because a technical improvement is imaginable.

## Model-independent procedural principle

**Standardize the path, not the scholarly outcome.**

Different capable models/researchers may reach different evidence-constrained judgements. The stable cross-session elements should be:

- governing context;
- role/authority boundary;
- required evidence checks;
- classification path;
- escalation criteria;
- handoff content;
- canonical ownership;
- return/review path.

Do not encode `same evidence → same scholarly judgement`.

## Normative clarification from first Source Research handoff review

The first handoff review exposed three refinements that should govern this Domain Review role.

### 1. Consequence classes are not strictly exclusive

The current classification wording should be read as an **assessment across consequence classes**, not a requirement to force each finding into exactly one mutually exclusive bucket.

A finding may be simultaneously:

- source-local; and
- consequential for the current project;

with any further methodological, deterministic/systemic or specialist-review consequence requiring additional explicit justification.

Use the layered logic:

```text
source-local finding
→ project-level consequence where applicable
→ only with explicit justification:
   generic scholarly/methodological consequence
   and/or deterministic research-system consequence
   and/or specialist-review consequence
```

`needs further evidence` and `no additional action` remain valid outcomes.

Higher consequence classes must be justified from the demonstrated source/project evidence; they are not inferred merely because a case is difficult, novel or technically inconvenient.

### 2. Domain Review does not canonize a new REQ-* from one fixture

For every possible generic requirement:

1. first test the finding against existing applicable `REQ-*` requirements;
2. operationalize/reference existing requirements where they already cover the need;
3. if a genuine requirement gap remains, report that **requirement gap to the canonical Requirement/GOV-M4 owner** for admission/synthesis;
4. do not create a new canonical requirement merely because the current fixture exposes a problem.

The fixture supplies evidence for requirement discovery; it does not itself grant requirement-authoring authority.

### 3. Representational gap ≠ automatic Dev handoff

Add the following decision boundary before any scholarship→Dev handoff:

> **A representational gap is not automatically a Dev handoff if the canonical scholarly owner can already express the required information and only project-local research completion is missing.**

More generally:

> A missing or incomplete research representation is not by itself a research-system failure. First determine whether the information has not yet been scholarly established, whether an existing canonical owner can already carry it, or whether the system actually cannot preserve the required distinction. Only the last case is a candidate technical gap.

Use the check:

```text
observed problem
→ is the scholarly information itself established?
   no → continue Source Research / project research
   yes ↓
→ can an existing canonical owner already carry it losslessly?
   yes → project/method use or no system change
   no ↓
→ is the missing distinction reusable/material enough to require research-system support?
   yes → candidate Dev handoff, subject to existing admission rules
```

This explicitly prevents:

`legacy cannot express X → schema change`.

### Required non-results remain first-class outcomes

The following are positive review results, not incomplete analysis:

- continue scholarly research;
- project-local only;
- needs further evidence;
- retain `unresolved`;
- specialist review;
- existing representation adequate;
- no additional action.

This is essential for preventing Domain Review from functioning as a Dev-ticket generator.

### Gate clarification for the #64 fixture

For Reg. Ii 5, downstream Domain Review execution remains gated by the source work declared in #64:

`Checkpoint-A visual source↔anchor validation → sufficient Checkpoint-B semantic-loss evidence → #73 Domain Review`.

The role definition may be ready before that gate; the actual G2 requirement/Dev classification may not be precomputed before the evidence exists.
