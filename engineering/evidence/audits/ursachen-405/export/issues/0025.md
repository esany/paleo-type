## Prerequisite
Do not approve a material repository-wide refactor until #41 has established `GOVERNING_OBJECTIVE.md` as the canonical governing objective with explicit human change authority. Every later structural/technical decision in this issue must demonstrate alignment with that objective before implementation.

## Purpose
This issue is the synthesis/controller for a domain-driven redesign of `paleo-type`. It must not accumulate another layer of method prose. Its job is to decide which scholarly requirements belong in:

- normative scholarly method;
- canonical information/data structures;
- deterministic invariants/validation;
- derived human-readable views;
- AI/Human-in-the-loop workflow;
- independent specialist judgement;
- or no new structure at all.

The target is a smaller, more robust system in which fewer correctness requirements depend on agents interpreting duplicated prose.

## Derivation rule
Every structural or technical decision must be derived in this order:

`scholarly objective → research/source requirement → governing discipline → evidence/standard/expert practice → epistemic requirement → information requirement → enforcement/review mode → technical implementation`

A proposal that starts from a technology and searches for justification afterwards fails this audit.

## Execution sequence

### Phase A — Scholarly requirements discovery
1. **#38 — State of the art / standards / expert knowledge refresh** establishes the current reference frame and distinguishes formal standards, disciplinary practice, empirical evidence, tacit expertise and source-specific choice.
2. **#26–#35 — Domain audits** derive explicit requirements. Each material finding must be expressed as:

   `requirement → why it matters → evidence basis → information needed → failure if absent → validation/judgement type`

3. Real Knau material, especially Reg. Ii 5 fol. 61v–63r and its legacy representation, is used as a representative test case to falsify or confirm abstract requirements. Knau is a test vector, not the generic model.

### Phase B — Architecture derivation
4. **#36 — Research software/data engineering** maps stable deterministic requirements to the smallest adequate canonical structures, schemas, referential checks, migrations and derived outputs.
5. **#37 — AI/HITL** determines which epistemic tasks remain judgement-based, how AI evidence is separated from validation, and where independent specialist escalation is required.
6. **#39 — Human usability/transparency** tests whether a non-specialist owner and a reviewing specialist can reach the relevant source/result/evidence without understanding internal storage machinery.

For every requirement choose explicitly one primary enforcement mode:

`method prose | canonical data model | deterministic validation | derived human view | AI workflow rule | specialist judgement | no action`

Duplicating the same invariant across several modes requires a concrete reason.

### Phase C — Structural synthesis
7. This issue produces one matrix:

`requirement → current support → observed failure/gap → chosen enforcement mode → smallest change/no change → migration/test consequence`

8. Compare at least:
- no refactor;
- targeted consolidation/validation changes;
- material structural refactor.

9. Any approved migration must be cohesive and tested against representative real project data. It must preserve provenance, readings, uncertainty and decision history.

### Phase D — End-to-end validation
10. Validate the resulting structure by asking:
- Can a historian understand the investigation, diplomatic text, uncertainty, evidence and next action from repository + source without chat?
- Can a specialist drill from a consequential claim to exact source evidence and decision history?
- Can deterministic structural errors be caught without relying on prompt obedience?
- Is there one canonical owner per fact/state/rule?
- Are generated human views derived rather than parallel truth stores?
- Has normative prose become smaller rather than merely moved?

For each material domain finding classify current support as:

`adequate | gap | risk | needs evidence | not applicable`

and record:

`scholarly requirement → evidence/standard/expert practice → current representation → observed failure/risk → information requirement → enforcement mode → smallest candidate measure`

Do not promote a candidate technical measure merely because a requirement exists.

## Key anti-bloat rule
If a rule is deterministic and stable, prefer making it structurally impossible or machine-checkable over repeating it in `AGENTS.md`, workflow prose, gates and project instructions.

If a rule is genuinely epistemic, keep it in the smallest authoritative methodological location and reference it rather than rephrasing it elsewhere.

If a rule exists only because of one project incident, keep it project-local until generalisability is demonstrated.

## Definition of Done
This issue is complete when:
- #41 is complete before any material mission-level refactor is approved;
- relevant #26–#39 reviews have explicit outcomes;
- the domain-to-information-to-technology derivation is visible;
- duplicated/prose-only invariants have been identified;
- representative Knau data has been used for migration/loss testing without defining the generic architecture;
- the smallest justified structural option has been selected, including `no refactor` if appropriate;
- approved implementation has tests/migration checks and a human-readable result path;
- another capable researcher/AI can work correctly without reconstructing a distributed rule hierarchy or old chat.

## Non-goals
- no database, RDF, TEI authoring system, UI, multi-agent system or schema framework is pre-authorized;
- no wholesale rewrite merely to make the repository look architecturally cleaner;
- no additional parallel methodology layer;
- no assumption that more formal structure is better unless it prevents a demonstrated research failure or materially improves auditability/reproducibility.

### 4. Concrete current inconsistencies exposed by the review

**A. Person identity, association, agency and role are flattened.** `corpus/sources.tsv` still carries flat `persons` strings for both 1533 Ziegenrück source groups, while `events.tsv` correctly separates the documented visitator commission (Menius, Myconius, Wangenheim, Denstedt, Kothe/Cotta) from Johann Friedrich as sovereign authority. `entities/persons.tsv` still encodes context-dependent roles in identity notes, misses Wangenheim, and has the Kothe/Cotta identity problem unresolved. The user's simple question “who are the documented actors per source group?” cannot currently be answered from one evidence-clean representation.

**B. Dates were previously allowed to leak across levels.** The removed `1533-03-03` normalization demonstrates the failure class: a chronology/event date or wider context can be transferred to a bounded group and become falsely precise. The current correction is good, but the generic semantic rule should now be explicit: archival-unit dating, event/field-visit dating, source-group/document production dating, and copy/extract/redaction dating are different claims and do not inherit downward automatically.

**C. Research-function/priority separation was partly over-corrected.** `project-lifecycle.md` correctly says an actual `(Project, Source) → research_function` belongs in `source-uses.tsv` and does not establish current priority. Yet Reg. Ii 4 `source-uses.tsv` is empty despite completed principal diplomatic work on Reg. Ii 4 and an explicit controlled textual comparison with Reg. Ii 5. Avoiding role→priority inference by omitting real use history loses useful state. Reg. Ii 5, by contrast, retains its historical use rows. The correct protection is **persist the actual use, forbid priority inference separately**.

**D. Completion state is not propagated consistently.** Reg. Ii 4 `STATUS.md` says the bounded #96–#99 workflow is complete and a new owner/roadmap choice is needed, while `project.yml:active_scope` still describes the Knau inspection as active. Issue #100 also remains open although its own completion condition (#96–#99 resolved plus post-collation decision recorded) is met. This is restartability residue, not a scientific disagreement.

**E. Reg. Ii 5 provenance quarantine is too path-wide.** `legacy-witness-provenance.tsv` treats `research/g2-*` wholesale as witness-provenance-uncertain. That is appropriate for G2 claims derived from ambiguous legacy readings, but not for directly source-verified baseline provenance and physical/source-order observations whose File/locus are explicitly Reg. Ii 5. Provenance must follow the **evidence lineage of the artifact/claim**, not the directory name in which it lives.

**F. Planning/audit surfaces contain superseded operational state.** PR #93 deliberately reconstructed the accepted repair from `main` without promoting PR #88/#92 history, but PR #88 and #92 remain open. Issue #64 still contains historically valuable source-work and G2 evidence but its active-work language conflicts with the current Reg. Ii 5 STATUS (`no owner-selected manuscript task`). These surfaces should remain audit evidence where useful, but their current/superseded status needs explicit reconciliation so a fresh session does not infer priority from an old open item.

**G. The relationship ledger is already more general than its documentation/validation admits.** `corpus/relationships.tsv` is described mainly as Source→Source relations, but current data already includes Source→event and Source→place relations. The validator strongly checks `part_of` and `textually_corresponds_to`, while generic contextual endpoints are only weakly constrained. The agent-role problem therefore should first test whether this existing evidence-bearing relation mechanism can be made consistently typed/validated rather than introducing a new agent subsystem.

### 5. Learnings to feed back into the concept

1. **Maturity must be read by evidence dimension, not one project status label.** At minimum distinguish source identity/provenance, source-exact observation/reading, adjudication/collation, validation, and current activation/priority. These need not become a new schema; they are a reasoning/restartability rule for STATUS and review.
2. **Current activation is not evidential authority.** A dormant Project can contain valid source-specific evidence; an open Issue can be stale; a legacy directory can contain both unreliable old readings and later exact-source observations.
3. **Provenance follows the claim/artifact lineage, never the path label.** Quarantine/migration must be granular enough to preserve directly re-established evidence instead of downgrading it because neighboring material is ambiguous.
4. **Contextual roles are relations, not entity properties.** Person identity must remain identity-only. `visitator`, `sovereign authority`, `scribe`, `mentioned person`, `local informant`, etc. must be evidence-bearing claims tied to the exact event/source/stage they concern. Event membership must not be projected automatically onto every source group.
5. **Dates are contextual claims with an exact subject/stage.** No downward inheritance from archival unit/event/neighboring itinerary. Exactness may be downgraded without changing broader cycle context.
6. **Persist actual research use; keep priority separate.** `principal`, `comparison`, `context`, etc. describe what happened in a Project. They must not be erased merely because the Project is no longer active or because roles must not imply NEXT ACTION.
7. **Completion is a state transition.** When a bounded scope finishes, `active_scope`, STATUS, and planning surfaces should be reconciled in one bounded consistency pass; completed scope remains history, not active work.
8. **Migration quality has three independent dimensions:** information survival, work-state survival, and authority/provenance survival. The 2026-09 recovery already established this principle; the Reg. Ii 5 over-quarantine shows why it must also be applied at artifact/claim granularity.
9. **Vertical source work is the best architecture test.** Reg. Ii 4 #96–#99 exposed more useful model facts than abstract schema work: witness independence, release timing, real use history, no-correction outcomes, and completion-state propagation.
10. **Do not answer a semantic gap by adding another subsystem.** The current file-based architecture remains adequate. First consolidate semantics in existing owners and add deterministic checks only where the meaning is settled.

### 6. Existing requirements already cover most of this — do not add a new requirement family

The findings are primarily a tighter application of existing requirements:

- REQ-ARCH-002: provenance/context separate from record and interpretation, including event/agent/context claims;
- REQ-ARCH-005: catalogue assertion, inference and direct inspection separate;
- REQ-ARCH-006: relationships are evidence-bearing claims;
- REQ-ARCH-007: research function is Project-relative;
- REQ-ARCH-010: documentary form/stage remains distinguishable when consequential;
- REQ-GWP-001/002/004/008: one owner, exact provenance, reconstructable revisions, restartability;
- REQ-RSE-003/004/005/008: canonical/derived separation, referential integrity, formalization only for stable semantics, loss-aware transformation.

No new generic ontology or requirement namespace is justified by this review.

### 7. Smallest concept to carry forward

**Concept A — contextual-claim discipline.** Identity tables remain identity-only. Dates, agents/roles, source stage, event membership and transmission assertions are attached to the exact subject they describe with evidence/status. Do not infer event agents as source-group actors or archival-unit dates as local document dates. First test reuse/clarification of the existing relationship ledger; add structure only if real validation/retrieval needs cannot be met there.

**Concept B — project-state discipline.** Persist actual Project→Source uses independently from current priority. `STATUS.md` owns current gate/NEXT ACTION; `project.yml:active_scope` must not remain active after the bounded scope has completed. Completion triggers a bounded consistency check of volatile project/planning surfaces.

**Concept C — provenance-granular legacy recovery.** Replace path-wide scientific classification with artifact/claim-level lineage where evidence differs. For Reg. Ii 5 specifically, direct exact-File baseline provenance and source-order/phenomenon observations should be distinguishable from witness-ambiguous old transcription/apparatus claims. This does **not** automatically promote the old readings.

**Concept D — typed dating by use, not premature universal schema.** The method/Corpus semantics must state which object a date belongs to. Keep current simple date fields where truthful; use explicit contextual/event/redaction claims when a single pair would conflate distinct temporal assertions. Only introduce a more formal date-claim structure if repeated real data requires it.

No material implementation is performed by this checkpoint. If admitted, the smallest order is:
