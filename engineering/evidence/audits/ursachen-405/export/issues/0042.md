## Text

## Motivation
The repository now has a substantial set of trigger-based future issues plus the P1 governing-objective work and transdisciplinary structural-audit issues. Without an explicit work-sequencing model, GitHub does not clearly distinguish scheduled governance work from intentionally deferred backlog.

This change makes that distinction explicit while preserving the repository's key rule that GitHub metadata is navigation only and never canonical research truth.

## Changes
- add top-level `MILESTONES.md` defining:
  - M1 — Governing Objective & Mission Protection (`#41`);
  - M2 — Scholarly Domain Architecture Audit (`#38`, `#26–#35`) with #38 first, domain reviews next/parallel, and #35 as cross-domain integrity consolidation;
  - M3 — AI, Engineering & Human Usability Audit (`#36`, `#37`, `#39`);
  - M4 — Structural Synthesis & Refactor Decision (`#25`);
  - conditional M5 only if M4 explicitly authorizes implementation;
  - no-Milestone = backlog/deferred-until-trigger semantics;
  - entry/exit conditions, required outputs, internal ordering and anti-scope-creep rules for each phase.
- update `README.md` so GitHub Milestones no longer mirror G1–G6; G1–G6 remain scholarly maturity states in `research-gates.md` + project `STATUS.md`.
- add `DECISIONS.md` D-010 recording the durable rule that Milestones schedule admitted work, while unmilestoned Issues remain backlog.

## Key design rule
`M1–M4` organize a bounded governance/architecture review. They are not research maturity, evidence confidence, or a substitute for project `STATUS.md`.

The intended sequence is:

`M1 mission protection → M2 scholarly-domain requirements → M3 AI/engineering/human-usability derivation → M4 refactor/no-refactor decision → conditional M5 implementation`

## Backlog
Existing technology/future issues such as #1, #2, #3, #4, #6, #11, #12, #13 and #22 stay unmilestoned until their own triggers are demonstrated or a governing audit explicitly admits them.

## GitHub metadata follow-up
The current connected GitHub tool can assign an Issue to an existing Milestone but does not expose Milestone creation. Therefore this PR defines the exact native Milestone names and assignments, but does not create the GitHub Milestone objects themselves. Once the four M1–M4 objects exist, Issues can be assigned exactly according to `MILESTONES.md`. M5 must not be created in advance.

## Acceptance check
- no new research truth store is introduced;
- G1–G6 are not duplicated as GitHub Milestones;
- no implementation is pre-authorized;
- `no milestone` has a clear intentional meaning: backlog/deferred until trigger;
- each active governance phase has explicit entry/exit criteria and required outputs.
