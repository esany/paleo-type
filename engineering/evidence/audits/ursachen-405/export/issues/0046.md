## Text

Implements the canonical repository-level part of #41.

## Problem
The repository's scholarly mission was already expressed across README, AGENTS, method and decisions, but there was no single highest-order canonical objective with explicit precedence, AI operating consequences and human-only material change authority.

## Changes
- add a short, implementation-independent `GOVERNING_OBJECTIVE.md`;
- make transdisciplinary source/problem orientation, genuine Human-in-the-loop, result-to-evidence provenance/auditability and lean technical subsidiarity explicit;
- require AI to load the objective, mandatory guardrails and all canonical requirements applicable to the concrete task before acting;
- add a hard stop against autonomous material objective changes;
- reference the canonical objective minimally from README, authoritative scholarly workflow, maintenance and D-013 rather than duplicating it;
- add narrow `.github/CODEOWNERS` ownership for `GOVERNING_OBJECTIVE.md` by `@esany`;
- update #25 separately so future structural/technical decisions must demonstrate alignment with the objective.

## Human authority
The repository owner explicitly confirmed the governing principles during #41 work: the problem is transdisciplinary; Human-in-the-loop and provenance/appropriate traceability from result to evidence are central; other structures should be lean; AI may propose but not autonomously change the objective; material objective changes require the owner's explicit decision.

## Validation
The seven #41 drift scenarios were checked and documented on #41. No implementation-specific choice (TSV, TEI, RiC, database, model, G1–G6, GitHub or Knau) is constitutionalized.

## Deliberate non-changes
- no manuscript readings or transcription content;
- no source relationships or source identity;
- no project gate state / Knau STATUS / NEXT ACTION;
- no schema/data migration;
- no application, database or agent architecture.

## GitHub protection limitation
The API shows no current repository rulesets. GitHub supports protected-branch PR/code-owner-review rules for public repositories, but this integration exposes no write action for those settings. CODEOWNERS therefore provides the narrow repository-side review-routing measure available here; a `main` protection/ruleset requiring PR + code-owner review remains the one hard-enforcement step to enable in repository settings.
