## Status / authority

**P1 generic workflow / information-requirement derivation. No storage platform, repository split, media subsystem, asset manager or bulk source migration is authorized by this Issue.**

This Issue derives the smallest generic source-intake / evidence-availability workflow required so that a source supplied once for active research does not become unusable merely because the original chat/session ends.

The immediate Reg. Ii 5 case has demonstrated a gap between **reproducible provenance** and **research-ready evidence availability**.

## Demonstrated failure

In #68 the supplied Reg. Ii 5 PDF was:

- byte-exactly verified;
- mapped through the canonical folio ↔ export-image ↔ PDF-page crosswalk;
- rendered reproducibly to four unprocessed baseline PNGs;
- directly inspected in the then-current research context;
- documented with parent SHA, render recipe and restart instructions.

However, the PDF/PNGs were not persisted in a location reachable by a fresh authorized work context. The earlier conclusion that restartability was satisfied by `parent identity + recipe + authorized researcher can reproduce` therefore proved insufficient for the actual project operating model.

A later Source Research chat can know exactly **which evidence should exist** while still being unable to **open the evidence needed for the current NEXT ACTION**.

## Governing distinction

The project must distinguish at least three independent properties:

```text
IDENTIFIABILITY
Which exact source/file/image is this?

REPRODUCIBILITY
Can a defined derivative be recreated from a verified parent?

RESEARCH-READY AVAILABILITY
Can an authorized current/fresh work context actually open the evidence required for the next scholarly action?
```

None implies the others automatically.

A URN, File ID, SHA-256, page crosswalk or render recipe may establish identity/provenance. It does not by itself make the image available to a human reviewer or Source Research context.

## Research-ready source-access invariant

For source work requiring visual inspection:

> **Authoritative identifiers secure reference; accessible image instances secure research. Both are required.**

A source/intake step is not operationally complete for active visual research merely because the evidence could theoretically be reacquired or regenerated later.

At least one authorized access path to the actual source representation needed for the current work must be known and testable.

## Candidate generic intake path

Derive and test the smallest form of:

```text
source/file supplied or discovered
→ establish Source/Project context
→ establish exact File/instance identity where applicable
→ capture evidenced institutional identifiers/URNs when actually present
→ determine rights/access/redistribution constraints
→ determine whether the current research requires direct image/file access
→ establish durable authorized evidence location or retrieval path
→ record canonical identity/provenance without duplicating the binary as metadata
→ create/recreate working derivatives where needed
→ verify fresh-context access to the evidence required by NEXT ACTION
→ only then declare research-ready restartability
```

Do not assume every source requires repository-local binaries. A stable institutional access path may be sufficient if a fresh authorized context can actually retrieve/open the needed representation reliably.

Conversely, do not treat a stable URN as sufficient when the human researcher still cannot inspect the image from the working environment.

## Rights / storage boundary

Separate these questions explicitly:

1. **May this file/image be publicly redistributed?**
2. **May it be stored in a controlled/private research environment?**
3. **May it only be accessed from the institution/provider and not retained?**
4. **Who/what is authorized to retrieve it for research?**

`not publicly redistributable` must not be silently collapsed into `must remain transient`.

Likewise, `private repository` must not be assumed to satisfy rights conditions without evidence.

Where rights/access facts are genuinely owner-only or externally constrained, route the narrow decision/fact to #75 Human Owner/Governance. Routine technical storage mechanics remain outside owner micromanagement once the allowed class is known.

## Visible/institutional identifiers

If an institutional URN/identifier is visibly printed or otherwise directly evidenced on the source image/page:

- capture it as observed evidence;
- verify/resolve it where technically possible and relevant;
- do not synthesize or infer identifiers from naming patterns;
- preserve distinction between identifier and actual accessible image instance.

The Reg. Ii 5 fixture should explicitly re-check the visible per-leaf URNs rather than retain the prior assumption that no stable image URNs are available.

## Fresh-context restart test

A workflow claiming active-source restartability should pass a concrete test:

> Starting from repository state plus the authorized source-access mechanism — without the old chat — can another capable work context open the exact evidence needed for the current `NEXT ACTION` and verify its identity?

For visual source work this means the actual image/PDF page becomes inspectable, not merely that a recipe exists.

Possible result classes:

- **PASS — repository/local controlled evidence available**;
- **PASS — external/institutional evidence retrievable and exact identity verified**;
- **PASS — verified parent available and required derivative reproducibly generated in the fresh context**;
- **BLOCKED — evidence identity known but actual evidence inaccessible**;
- **BLOCKED — rights/access state prevents authorized persistence/retrieval**;
- **UNRESOLVED — identity/correspondence/access not yet established**.

Do not encode these exact labels as schema unless repeated usage demonstrates value.

## Project creation / source-intake decision

Test the earlier project-intake question as part of this workflow:

When a new source/file is supplied, the work context should determine from canonical rules whether it belongs to:

- an existing Project/Source relationship;
- a new Source under an existing Project;
- a new Project because the research object/scope is genuinely distinct;
- unresolved intake pending human purpose decision.

Do not create a new Project merely because a file was uploaded. Human owner input is required only where research purpose/scope cannot be derived from existing project state.

## Canonical ownership hypothesis

Do not introduce a new media registry by default.

First test whether the requirement can be carried by existing owners:

- `corpus/files.tsv` — exact digital File identity, preservation/storage/rights status;
- Source crosswalk — archival/image/PDF/institutional locator correspondence;
- project `STATUS.md` — active evidence-access state and NEXT ACTION;
- project/source inspection log — actual use/inspection event;
- methodology/source/provenance + historical-source workflow — generic intake/access rules;
- `AGENTS.md` / #77 fragments — work-context requirement to verify actual evidence availability before execution.

Only propose additional structure if these owners cannot express a recurring, material distinction without ambiguity or duplication.

## Relationship to #68

#68 is the immediate P0 Reg. Ii 5 fixture and must repair actual access for #64.

This Issue generalizes only what the fixture demonstrates. It must not block the immediate restoration of image access.

## Relationship to #71 / #77

A composed `TASK START / RESUME` or source-work handoff should distinguish:

```text
EVIDENCE IDENTIFIED
EVIDENCE ACCESSIBLE NOW
ACCESS / RETRIEVAL PATH
RIGHTS / AUTHORITY LIMIT
FRESH-CONTEXT ACCESS VERIFIED?
```

These are candidate information requirements, not necessarily permanent template fields. Test the smallest wording that prevents `known evidence` from being mistaken for `available evidence`.

## Deterministic / judgement boundary

Potentially deterministic/structural checks include:

- SHA-256 equality for exact File identity;
- crosswalk lookup for an already-evidenced File;
- presence/resolution of a recorded access path;
- whether a required binary/URL is actually reachable in the authorized work context;
- whether a render command produced the expected page/dimensions when those parameters are settled.

Not deterministic:

- whether rights terms permit a particular storage interpretation when legal/institutional terms require judgement;
- whether the source evidence is palaeographically sufficient;
- whether a visible mark/URN has been correctly read when uncertain;
- whether a new Project is scientifically warranted when research purpose is genuinely undecided.

## Acceptance criteria

- [ ] identifiability, reproducibility and research-ready availability are explicitly distinct;
- [ ] active visual source work requires actual authorized image access, not identifier-only availability;
- [ ] public redistribution and controlled/private research storage are not conflated;
- [ ] visible/evidenced institutional URNs are captured rather than inferred or ignored;
- [ ] fresh-context restartability is tested from repository + authorized access path without old-chat dependence;
- [ ] source/file upload does not automatically create a new Project;
- [ ] owner input is requested only for genuine purpose/rights/access decisions;
- [ ] existing canonical owners are preferred over a new media/asset subsystem;
- [ ] #68/Reg. Ii 5 supplies the first real falsification fixture;
- [ ] no generic storage technology is selected before the rights/access/use cases demonstrate need.

## Non-goals

- no immediate GitHub privacy change;
- no assumption that private GitHub storage is legally sufficient;
- no generic DAM/asset manager;
- no S3/object-store architecture;
- no IIIF server requirement;
- no media database;
- no bulk binary migration;
- no automatic Project creation from upload;
- no claim that URN/reference availability replaces human-visible images;
- no blocking of #64 while the immediate evidence-access gap is repaired.
