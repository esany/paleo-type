## Text

## Research benefit
Automate repetitive corpus discovery/metadata ingest only when manual entry becomes a real bottleneck.

## Why not now
The present corpus size and workflow do not justify ingest infrastructure.

## Trigger
Roughly 20+ source records **or** repeated evidence that manual archival-metadata transfer is a material bottleneck.

## Definition of Done
- ingest/export metadata into canonical corpus records without overwriting curated fields;
- preserve original record URLs/IDs and imported-metadata provenance;
- detect duplicates/candidate relationships without auto-asserting textual identity;
- generate reviewable diffs, not opaque writes;
- respect portal permissions/stability.

## Trigger review
Re-check when corpus growth or repeated metadata-entry work reaches the trigger. Otherwise leave deferred.

## Kommentar 5464523720 · 2026-08-29T19:53:17Z · esany

## Boundary with #69/#70 — do not let future metadata ingest bypass research intake

#4 remains the owner for **future repetitive corpus discovery/metadata ingest** if its trigger fires.

A separate generic intake requirement has now been captured in #69: supplied File → exact File identity/provenance → Source identity/structure → explicit Project routing → bounded Project research state → validation/restartability.

#70 is the deferred post-pilot review of whether that intake needs a small guided/preflight component.

If #4 is triggered later, metadata import should feed/reuse the #69 intake semantics rather than become a parallel Source/Project creation path. In particular automated discovery/import must not:

- infer exact File identity from filename/metadata;
- auto-assert Source identity/granularity beyond evidence;
- auto-create a Project;
- auto-assign imported Sources to the current Project;
- bypass explicit Project research-function decisions;
- create a second validation/ownership model.

Possible later integration is intentionally evaluated under #70; no change to #4's current trigger or implementation status is made now.
