## Current observation

`paleo-type` has deliberately accumulated normative scholarly and AI-governance prose because the relevant domain requirements first had to be discovered and separated correctly. That was necessary, but it creates a new failure mode if stable deterministic requirements remain primarily encoded as chains of Markdown instructions that every AI session must re-read, reconcile and re-interpret.

The repository already demonstrates the preferred direction in the source/provenance layer:

- `corpus/source-contract.json` expresses stable recurring structural constraints in machine-readable form;
- `tools/source_contract.py` validates source/file/project/crosswalk referential integrity, controlled values, project roots, `part_of` structure, checksums and related invariants;
- the resolver derives `project_root` / `internal` / `external` scope deterministically from canonical source structure rather than asking AI to infer it afresh;
- `.github/workflows/source-contract.yml` runs validation/regression checks automatically for relevant changes.

However, the same degree of explicit control is not yet established for several already-demonstrated requirements, especially the future canonical G2 witness/locus/phenomenon/evidence representation, deterministic human-readable witness generation, and the boundary between a new scholarly judgement and an authorized mutation of existing canonical research state.

## Risk

If a stable deterministic rule is represented mainly by duplicated or chained prose, correctness depends on model/session behaviour:

1. the AI must load every applicable document;
2. it must resolve overlaps and precedence correctly;
3. it must reconstruct the same invariant each time;
4. it must remember to apply it at every write/transform;
5. another model/session must make materially the same interpretation later.

That is not sufficient protection for invariants whose violation can be detected or prevented mechanically.

A second, distinct risk exists even where scholarly judgement is genuinely non-deterministic: a later AI/researcher may legitimately evaluate the same evidence differently, but that difference must not by itself overwrite the prior canonical research state and erase the earlier decision path.

## Governing distinction — three levels

The target is **not** to encode scholarly judgement as software. The analysis must distinguish three levels.

### 1. Deterministic structure / invariants

These are stable machine-checkable or deterministically derivable properties where justified, for example:

- identifier uniqueness and referential integrity;
- valid Source/File/Project ancestry and ownership;
- canonical locus/address validity;
- required provenance links;
- stable controlled status/structure values where semantics are actually settled;
- deterministic renderer/generator behaviour;
- migration completeness and semantic-loss regression fixtures;
- canonical-vs-derived boundaries;
- rebuildability of generated outputs;
- non-loss of prior decision/revision references.

These should be executable only where the underlying semantics are stable enough to justify it.

### 2. Non-deterministic scholarly judgement

Examples include:

- whether a grapheme is actually `r`;
- which abbreviation expansion is justified;
- whether two passages are written by the same hand;
- whether collation demonstrates textual dependence;
- whether a historical identification is warranted;
- philological or historical interpretation;
- legitimate differences in qualified researchers' evaluation of the same evidence.

These questions require disciplinary method, evidence and sometimes qualified specialist review. Code must not manufacture scientific truth or force convergence.

### 3. Deterministically governed canonical-state transitions

This level does **not** make the scholarly judgement deterministic. It governs when and how a judgement may replace an already canonical research state.

The analysis must derive the smallest adequate controls ensuring that:

- a new AI/researcher run cannot overwrite existing canonical research state merely because it produces a different judgement;
- differences may enter as candidates, challenges or alternatives without canonical mutation;
- a canonical mutation requires an explicit admissible transition process;
- minimum transition provenance is inspectable;
- predecessor state, transition reason and evidence/review basis remain reconstructable where material.

> Scholarly judgement may legitimately vary; canonical research state must not vary merely because a model or researcher produces a different judgement. Differences enter as candidates, challenges or alternatives. Canonical mutation requires an explicit, evidence-aware and reconstructable state-transition event.

> **A different AI/researcher judgement is not itself a canonical-state transition event.**

## Central canonical-state invariant

Use the following as an analysis invariant:

```text
canonical state S
+ canonical evidence state E
+ applicable method/version M
+ no admissible transition event
        ↓
re-processing may produce candidates/challenges/alternatives
        ↓
canonical state remains S
```

This does **not** mean:

`same evidence → same scholarly judgement`.

An alternative scholarly evaluation may legitimately arise. The invariant says only that a different evaluation does not possess mutation authority by itself.

## Admissible transitions may include re-adjudication

Do **not** derive the false rule `canonical change requires new evidence`.

Depending on the real scholarly case, an admissible transition may be prompted by, for example:

- new evidence;
- explicit re-evaluation of existing evidence;
- qualified specialist review;
- recognized prior error / correction;
- a materially relevant method/version change;
- another scholarly justified re-adjudication.

This is not a closed transition ontology. The analysis must determine from real recurring research-state changes which transition distinctions are actually structurally necessary and which should remain prose/judgement.

## Information requirements for reconstructable transitions

For a consequential canonical state change, derive which of the following information is actually required by the real object/use case to reconstruct the transition:

- transition identity;
- target claim / reading / locus / canonical object;
- previous canonical state;
- resulting canonical state;
- transition kind / basis;
- reason;
- evidence added and/or re-evaluated;
- applicable method/version where material;
- responsibility / actor role;
- review / validation status where material;
- previous-state / superseded-decision reference where applicable.

This is an **information-requirement list**, not a storage design. It does **not** pre-authorize or pre-select:

- a new table;
- concrete field names;
- a transition ontology;
- event sourcing;
- a database;
- a universal claim engine.

#64 and the existing real research structures, including `apparatus/decisions.tsv`, must determine what the smallest lossless representation actually needs to be for G2.

## Derivation from already canonical REQ-* requirements

Canonical-state transition control is not a new mission or free-standing architecture idea. It is an incompletely operationalized intersection of existing requirements:

- **REQ-GWP-004** — consequential revisions/rejections retain enough history to reconstruct research-state change;
- **REQ-GWP-005** — consequential AI-assisted work and independent human/specialist review expose responsibility and validation level;
- **REQ-PAL-007** — alternatives, rejected readings, residual uncertainty and supersession/decision references remain traceable;
- **REQ-AI-005** — AI preserves alternatives/unresolved outcomes rather than optimizing them away;
- **REQ-AI-006** — consequential AI effects carry proportional provenance;
- **REQ-AI-007** — write boundaries distinguish analysis from canonical research-state writes and more consequential change classes;
- **REQ-RSE-008** — transformations preserve provenance/decision history and remain auditable;
- **REQ-RSE-010** — automation writing canonical research state is reviewable and narrower than scholarly judgement.

Relevant supporting requirements include REQ-GWP-001 (one canonical owner), REQ-GWP-008 (restartability without chat), REQ-RSE-003 (canonical state separate from derived views), and REQ-AI-003 (AI output/evidence/validation statuses remain distinct).

The combined requirement is:

```text
revision history
+ alternatives / supersession
+ responsibility / review
+ AI write authority
+ canonical-state effects
+ provenance-preserving transformation
        ↓
deterministically governed canonical-state transitions
```

## Derivation rule to test

For every material requirement in `requirements/domain-requirements.tsv`, #25 should be able to answer:

`requirement → governing level (deterministic structure | scholarly judgement | canonical-state transition control) → canonical information needed → enforcement owner → executable invariant/derivation if feasible → human/specialist judgement if not → test/fixture`

Possible primary enforcement owners remain:

`method prose | canonical data contract | validator | resolver/derivation | deterministic generator | migration/regression test | AI workflow | specialist judgement | no action`

A requirement should not be repeated across several owners without a concrete reason.

## Anti-false-determinism boundary

This issue does **not** require:

- `same evidence → same palaeographic reading`;
- `same evidence → same historical interpretation`;
- AI and expert agreement;
- software deciding the correct grapheme.

It requires:

- `different judgement alone ≠ canonical mutation authority`;
- `canonical mutation → explicit admissible transition → reconstructable prior state + basis/provenance`.

## Non-goals

- no database/framework/application by default;
- no attempt to encode palaeographic, philological or historical judgement as deterministic truth;
- no assumption that the same evidence must yield the same scholarly judgement;
- no transition table/schema/event model pre-authorized by this issue;
- no closed transition ontology;
- no broad schema formalization before semantics are stable;
- no automatic canonical writes that bypass evidence-aware review;
- no refactor for aesthetic cleanliness;
- no bulk G2 migration before #64 acceptance;
- no implementation merely because a candidate invariant has been identified.

## Architectural principle under review

**Markdown should explain scholarly method and govern genuine judgement. Stable deterministic semantics should, where justified, be represented once and enforced or derived by code. Scholarly disagreement may produce candidates or challenges, but mutation of canonical research state must be a separate explicit, evidence-aware and reconstructable transition rather than an incidental effect of who or what re-runs the analysis.**

### 2. Candidate ≠ canonical mutation — current support

The repository already has useful, non-universal distinctions and should preserve them rather than replace them with a new ontology:

- transcription rows: `observed | working | variant | unresolved` plus `alternatives` and `evidence_note`;
- `apparatus/decisions.tsv`: real transitions with `previous → current`, statuses `rejected | variant | observed`, reason/evidence and residual uncertainty;
- `lexicon.tsv`: `working | variant` and explicit alternatives/limitations;
- `numerals.tsv`: `working | observed | unresolved`, including the external C2 comparison observation with a strong no-same-hand/no-direct-proof limitation;
- `source-audit.tsv`: evidence status plus separate `usable_claim` / `blocked_claim`.

Real examples already show correct transition semantics without forcing certainty: D008/D009 withdraw fluent reconstructions to unresolved state; D010 keeps a repeated surname token variant rather than promoting one spelling; D011 promotes only the directly reinspected numeral form `80` while leaving its meaning/syntax unresolved.

What is **not** yet consistently protected is the boundary between these candidate/working states and a direct edit of the canonical current reading/observation. The current method expects consequential changes to be logged, but code does not currently detect a changed transcription/palaeography/source-audit state that bypasses the existing Decision/revision path.

### 3. `apparatus/decisions.tsv` as the real transition case

Current strengths:

- stable Decision IDs D001–D011;
- explicit previous/current values;
- explicit reason and evidence class;
- rejection/variant/observation transitions are visible;

### 8. Prose vs executable-control recommendation

Do not remove prose now. Existing project-lifecycle/maintenance/Decision prose often explains *why* executable source-contract invariants exist and is not harmful duplication by itself. Future consolidation should target only repeated normative statements that force sessions to reconstruct the same stable rule.

Genuine scholarly prose that must remain judgement-based includes evidence-before-plausibility, reading/expansion/hand/dependence adjudication, specialist escalation and consequence-based validation.

Potential deterministic controls should be added only after a demonstrated repeatable failure. The clearest future candidate is a **bounded transition-completeness regression** for consequential canonical reading changes, but its target/address/phenomenon semantics must not be designed before #64.

### 9. Owner-admission boundary

D-016 material repository/architecture implementation admission is distinct from scholarly canonical-state transition control. A normal evidence-aware reading revision inside an admitted research method does **not** require a new architecture Owner admission. Depending on consequence it may require an explicit Decision, evidence/re-adjudication rationale, AI provenance and/or specialist review.
