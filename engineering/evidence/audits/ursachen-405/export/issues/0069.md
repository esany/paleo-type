## User/research objective

A researcher should be able to use `paleo-type` for a newly supplied source file without understanding the repository's internal software architecture. The system should ask the human only for research-purpose, source-identity/granularity, rights/authority or project-choice facts that cannot be safely derived. Stable structural consequences should be derived/validated deterministically where justified.

The goal is **not** a generic media platform. It is a small, reliable research-intake path that routes a supplied digital source into the already-defined METHOD/CORPUS/PROJECT owners without requiring the user to remember them.

## Demonstrated gap

The current repository already has the necessary semantic components, but their execution order is distributed across several owners:

- `methodology/historical-source-workflow.md` — authoritative end-to-end scholarly method;
- `methodology/source-and-provenance.md` — Source/File identity, exact instantiation, checksum, rights/preservation and reusable crosswalk ownership;
- `methodology/project-lifecycle.md` — what a Project is, `project_source_id`, Project→Source research use and new-project creation;
- `methodology/maintenance.md` — canonical ownership, restartability and material-change admission;
- `templates/project/` — minimal target-model Project bootstrap;
- `corpus/source-contract.json` + `tools/source_contract.py` — existing deterministic structural checks;
- `corpus/sources.tsv`, `relationships.tsv`, `files.tsv`, `source-data/` — canonical corpus owners;
- `projects/<id>/project.yml`, `source-uses.tsv`, `research/use-evidence.tsv`, `STATUS.md` — project owners.

A new researcher/AI can reconstruct these rules, but currently still has to synthesize the **intake sequence** from several files. That leaves avoidable room for recurring failures such as:

- filename/content similarity treated as File identity;
- an uploaded PDF treated automatically as a new Source;
- a new Source treated automatically as a new Project;
- a file silently attached to the currently active Project because of chat context;
- a source-wide crosswalk applied before exact File identity/correspondence is established;
- project-relative research function confused with Source identity or structural membership;
- rights/preservation questions confused with provenance identity;
- duplicate canonical truth created because the correct owner/path was not selected;
- a user being forced to know which TSV/YAML/Markdown file must be edited.

The recent Reg. Ii 4 / Reg. Ii 5 upload case is a positive empirical fixture: SHA-first identity prevented a comparison export from being used as the principal Reg. Ii 5 File, and the later exact Reg. Ii 5 match allowed the canonical page crosswalk and #68/#64 workflow to proceed. This pattern is general enough to codify as intake method without generalizing the project-specific hashes/crosswalks themselves.

## Already canonical invariants to preserve

These are not new decisions:

- File identity is byte-level when an exact file is consequential; filenames are not sufficient identity.
- `corpus/files.tsv` is the sole canonical owner of File identity/checksum/coverage/storage/rights.
- `corpus/sources.tsv` owns canonical historical/documentary Source identity.
- `corpus/relationships.tsv` owns evidenced `part_of` and other Source→Source claims.
- reusable source-wide crosswalks live once in `corpus/source-data/<source_id>/`.
- every Project has exactly one `project_source_id` rooted in a historically independent Source structure.
- a PDF, fragment, place, current question or temporary comparison task does **not** automatically create a Project.
- Project structural status (`root`/`internal`/`external`) is derived from `project_source_id + part_of*` rather than copied.
- `research_function` is Project-relative and open-vocabulary; it is not inferred from Source type or structural status.
- concrete Project-use→File evidence is separate from Project→Source research function where the target model is used.
- target-model projects are bootstrapped from `templates/project/`; do not create speculative empty research directories.
- current Reg. Ii 5 remains on its explicit legacy compatibility representation until separately admitted migration.
- rights/redistribution authority is not inferred from provenance, a checksum, a URL/URN, or possession of a file.

## Required intake decision procedure

The canonical workflow should state one unambiguous sequence, while leaving detailed semantics with their existing owners:

```text
new supplied local/working file
→ compute exact identity/checksum where consequential
→ match/reuse known File or establish that this is a distinct/unresolved File instance
→ establish/verify which historical Source the File instantiates
→ establish only evidenced Source structure/relationships
→ record/reuse File→Source provenance and rights/preservation state
→ establish/reuse source-wide correspondence/crosswalk only when actually evidenced
→ explicit Project routing decision
     ├─ use in existing Project
     ├─ candidate new Project
     └─ no Project yet / Corpus-only state
→ create only the project-relative research state actually required
→ run deterministic contract/integrity checks
→ update project STATUS/NEXT ACTION when Project state materially changes
→ restartability check
```

### Mandatory Project-routing question

Before any Project-specific mutation, the system must explicitly establish one of:

1. **Existing Project** — the Source/File will be used by an identified existing Project; record only the actual Project→Source use/evidence needed.
2. **Candidate new Project** — ask/confirm whether a new Project should be created; do **not** create it automatically merely because a new Source/File exists.
3. **No Project yet** — retain the canonical Corpus Source/File state without forcing project creation.

A `candidate new Project` becomes a Project only after the historically independent root is adequately identified and the human/research purpose and active scope are confirmed. Then use the existing `templates/project/` contract.

## Deterministic vs scholarly/human boundary

### Deterministic / machine-checkable when inputs are established

Candidate invariants for current or later executable enforcement:

- SHA-256 exact match to a canonical File → reuse that File identity; no duplicate File row for the same known exact bytes.
- no SHA match → do not apply a known File-specific crosswalk automatically.
- referenced Source/File/Project/use IDs resolve.
- `project_source_id` resolves to a canonical Source.
- `root/internal/external` is derived from `project_source_id + part_of*`.
- a use-evidence File belongs to the same canonical Source as its Project use.
- File checksum format, controlled storage state, repository-preserved-path existence/hash and current Source-contract rules validate.
- project ID matches directory ID and required project keys exist.
- source-wide crosswalk rows belong to their canonical Source and satisfy current contract constraints.
- no duplicate canonical owner is introduced when an existing Source/File/crosswalk already owns the fact.

These rules should reuse/extend the existing `source-contract` validator only if a real missing invariant is demonstrated; do not create a parallel intake schema.

### Human / archival / research judgement

The workflow must stop or ask rather than infer when deciding:

- whether a non-matching file is another export/derivative/compilation/version of a known Source;
- the historically correct Source identity/granularity when evidence is insufficient or ambiguous;
- whether a Source relation (`part_of`, extract/copy/parallel/etc.) is actually warranted;
- whether the Source should be used in a particular Project;
- which `research_function` and relevant scholarly locus it serves;
- whether a historically independent Source structure warrants a new Project;
- the new Project's research object and active scope;
- rights/redistribution/contractual authority facts that cannot be independently verified;
- specialist textual/palaeographic/historical judgements.

The user should not have to know repository paths or schemas in order to answer these questions.

## Required owner/mutation matrix

The resulting method should make this routing explicit:

| Established fact/action | Canonical owner |
|---|---|
| historical Source identity | `corpus/sources.tsv` |
| evidenced Source→Source relation | `corpus/relationships.tsv` |
| exact digital File identity/checksum/coverage/storage/rights | `corpus/files.tsv` |
| reusable source-wide folio/image/PDF correspondence | `corpus/source-data/<source_id>/` |
| Project root/purpose/scope | `projects/<id>/project.yml` |
| Project→Source research function/locus | `projects/<id>/source-uses.tsv` (or explicit legacy compatibility owner where applicable) |
| Project-use→File evidence | `projects/<id>/research/use-evidence.tsv` when actually needed |
| project-specific inspection state | existing project inspection/research owner when needed |
| active gate/gaps/NEXT ACTION | `projects/<id>/STATUS.md` |
| generic intake rule | `methodology/historical-source-workflow.md`, referencing detailed owners rather than duplicating them |

## Minimum user interaction target

After the pilot, a routine intake should require only questions that the repository cannot safely derive. A normal operator should not have to decide:

- which TSV/YAML/Markdown files to edit;
- whether a Source is structurally internal/external once the graph/root is known;
- whether an existing canonical File/Source ID resolves;
- which validation command protects referential integrity;
- where File provenance vs Project research-use data belongs.

The operator may still need to answer:

- what source/export was actually supplied when identity is unresolved;
- what rights/authority facts apply if not verifiable;
- whether the material should enter an existing Project, become a candidate new Project, or remain Corpus-only;
- the research purpose/scope of a genuinely new Project;
- genuine archival/scholarly judgements not derivable from stable structure.

## System-audit refinement — SHA determinism without premature global File-row uniqueness

Current `corpus/source-contract.json` / `tools/source_contract.py` validates unique `file_id`, SHA-256 syntax, Source references, controlled storage state, and for `repo-preserved` files the actual path/hash. It does **not** currently enforce global SHA uniqueness across `corpus/files.tsv`.

The intake workflow should therefore distinguish the stable fact from a stronger policy not yet demonstrated:

### Stable deterministic fact

`same verified SHA-256 → same exact byte sequence`.

For a newly supplied file:

- one compatible canonical File row with that SHA → the intake may reuse that known canonical File identity;
- no canonical File row with that SHA → do not treat the file as an existing canonical File and do not transfer its File-specific crosswalk automatically;
- multiple/conflicting canonical rows with the same SHA, especially across incompatible Source/provenance claims → **stop and resolve the registry/provenance conflict**, rather than choosing one by filename/project context.

### Not yet established as a universal invariant

Do **not** add a global `sha256 must be unique across all File rows` validator merely from this Issue. A future real case may need to distinguish byte identity from acquisition/provider/provenance-event semantics. If duplicate SHA rows actually occur, determine whether they are erroneous duplicate File identity or intentionally distinct provenance records before formalizing a constraint.

This keeps determinism exactly where the evidence supports it: byte identity is deterministic; the canonical modelling consequence remains subject to the established File semantics and any demonstrated multi-provenance case.
