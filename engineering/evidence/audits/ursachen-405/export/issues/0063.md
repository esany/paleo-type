## Status
**Conditional planning issue only. No new Project directories or project-state materialization is authorized now.**

## Current canonical source structure
The current Corpus already establishes three distinct historical parent roots through canonical Source nodes and `part_of`:
- `ACT-THHSTAW-EGA-REG-II-5`;
- `ACT-THHSTAW-EGA-REG-II-4-BD-II`;
- `ACT-THHSTAW-EGA-REG-II-3`.

Reg. Ii 3 contains two distinct protocol Sources:
- `THHSTAW-EGA-REG-II-3-PROT-NEUSTADT-41R-63V`;
- `THHSTAW-EGA-REG-II-3-STAT-VIS-00000235`.

They remain distinct Source/handwriting/text objects under the same Reg. Ii 3 root. They are not separate Projects merely because they require independent Source-specific scholarly treatment.

## Planning principle
D-014 establishes that a Project is anchored to one historically independent Source root by `project_source_id`.

It does **not** require every known historical root to receive a Project directory immediately for symmetry.

Create/materialize an additional Project only when that root needs a durable, independently maintained PROJECT-layer state: for example its own active scope, STATUS/restart point, research-use records, source-specific work, decisions or other fortschreibbare Erschließungsarbeit.

A Source may exist canonically in CORPUS without a Project until such project state is actually needed.

## Current candidate roots
When independently maintained Project state is genuinely needed, the natural candidates are:
- Reg. Ii 4 Bd. II → `ACT-THHSTAW-EGA-REG-II-4-BD-II`;
- Reg. Ii 3 → `ACT-THHSTAW-EGA-REG-II-3`.

Reg. Ii 5 already has a Project anchored to `ACT-THHSTAW-EGA-REG-II-5`; its current directory slug containing `knau` does not change that canonical boundary anchor.

## Creation constraints
Any later admitted materialization must:
- use one historical root as `project_source_id`;
- derive internal/external Source status through `part_of` rather than copy it;
- keep the two Reg. Ii 3 protocol Sources distinct while deriving both as internal to a Reg. Ii 3 Project;
- not create Project wrappers for individual protocols merely to own metadata/crosswalks;
- not create empty `source-work`/research/palaeography/transcription trees for symmetry;
- not require a `principal` function at Project creation;
- not infer Project→Project relations from another Project using one of its Sources;
- remain restartable from actual maintained Project state, not boilerplate.

## Trigger per root
Materialize a root Project only when at least one concrete continuing Project-layer need exists, such as:
- independent source-specific transcription/palaeographic/editorial work that needs durable Project ownership;
- a distinct active scholarly scope and NEXT ACTION;
- recurring Project→Source research uses/decisions that should be maintained independently;
- another demonstrated restartability/ownership need that cannot remain truthful in CORPUS alone.

Do not materialize solely because the root exists.

## Reg. Ii 5 slug
Renaming `projects/ega-reg-ii-5-knau/` is **not part of this Issue**.

`project_source_id` already carries the canonical Project identity; Knau is an active scope. A later path rename is ordinary navigation/maintenance only if the existing slug causes a demonstrated human/restartability problem. It must not be coupled to Reg. Ii 3/4 materialization merely for symmetry.

## Duplicate-root rule
This Issue does **not** establish a validator hard-fail that forbids two Projects from ever naming the same exact root. No current real duplicate-root case exists and D-014 does not yet define that inverse uniqueness rule.

If such a conflict occurs later, resolve it from the actual scholarly/project-lifecycle need rather than hard-coding a prohibition in advance.

## Dependencies / sequence
- #58 governs later implementation admission.
- #59 supplies the planned Project→Source use semantics before a newly materialized Project should adopt that model.
- #60 is specific to the Reg. Ii 5 migration fixture and no longer blocks Reg. Ii 3/4 Project planning.

## Acceptance criteria for any later admitted materialization
- [ ] a real durable Project-layer need/trigger is documented for the root;
- [ ] `project_source_id` resolves to the intended historical Source root;
- [ ] existing internal Sources derive correctly from `part_of`;
- [ ] Reg. Ii 3 protocol Sources remain separate;
- [ ] no protocol Project wrappers are created;
- [ ] no empty future-proof work trees are created;
- [ ] no automatic Project→Project relation is introduced;
- [ ] Project state is human-readable and restartable;
- [ ] no duplicate-root hard-fail is introduced under this Issue;
- [ ] implementation has separate explicit owner admission.

## Non-goals
- no current Project creation;
- no Reg. Ii 5 slug rename;
- no full transcription simply to justify a Project;
- no Research-Question project layer;
- no empty Source-work hierarchy;
- no implementation in the current planning phase.
