## Status / authority

**P1 analysis / role-refinement planning only. No new role, implementation, validator, workflow engine, assurance gate or repository-wide rename is authorized by this Issue.**

This Issue records a cross-repository analysis finding: the current `Development / Implementation` function in #74 is semantically broader than ordinary “Fullstack Developer” work. Correct implementation in `paleo-type` requires research-software, requirements, provenance, verification, AI-context/tool-routing and Human-in-the-loop competencies in addition to conventional software engineering.

The current hypothesis is therefore:

> Treat #74 as a **Research Software & AI Systems Engineering / Implementation function** with an explicit competency profile, **without creating another authority layer**.

The role name may remain `Development / Implementation` if that is clearer operationally. The important change is the competency and assurance contract, not job-title aesthetics.

## Why this is a demonstrated gap

The repository already requires Dev to preserve scholarly meaning, canonical ownership, provenance, uncertainty, migration/loss semantics and deterministic/epistemic boundaries. It also requires Dev to stop when implementation exposes a new scholarly-semantic or architectural choice outside the admitted handoff.

Those obligations cannot be fulfilled reliably by generic coding competence alone. A technically valid implementation can still fail the research system by:

- silently reinterpreting a scholarly requirement;
- converting epistemic uncertainty into a deterministic state;
- moving a fact to a technically convenient but wrong canonical owner;
- passing CI while losing provenance, decision history or source meaning;
- making a derived view a second truth store;
- creating model/prompt dependency instead of deterministic control;
- shifting software-structural questions back to the human owner;
- leaking rights-restricted source material through tooling or test fixtures;
- treating a new AI/model judgement as authority to mutate canonical research state.

This is a competency/assurance problem inside the existing role topology, not evidence for a sixth operational role.

## Required competency profile to test

A #74 work context should be able to apply, proportionally to the admitted task:

### 1. Research Software Engineering

- scholarly requirements and evidence remain prior to implementation convenience;
- smallest adequate mechanism is preferred;
- code/data structures are treated as replaceable support infrastructure;
- local inspectability, Git diffability, portability and maintainability remain design criteria where useful.

### 2. Requirements Engineering

- distinguish demonstrated problem, information requirement, acceptance criterion and implementation choice;
- consume a Domain Review handoff without re-deriving the underlying scholarship;
- identify missing/ambiguous semantics and return them rather than filling them with technical assumptions;
- preserve explicit non-goals and scope boundaries.

### 3. Information / data modelling and canonical ownership

- distinguish METHOD / CORPUS / PROJECT / derived state;
- preserve one-fact-one-owner semantics;
- understand Source/File/Project/use/evidence/locus distinctions sufficiently to avoid architectural semantic loss;
- keep deterministic derivation separate from copied truth.

### 4. Provenance and research-data stewardship

- preserve exact evidence identity and transformation provenance where material;
- understand canonical vs derived artifacts;
- preserve decision/revision history and restartability;
- maintain rights/access/preservation boundaries without inventing authority.

### 5. Verification, validation and semantic-loss engineering

- translate settled deterministic requirements into tests/invariants where justified;
- use representative migration/loss fixtures rather than only happy-path unit tests;
- distinguish technical verification from scholarly adequacy review;
- test rebuildability, referential integrity, transition/history preservation and no-parallel-truth properties where applicable.

### 6. AI systems / context and tool engineering

- prefer deterministic tools for deterministic questions rather than model self-certification;
- load/compose role/task context from canonical repository state rather than rely on remembered master prompts;
- preserve stage-specific context/blind-reading boundaries when AI tooling participates in research workflows;
- make model/tool/version assumptions visible only when materially relevant.

### 7. Human-in-the-loop / authority engineering

- distinguish routine autonomous implementation from owner-reserved admission/purpose/use decisions;
- do not ask the owner to choose repository paths, schemas or deterministic mechanics that are derivable;
- stop material scope expansion under D-016;
- keep independent specialist validation distinct from AI/Dev self-review.

### 8. Human auditability / information architecture

- technical outputs carrying scholarly meaning must be reviewable in research-facing language;
- derived human views should be rebuildable from canonical state;
- a reviewer should be able to understand `problem → requirement/evidence → owner → implementation → deterministic checks → remaining judgement/open points` without reverse-engineering code.

### 9. Reproducibility / preservation-aware engineering

- exact input identity and materially relevant tool/version/parameter information are preserved where needed;
- reproducibility is defined at the scientifically relevant level, not falsely as universal byte identity;
- controlled/restricted source bytes remain inside permitted boundaries.

### 10. Scholarly-interface literacy

Dev does **not** become the palaeographic/editorial/archival adjudicator. It does need enough interface literacy to recognize when a distinction is scholarly semantics rather than an implementation detail and therefore must be preserved or returned to Domain Review.

## Engineering authority boundary

The competency expansion does not expand #74 authority.

Correct pattern:

```text
validated/admitted scholarly requirement
→ Dev/RSE/AI-systems implementation
→ deterministic verification where legitimate
→ explicit open semantic choices returned
→ Domain Review scholarly adequacy review
→ research NEXT ACTION
```

Not:

```text

→ Dev may now decide the manuscript / generic method / owner purpose / publication / specialist truth
```

## Conceptual control stack

Prefer layered controls rather than one large AI prompt:

```text
canonical mission / method / requirements
        ↓
role + task context derived from repository state
        ↓
bounded handoff with evidence + non-goals + return condition
        ↓
deterministic tool/validator/generator for settled semantics
        ↓
Dev implementation
        ↓
regression / semantic-loss / provenance checks
        ↓
Domain Review scholarly adequacy review
        ↓
canonical persistence / NEXT ACTION
```

This keeps model capability useful but prevents the model from being the only place where process knowledge lives.

## Technical assurance boundary — do not create another role yet

A separate independent technical-assurance role is **not currently justified**.

First use:

- ordinary code review / tests where available;
- deterministic regression and migration/loss fixtures;
- #73 scholarly adequacy review for implementations carrying research semantics;
- explicit owner admission only where D-016 requires it.

Revisit a distinct technical-assurance function only if a real trigger appears, such as:

- repeated high-consequence failures survive Dev's own tests;
- a material migration cannot be credibly reviewed by the implementing context alone;
- security/rights/preservation controls require independent technical attestation;
- systematic AI infrastructure becomes sufficiently consequential that implementation and evaluation independence materially improves reliability;
- external release/institutional transfer requires independent software/data assurance.

If triggered, define the smallest review function then; do not pre-create an assurance bureaucracy now.

## Dev/RSE consequence of the no-chat-knowledge-monopoly principle

The new #71/#72/#73/#77 clarification has one concrete implication for #74 / Research Software & AI Systems Engineering that should remain durable without creating another role or workflow owner.

A Dev work context must treat an upstream chat/handoff as **navigation and bounded task input, not as canonical truth or a knowledge dependency**.

Use the following operational sequence when a real #73→#74 handoff arrives:

```text
REHYDRATE
→ read current main + canonical task/owner + relevant project STATUS/NEXT ACTION + persisted evidence/requirements

VERIFY
→ confirm that material upstream findings/uncertainty are actually persisted/referenced; resolve deterministic Source/File/Project/owner facts from canonical state rather than trusting repeated prose

BOUND
→ identify current Dev authority, admitted scope/non-goals, scholarly decisions already established, unresolved questions Dev must not decide

EXECUTE
→ implement only the bounded technical target; prefer deterministic derivation/validation over model judgement where semantics are already fixed

PERSIST
→ make implementation, tests/loss evidence, consequential limitations and newly exposed unresolved choices reconstructable outside the Dev chat

RETURN
→ hand the scholarly adequacy question back to #73 / canonical research owner; CI/validator PASS is technical evidence, not scholarly acceptance
```

### Additional Dev invariants

- Do not ask the human to shuttle findings already persisted by #72/#73.
- Do not turn `Source Research observed loss` directly into a schema/Dev requirement; #73 owns that classification boundary.

- Preserve `unresolved`, `not investigated`, alternatives and explicit non-goals across implementation; a cleaner technical representation must not epistemically smooth the scholarly input.
- If implementation exposes a new scholarly-semantic choice, stop and return the choice + alternatives + consequences to #73 rather than deciding it from technical convenience.
- The Dev chat itself is replaceable: consequential implementation state must be recoverable from Git/repository/Issue state without replaying the conversation.
