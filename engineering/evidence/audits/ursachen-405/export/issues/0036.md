## Governing requirement
Software/data architecture must remain subordinate to scholarly source work: it should reduce error, preserve semantics, improve auditability and remove repeated burden without forcing the research into an unnecessary platform.

## Review criteria
Verify at a future refactor:
- whether current Markdown/TSV/YAML still fit data volume, relations and collaboration needs;
- whether canonical ownership and METHOD/CORPUS/PROJECT boundaries remain enforceable and understandable;
- whether repeated machine-checkable errors justify executable validation;
- referential integrity of source/file/entity/relationship/project identifiers;
- controlled vocabularies/status values and schema evolution;
- deterministic generation of human-readable views and exports from canonical data;
- migration/versioning strategy for canonical formats;
- testability of transformations and preservation of decision/provenance history;
- performance/scalability only against observed corpus/workload, not hypothetical scale;
- simple local inspectability and Git diffability where they remain valuable;
- dependency/toolchain risk, maintenance burden and portability;
- clear separation between research truth and caches/indexes/generated artifacts;
- reproducible and reviewable automation rather than opaque writes.

## Engineering-quality check
A mature refactor should prefer executable invariants over repeated governance prose when the rule is deterministic, while leaving epistemic/scholarly judgements to evidence-aware workflows. Complexity must have measurable research benefit.

## Measures if a gap is demonstrated
Possible minimal measures:
- add targeted validators for recurring errors under #11;
- add small generators for derived witness views/exports;
- formalize schemas only for stable recurring structures;
- introduce tests around migrations/transforms;
- automate import only when #4 is triggered;
- introduce a database/index/application only when file-based canonical data demonstrably fails requirements;
- keep any cache/search index derived and rebuildable;
- use cohesive PRs for repo-wide migrations with before/after examples and rollback plan.

## Trigger
Review when data volume/relations make flat files materially error-prone, repeated manual transformations become a bottleneck, collaboration creates merge/consistency failures, external consumers require stable APIs/schemas, or a major canonical-format migration is proposed.

## Definition of Done
- every new technical component maps to an explicit scholarly requirement or observed failure;
- machine-checkable invariants are tested where justified;
- canonical research truth remains inspectable and recoverable;
- migration is loss-checked against representative real source data;
- derived outputs are reproducible;
- maintenance burden is lower or justified by demonstrable reliability/interoperability gain;
- simpler rejected alternatives and reasons are documented for consequential architecture choices.

## Do not
Do not adopt databases, frameworks, containers, knowledge graphs, APIs or CI/CD merely because they are normal software practice. Do not optimize for hypothetical scale before scholarly semantics and real workload demand it.

### Canonical vs derived boundary for later design

**Canonical:** source/file identities and mappings; project source roles/loci; diplomatic witness units/source phenomena; consequential evidence/decisions/status; source/entity/event/claim relations at demonstrated status; review/validation state where consequential.

**Derived/rebuildable:** human-readable diplomatic witness; expert review packet; TEI/HTML exports; search/index/cache; reports; UI projections.

### Trigger assessment

- General database/platform trigger: **not fired**.
- General machine-readable schema framework (#11): **not yet fired as a broad replacement**; observed problems are still concentrated and target representation has not been selected.
- Targeted referential validation: **justified once** canonical locus/unit representation is selected because multiple requirements depend on exact addressability.
- Deterministic witness generator: **already justified** by REQ-EDIT-008 / REQ-GWP-010 / HITL.
- Migration tests/loss test: **mandatory before** any bulk G2 migration.

### Architecture handoff

The smallest plausible technical target is still a file-based canonical core plus: (1) a stable typed scholarly address/unit representation; (2) minimal phenomenon/claim/evidence structures proven by real Knau cases; (3) targeted validators; (4) deterministic derived witness/review views. No larger software platform is authorized by this audit.

Overall: **targeted change**, not platform refactor.
