### Do not let the Skill decide the Source/File model

Nr. 632 (135 JPEGs) and Nr. 754 (61 viewer images) are valuable **technical fixtures**, but the retrieval layer must remain neutral about whether:

- every image becomes a canonical `corpus/files.tsv` File row;
- an external manifest/package receives a separate durable representation;
- later internal documentary Sources use a subset of root-level image Files.

Those are canonical evidence-model questions, not provider-download logic.

#268 has now been generalized from “one large PDF” to the real failure class: exact File(s) may initially belong to a broader archival-root Source and later need to evidence contained Sources discovered during inspection. The preferred semantic direction is one exact File identity plus a reusable contained-Source↔File+locator mapping, rather than duplicate File rows or hidden Skill-local package truth.

### Consequence for #271 design

The Skill may safely implement/fixture the provider side only if its output remains lossless enough for the later canonical choice:

- stable ordered image inventory;
- exact original filename/route where evidenced;
- per-image SHA-256 and technical metadata;
- package/manifest identity clearly labelled as derived/local packaging, not original archive File identity;
- external storage/access facts explicit;
- no Source segmentation, Project creation or research-function inference.

The later Corpus intake can then decide which exact image Files/manifest references become canonical under the admitted #268 model without re-downloading or inventing provenance.

**Dependency consequence:** #271's provider/download semantics can remain separable, but its canonical File/manifest integration decision should not be finalized in a way that pre-empts #268. This does not by itself admit #271 implementation.
