## Human-Owner requirement

In Human-facing research interaction, internal repository shorthand such as `S1`, `G2`, issue numbers, fixture labels or machine-state tokens must **never stand alone as the explanation of a scholarly action**.

Whenever such shorthand is used, the assistant must also expose the mapping into the scientific / disciplinary level:

```text
INTERNAL TOKEN / CODE
→ scholarly activity or research question in ordinary disciplinary language
→ why it matters for this source/project
→ evidence needed / what can establish it
→ claim ceiling / what it does NOT establish
```

If a machine representation is additionally needed, that must be presented as a **separate subordinate layer**:

```text
scholarly requirement
→ information that must be preserved
→ machine-readable fields / identifiers / checks only as implementation support
```

The Human Owner can then supply or correct concrete machine data without being forced to infer their scholarly meaning from repository codes.

## Demonstrated real-use incident

While discussing the next methodical step for Nr. 632, the assistant wrote that “S1” should be completed without first explaining what `S1` means.

In the current METHOD, `S1` is:

> **Establish investigation source group and provenance.**

Scientifically, this is the archival/source-critical establishment of the source basis: identify which exact archival/documentary object(s) are being investigated, distinguish them from related records/witnesses/loci, preserve their archival identifiers and provenance, and ensure that the exact digital instantiation actually inspected can later be recovered and audited.

The bare code `S1` hid that disciplinary meaning from the Human even though the Human is supposed to control and understand the research process.

## Why this matters in the Wirknetz

Failure mechanism:

```text
repo-internal method code
→ assistant treats code as self-explanatory
→ Human sees process token but not scholarly purpose
→ machine/workflow layer becomes cognitively primary
→ Human cannot easily judge whether proposed action still serves the research goal
→ increased risk of silent scope drift, authority inflation, or machine-data work replacing scholarship
```

Desired mechanism:

```text
Human research need
→ scholarly action explained in disciplinary language
→ evidence / uncertainty / claim ceiling visible
→ internal METHOD token shown only as secondary mapping
→ concrete information-preservation need made explicit
→ machine-readable representation derived from that need
→ Human can add/correct technical data without losing scholarly control
```

This supports the Governing Objective's precedence:

`scholarly/research requirements → methodology → information model → software/AI`

rather than reversing it.

## Concrete example — Nr. 632

### Scholarly level

For Nr. 632, the source-basis/provenance activity currently means:

- establish the exact archival object and catalogue identity;
- retain the official archival provenance and stable digital identifier;
- know exactly which 135 digital images constitute the inspected representation;
- preserve their order and exact identity;
- ensure that later observations can be traced back to a concrete image/file;
- keep catalogue description distinct from manuscript observation;
- record what has and has not actually been inspected.

This does **not** itself establish manuscript contents, documentary boundaries, hands, readings, historical interpretation or relevance of individual loci.

### Information that must be preserved

At the current fixture, the already demonstrated machine-support needs include, as applicable:

- archive / fonds / signature / official title / date;
- record URL + GUID;
- provider image sequence and actual filenames;
- provider file-list identity/hash;
- exact local package identity and integrity state;
- exact per-image checksum/dimensions where already produced by the acquisition package;
- mapping between provider image name and working/local image;
- inspection coverage: which image was inspected, for what purpose/depth, and what remains not inspected/unresolved;
- later, any canonical File/Source identifier only if the normal intake/model decision actually creates one.

These are **supporting information requirements**, not the scholarly explanation itself.

No new field/schema is chosen by this Issue.

## Feature requirement

Human-facing scholarly assistance should satisfy all of the following:

- [ ] first use of an internal research-stage/maturity code in a conversation gives its scholarly name and plain disciplinary meaning;
- [ ] issue numbers / fixture IDs / implementation tokens are never used as substitutes for explaining the research action;
- [ ] the Human can see **what scientific question/action is being undertaken and why** before machine representation details;
- [ ] machine-readable data needs are explicitly distinguished from scholarly evidence and research findings;
- [ ] when the Human is asked to supply machine data, the assistant explains what scholarly/reproducibility requirement that data serves;
- [ ] technical completeness cannot be mistaken for scholarly maturity;
- [ ] mappings preserve evidence status, uncertainty and authority; translation into ordinary language must not add certainty;
- [ ] the interaction remains concise: this is not a requirement to dump every internal code or schema field into every answer.

## Acceptance fixture

Use the real Nr. 632 source-entry interaction.

A PASS response to “wie methodisch weiter?” should be understandable without prior knowledge of repository vocabulary and should say, in substance:

1. **Source basis and provenance** — establish exactly what archival object/digital representation is being worked on and make it recoverable/auditable (`S1` only as secondary label).
2. **Document/material reconnaissance** — inspect the visual source in order to learn its observable structure and preserve uninvestigated/unresolved states (`S2` only as secondary label).
3. only then progress to transcription, palaeographic testing, contextual source criticism etc. as the evidence/question warrants.

If machine data are needed, the response should name the concrete data and why they are needed, but must not make the Human reverse-engineer the scientific workflow from fields, codes or issue numbers.

### Strong external findings relevant to the proposed work form

1. **Historical source and derived research data should remain distinguishable.** The DFG History 2026 guidance explicitly recommends distinguishing historical sources/digitisations from data derived by transcription, excerpting, commentary, markup, contextualisation, etc., and requires documentation of creation context and processing for traceability/reuse. This strongly supports #307 and the proposed separation of source observation from derived interpretation.

2. **The research process and division of responsibility must be intelligible.** DFG History 2026 requires methods/workflows that create or transform data to be described and, in collaborative work, responsibilities for tasks/phases to be explicit. This supports the #308 requirement that the Human sees the scholarly action and the machine-data purpose rather than opaque internal tokens.

3. **Editorial method must be purpose- and source-fit, explicit and criticisable.** DFG edition criteria tie aim, edition type, method and publication form together. MLA vetting asks for clear editorial principles/practical methods, provenance, physical description, accuracy checks, rationale for technological choices, documentation and preservation. The MLA digital-age statement treats transparency, accuracy, appropriate method and responsible documentation as fundamental. This supports a dual scholarly/operational view, but not a universal workflow ontology.

4. **Digital representation is a mediation, not the physical object.** MLA asks editors to state how digital/photographic reproductions manipulate or differ from the material source. Campagnolo stresses that digital surrogates cannot capture all material features. Therefore Nr. 632 image inspection can support only properties observable from the digital representation; material/codicological non-observables must remain explicitly bounded.

5. **Palaeographical hand identity is a hypothesis requiring comparative evidence, not a visual impression token.** Horobin 2024 emphasizes intra-scribe variation, script variation and the methodological difficulty of hand attribution. This supports the repo rule that a writing-characteristic change may be observed provisionally without creating a named/same-hand identity.

6. **TEI supports — but does not itself prescribe our workflow.** TEI 4.12.0 provides mechanisms for transcriptional phenomena, facsimile/surface linkage, uncertainty and responsibility. This externally validates the need to keep observed text/phenomena, uncertainty and responsibility representable. It does **not** imply that TEI XML, a TEI schema or any specific field set must be introduced at reconnaissance stage.

7. **Context is necessary in historical research, but remains context.** NFDI4Memory explicitly centers provenance, source criticism and contextualisation of digital historical data. This supports problem-driven use of archival/fonds/history context after or alongside a concrete source question, but not promotion of contextual plausibility into manuscript observation.

8. **Technical standards remain subordinate to the scholarly need.** FAIR requires provenance and domain-relevant community standards but explicitly does not prescribe an implementation technology. IIIF can model ordered views of compound digital objects, but nothing in the current Nr. 632 task demonstrates a need to introduce IIIF. This supports the repo's technical-subsidiarity rule.
