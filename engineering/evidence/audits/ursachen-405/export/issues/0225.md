## 1. System problem to solve

`paleo-type` already contains a strong Governing Objective, extensive domain/system requirements, S1–S9 scholarly method, G1–G6 maturity gates, authority/evidence safeguards, restartability rules, deterministic Source/Project tooling and multiple failure-derived regressions.

Nevertheless, normal use still depends too heavily on the current AI reconstructing the **integration among those pieces** from prose and chat context.

The repeated practical failure is:

```text
Human need / intended scholarly outcome
→ rich repository rules and models
→ local defect / local guardrail / local support task dominates
→ valid local fix / PASS / STOP
→ higher-level outcome cursor is lost or weakened
→ next context reconstructs differently
→ non-specialist Human Owner is asked to choose domain/technical steps
→ usable scholarly result remains delayed
```

The problem is therefore not mainly missing rules. It is a **systemic operationalization / composition gap**.

## 2. Governing outcome

Design and validate the **smallest coherent generic mechanism** by which an owner-authorized scholarly need remains a durable control objective until one of two legitimate terminal conditions is reached:

1. a usable scholarly result at the required quality/maturity level; or
2. a real evidence / authority / specialist-validation ceiling that cannot be crossed without a genuine Human-Owner decision or new evidence.

The Human Owner must not need to know internal gate jargon, disciplinary sequencing or software architecture in order to receive high-quality scholarly support.

The system must remain generic and dynamically compose the needed capabilities from the actual source, question, desired outcome, maturity and evidence state.

---

## 3. Required end-to-end control chain

The mechanism must preserve a traceable chain equivalent in meaning to:

```text
HUMAN NEED / DESIRED SCHOLARLY OUTCOME
        ↓
OWNER-AUTHORIZED PROJECT PURPOSE + SCOPE
        ↓
CURRENT CANONICAL EVIDENCE + MATURITY STATE
        ↓
UNMET REQUIREMENTS FOR THE DESIRED OUTCOME
        ↓
QUESTION-/CLAIM-/SOURCE-RELATIVE CAPABILITY ACTIVATION
        ↓
SMALLEST COHERENT VERTICAL WORK SLICE
        ↓
EXECUTION ALLOCATION
  deterministic | AI-assisted | specialist | Human Owner
        ↓
EVIDENCE / QUALITY / GATE VALIDATION
        ↓
USABLE SCHOLARLY RESULT
        ↓
PERSIST / RESTART / CONTINUE OR TERMINATE AT A REAL CEILING
```

A local repair must return to the same valid higher-level outcome cursor unless the repair establishes that the cursor itself is no longer authorized or feasible.

Local `PASS`, `STOP`, Issue closure, CI success or support completion must never masquerade as whole-outcome completion.

## 4. System capabilities to operationalize

This Issue does **not** pre-decide whether these become one component or several reusable services/resolvers. It requires that the following functions become operationally available and composable.

### A. Need / outcome representation and resolution

The system must be able to receive a Human-Owner goal in ordinary domain-facing language and bind it, without semantic laundering, to the relevant Project purpose/scope and expected scholarly result class.

It must distinguish:

- stable Human need / intended outcome;
- Project purpose;
- current bounded scope;
- current scholarly question/work target;
- gate/maturity state;
- implementation/support tasks.

No one of these may silently replace another.

### B. Outcome → unmet-requirements resolution

Given a desired outcome + authorized scope + current canonical state, determine what scholarly/system requirements are still unmet.

This should use existing S1–S9, G1–G6 and domain requirements rather than invent a second method.

Where semantics are stable enough, the derivation should become deterministic and model-independent.

### C. Dynamic capability / competence activation

Activate only the competencies warranted by the source/problem/claim:

- archival science / diplomatics;
- palaeography;
- historical philology / lexicography;
- scholarly editing / textual criticism;
- historical source criticism;
- codicology/material study where relevant;
- metrology/accounting/domain history where triggered;
- RDM/GWP;
- Requirements Engineering / information modelling;
- RSE / software architecture;
- verification engineering;
- HCI/HITL;
- AI/context engineering;
- qualified specialist review where consequence warrants it.

No fixed permanent leader, role pipeline or Reg.-Ii.-5-shaped topology is assumed. Leadership/routing is claim- and context-relative.

### D. Human / AI / specialist / deterministic allocation

For every required function, decide explicitly which mode is appropriate:

`deterministic | AI-assisted | specialist judgement | Human-Owner decision`

Stable state, identity, provenance, dependency, context assembly, allowed transitions and regression checks should progressively move out of AI inference when they can be formalized without semantic loss.

AI should remain where interpretation, synthesis, hypothesis generation, semantic comparison or other genuinely non-deterministic reasoning is required.

The Human Owner should receive only genuinely non-derivable decisions, with a specialist-prepared decision surface.

### E. Durable higher-level outcome cursor

There must be a restartable representation or derivable control surface that answers:

- what usable outcome is being pursued;
- which scope authorizes it;
- current maturity/evidence position;
- which unmet requirements remain;
- what vertical slice is active;
- what local repair/support action temporarily interrupted it;
- where execution returns after that repair;
- what legitimate condition would terminate or invalidate the outcome cursor.

The implementation form is open. Avoid a new manually maintained prose truth store if the state can be derived from canonical owners.

### F. Repair / recovery return semantics

Bounded failure handling must behave like:

```text
valid scholarly cursor
→ local evidence/capability/support failure
→ smallest authorized repair
→ recheck affected prerequisite / authority
→ return to same scholarly cursor
```

Only an actual evidence ceiling, authority change, scope invalidation or specialist/Human decision should prevent return.

### G. Model-independent restart/context assembly

A fresh capable context must be able to reconstruct the full authorized control state without old chat.

The mechanism must reduce dependence on:

- prompt memory;
- one model's interpretation of prose;
- hidden sequencing knowledge;
- manual Human-Owner re-explanation.

### H. End-to-end system acceptance

Component regressions remain necessary but insufficient.

The system must have vertical acceptance fixtures proving that the pieces compose into useful scholarship.

## 5. Quality attributes — simultaneous, not tradeable by default

A valid solution must preserve all of these together:

1. **scholarly outcome quality** — scientifically usable result appropriate to source/problem;
2. **epistemic reliability** — evidence before plausibility, uncertainty and claim-layer separation;
3. **State of the Art / Best Practice** — relevant current disciplinary and technical competence activated proportionally;
4. **human usability** — non-specialist owner is not the fallback expert/architect/operator;
5. **auditability / restartability** — no chat knowledge monopoly;
6. **genericity** — reusable across materially different manuscripts/source structures;
7. **adaptivity** — capabilities assembled dynamically from need/context rather than fixed pipeline;
8. **AI independence** — stable semantics/control migrate to deterministic owners where justified;
9. **technological excellence** — clean contracts, tests, provenance, maintainability, security/platform boundaries;
10. **lean delivery** — smallest mechanism that preserves required quality; no infrastructure for its own sake;
11. **agile vertical flow** — small end-to-end slices delivering/revalidating real scholarly outcomes rather than horizontal local optimization.

A solution that maximizes one dimension while materially degrading another does not satisfy the system need.

- [ ] Stable semantics and transitions that can be deterministic do not depend on model memory.
- [ ] Canonical owners remain single-source; no duplicate control truth store is introduced.
- [ ] Existing Source/File/Project validators and context tooling are reused where adequate.

- [ ] Fresh-context restart reproduces the same authorized control state.
- [ ] At least one end-to-end regression/acceptance fixture tests the composition, not just components.

- [ ] Mechanism is not structurally dependent on Reg. Ii 5/Knau/visitation material.

- [ ] Development proceeded through vertical slices tied to real outcomes.
- [ ] No architecture component exists without a demonstrated requirement.
- [ ] New complexity replaces/reduces model/chat/manual burden rather than merely adding another layer.
- [ ] PASS → STOP applies to each repair hypothesis, followed by return to the higher-level outcome cursor until the outcome itself is complete or legitimately blocked.

## Self-audit / anti-fragmentation guard — added after explicit challenge against the operationalization audit

This comment is part of the planning/audit history of #225. It exists to prevent this programme from reproducing the exact failure pattern it is meant to solve.

### Finding

The proposed phased/child-Issue structure is useful only if decomposition remains subordinate to the end-to-end system outcome. Without explicit controls, separate Issues for Requirements, Concept, Implementation and Acceptance could themselves become locally successful horizontal workstreams whose PASS/closure is mistaken for system progress while the governing Human-need → scholarly-outcome chain remains broken.

Therefore decomposition is permitted only under the following rules.

### Child-Issue admission test

Create a child/work Issue only when all are true:

1. it has one independently reviewable result with its own bounded completion condition;
2. that result is explicitly necessary for #225's end-to-end outcome, not merely an interesting domain topic;
3. its input authority and parent outcome link are reconstructable from repository state;
4. it does not create a competing canonical owner for semantics already owned elsewhere;
5. its completion has an explicit return/reconciliation condition to #225;
6. it can fail/close without implying that #225 passed;
7. splitting it out reduces cognitive/review complexity rather than increasing planning bureaucracy.

If these conditions are not met, keep the work inside #225 or the owning canonical requirement/method artifact rather than creating another Issue.

Do not create Issues merely for disciplines or themes such as palaeography, AI, HCI, gates, outcome cursor, repair return, RSE, etc. A separate Issue requires a demonstrated independently testable mechanism/result, not topical importance.

### Parent/child invariant

Every child/work Issue under #225 must state, or derive unambiguously:

```text
PARENT SYSTEM OUTCOME: #225
CONTRIBUTION: <which end-to-end capability/requirement it establishes>
INPUT / CANONICAL OWNERS: <references>
BOUNDED RESULT: <what this Issue can establish>
WHAT IT CANNOT ESTABLISH: <especially whole-system success>
RETURN CONDITION: <how its result is reconciled to #225>
```

These meanings need not become a new universal template/schema; they are an acceptance invariant for this programme.

### Mandatory reconciliation on every local completion

Before closing any child Issue, PR, repair or implementation slice, answer in #225 planning state:

- Which #225 requirement/capability changed?
- Which remained unchanged?
- Did the higher-level outcome cursor remain valid?
- What is the next unresolved end-to-end gap, if any?
- Does this local PASS alter the whole-system acceptance state? If yes, exactly why; if no, state `LOCAL PASS ONLY`.

A child Issue may close even when #225 remains open. Silence must never be treated as whole-programme advancement/completion.

### Required acceptance/falsification tests

The resulting design must include tests for the composition failure itself, not only for components.

#### T1 — Ordinary-language outcome test

Given a non-specialist Human-Owner desired scholarly outcome plus valid Project/scope authority, the system resolves the relevant current state and unmet requirements without requiring the owner to know S1–S9, G1–G6, specialist sequencing or software architecture.

FAIL if the user must choose an internal method/gate/technical step that is derivable from canonical state and requirements.

#### T2 — Fresh-context equivalence test

Two fresh capable contexts, with no originating chat, given the same canonical state and controlled evidence must reconstruct materially equivalent:

- governing outcome;
- authorized scope;
- maturity/evidence state;
- unresolved requirements;
- Human/AI/specialist/deterministic responsibility boundary;
- valid continuation/ceiling state.

FAIL if materially different continuations arise solely from model interpretation of scattered prose.

#### T3 — Local-PASS containment test

A component regression, support repair, PR, child Issue or CI check passes.

PASS only if:

- the local result is recorded at its actual authority level;
- #225 remains open unless whole-outcome acceptance criteria are independently satisfied;
- no local PASS/STOP is promoted into system completion.

#### T4 — Repair-return test

Start from a valid higher-level scholarly/outcome cursor; inject or encounter a bounded resource/capability/process failure; perform the smallest authorized repair.

PASS only if execution returns to the same cursor unless a real authority/evidence invalidation is established.

FAIL if the repair becomes the new objective, produces an unrelated replacement target, or leaves the original outcome orphaned.

#### T5 — Non-specialist-owner boundary test

During an end-to-end fixture, record every Human-Owner question.

PASS only if questions are genuinely non-derivable purpose/priority/authority/use decisions.

FAIL if the owner is asked to substitute for palaeographic/editorial/philological expertise, technical architecture, repository synchronization, gate translation or routine sequencing.

#### T6 — Dynamic capability test

Use at least two materially different source/problem fixtures.

PASS only if different relevant competencies/methods can be activated without hard-coded Reg.-Ii.-5 structure or a fixed permanent role topology.

#### T7 — AI-independence / deterministic-substitution test

For every repeated system inference in the accepted design, classify whether semantics are stable enough for deterministic representation/derivation.

PASS only if stable machine-checkable semantics do not remain dependent on prompt/model memory without an explicit reason.

FAIL if the new mechanism merely concentrates prose and asks AI to interpret it more carefully.

#### T8 — No parallel-truth-store test

PASS only if the mechanism derives/references existing canonical owners where possible and does not require a second manually maintained copy of Project scope, gate state, evidence state, domain requirements or research truth.

#### T9 — Vertical-value test

Each implementation increment must demonstrate an observable improvement in an end-to-end scholarly flow or reduce a demonstrated correctness/usability/restartability burden.

FAIL if an increment only expands framework/API/schema/documentation without advancing or protecting a real vertical fixture.

#### T10 — Legitimate-ceiling test

The mechanism must be able to terminate or pause correctly when there is a real evidence ceiling, missing owner authority or warranted specialist-validation dependency.

PASS requires exposing the exact ceiling without fabricating substitute work or silently weakening quality standards.

#### T11 — System acceptance test

#225 cannot close from component counts, number of tests, architecture completion or documentation completeness.

Closure requires demonstrated evidence that the accepted mechanism can carry an authorized Human need through the full relevant chain to a usable scholarly result (or legitimate ceiling), survive fresh-context restart, recover after bounded repair and work on a materially different fixture.

### Anti-metric / anti-gaming rule

Do not use number of Issues closed, PRs merged, tests passed, requirements written, lines of code, schemas added or phases completed as proxies for #225 success.

The governing measures are outcome quality, reliability, Human usability, genericity, restartability, AI-independence gain and proportional overhead, as already defined in #225.

### Immediate planning consequence

Do **not** create the previously suggested full set of child Issues up front.

At the current state, only the Phase-0/Phase-1 consolidation is eligible to become a separate work Issue if separating it materially improves reviewability. Later Concept, Implementation and Acceptance Issues must be created only when their predecessor produces enough evidence to satisfy the child-Issue admission test above.

This preserves #225 as the durable whole-system outcome owner and makes decomposition demand-driven rather than a new fixed programme topology.
