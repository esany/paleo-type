## Research/user benefit

After the pilot, a researcher should be able to supply a source file and answer only the unavoidable archival/research/rights/project questions, without having to know `corpus/*.tsv`, Project templates, validator commands or ownership paths.

A small guided intake/preflight may be justified if it materially reduces repeated software supervision while preserving the source-critical and HITL boundaries defined in #69.

## Why not now

The canonical intake semantics and decision order are only now being consolidated in #69, and the current pilot has not yet demonstrated enough repeated independent intake/project-bootstrap cycles to choose an implementation form responsibly.

The repository already has substantial reusable machinery (`source-contract.json`, `source_contract.py`, resolver semantics, project template). Building a wizard, service or generalized importer before the normative workflow has been dry-run would risk encoding the wrong questions and duplicating canonical rules.

This Issue is therefore **deferred option evaluation**, not implementation admission.

## Trigger

Re-evaluate after #69 is accepted **and** at least one of the following is observed:

- two or more additional real source/file intake cycles show repeated manual orchestration across the same owners;
- a real new-Project bootstrap requires the user/agent to rediscover repository mechanics despite the documented workflow;
- repeated intake mistakes occur that are deterministic and preventable;
- the user still has to answer software-structural questions that should be derivable from canonical state;
- #4 automated metadata ingest is triggered and needs a safe downstream routing/preflight path.

A pilot-completion review may examine this Issue even if the trigger is not clearly fired, but lack of demonstrated burden is a valid reason to leave it deferred/close as unnecessary.

## Alternatives to compare

Do not pre-select technology. Compare at least:

### A. Documentation-only / AI-executed canonical workflow

Keep #69 as the sole intake procedure; AI/researcher follows it and runs existing validation. No new executable component.

Use if this already leaves the human with only research/authority decisions.

### B. Small deterministic `intake preflight` command

A local command receives a supplied file path and repository context, computes/checks byte identity, reports known/unknown File state, exposes possible existing Source/Project facts deterministically, lists required unresolved human decisions, and validates a proposed mutation plan.

It should prefer a dry-run/report over autonomous canonical writes.

### C. Guided local CLI/wizard over the same rules

A thin interaction layer asks only unresolved questions and then produces a reviewable plan/diff using existing canonical owners/template/validator.

No separate intake database/state store.

### D. AI workflow wrapper

AI performs the orchestration from #69 but must use deterministic tools for checkable facts and explicitly ask for project/rights/source-granularity decisions where not derivable.

This may require no repository component beyond clearer task routing.

### E. Integration with #4 metadata import

If automated discovery/import becomes active, imported metadata may feed the same preflight, but discovery must not bypass exact File identity, Source-granularity judgement, project routing or reviewable writes.

## Stable boundaries any option must preserve

- no File identity from filename/content similarity alone;
- exact known-byte match may resolve canonical File identity deterministically;
- unknown/nonmatching bytes trigger an unresolved/new-file path, not a guessed crosswalk;
- no automatic Source identity/granularity when archival evidence is insufficient;
- no automatic Project creation;
- no automatic Project assignment from active chat/current directory;
- Project creation requires confirmed historically independent `project_source_id` root plus research purpose/active scope;
- internal/external structural status is derived, not asked of the user;
- research function remains a Project-relative scholarly decision, not inferred from Source type;
- rights/public-redistribution authority is not invented;
- canonical facts are written only to their existing owners;
- use existing `source-contract`/template semantics rather than introducing a parallel schema;
- protected binaries are not made public for convenience;
- automation reports deterministic failures rather than self-certifying scholarly correctness;
- canonical-writing automation, if ever admitted, is reviewable and narrower than scholarly judgement (REQ-RSE-010 / REQ-AI-007/008).

## User-experience target

For a routine known or clearly characterized source file, the user should ideally see only a short research-facing interaction such as:

1. file identity/provenance result;
2. Source identity/status or the one unresolved archival question;
3. `existing Project | create candidate new Project | no Project yet` choice when project routing is not already explicitly given;
4. research function/scope questions only when a Project use is being created;
5. rights/authority question only when needed;
6. reviewable summary of what canonical state will change;
7. validation/result + next research action.

The user should not need to select repository paths, table names, schema fields or validator internals.

## Evaluation criteria

Compare alternatives by:

- reduction in user software/architecture questions;
- deterministic error prevention;
- preservation of archival/source judgement boundaries;
- inspectable/reviewable mutations;
- reuse of current canonical owners and validation;
- local portability and dependency burden;
- failure recovery/restartability;
- compatibility with protected/nonpublic source bytes;
- amount of new code/state that must be maintained;
- whether the component still adds value when AI tooling/models change.

## Acceptance criteria for later option review

- [ ] #69's normative intake workflow has been accepted/dry-run first;
- [ ] observed repeated burden/error is documented, or `no automation needed` is explicitly considered;
- [ ] alternatives A–E are compared against the actual post-pilot workflow rather than hypothetical scale;
- [ ] every proposed executable behavior maps to a stable deterministic requirement or a clearly bounded human question;
- [ ] no scholarly/archival judgement is converted into deterministic truth merely to simplify UI;
- [ ] no duplicate canonical intake state/schema is introduced;
- [ ] the smallest option that leaves the user with few software questions is selected, including documentation-only if sufficient;
- [ ] any material executable implementation receives a separate D-016 implementation admission before development.

## Non-goals

- no web upload platform;
- no asset/media management system;
- no database/API requirement;
- no autonomous archival description;
- no autonomous project creation;
- no generalized workflow engine;
- no project migration;
- no assumption that a GUI is better than a small CLI/AI-orchestrated flow.
