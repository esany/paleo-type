## Integration tasks

### 1. Preserve evidence layers

Do not rewrite primary findings into the current analysis vocabulary. Keep visible:

```text
A. original/open finding
B. structured secondary extraction
C. cross-competence interpretation
D. cross-fixture/cross-source interpretation
E. Concept Challenge
```

If a finding does not fit the existing taxonomy, record the mismatch as evidence.

### 2. Compare evidence strength correctly

Keep separate:

- cross-competence convergence on one fixture;
- cross-fixture recurrence;
- cross-source recurrence;
- literature support;
- scenario testing;
- human-observed evidence where available.

Do not add these as if they were interchangeable independent replications.

### 3. Requirement-efficacy synthesis

For recurring findings, classify only as far as evidence supports, for example:

- Requirement missing;
- Requirement exists but trigger/visibility/timing/sequence failed;
- mechanism gap;
- translation/authority error;
- freshness/propagation failure;
- function loss after simplification;
- enforcement gap;
- interaction/composition hypothesis;
- insufficient evidence / alternative explanation unresolved.

These are analytical outcomes, not new controlled Requirement states unless later promoted through the proper process.

### 4. Dependency / transdisciplinarity synthesis

Analyse what the dependency provenance shows about:

- independent judgement without isolation;
- productive transdisciplinary interaction;
- context starvation;
- premise inheritance;
- early convergence;
- legitimate question/evidence redirection by another competence;
- cases where no single competence can sensibly analyse the problem alone.

Do not turn observed interaction patterns into a workflow model in this Issue.

### 5. Concept Challenge

Evaluate individual Concept Candidate hypotheses against the frozen findings. Suggested non-normative dispositions:

```text
supported
partially supported
not evidenced
contradicted
over-specified
prematurely formalized
redundant with mature existing mechanism
source-/Project-specific
simpler explanation/mechanism possible
requires further research
```

Explicitly distinguish evidence for a scholarly/system need from evidence for the Concept Candidate's proposed implementation form.

## Output boundary

The output should be a **decision-ready research synthesis** that can later support a separate Synthesis/Requirements decision about:

- which needs appear persistent;
- which might justify generic capabilities;
- whether existing normative Requirements suffice;
- where new normativity may be justified;
- what solution space should subsequently be compared.

This Issue itself stops before making those normative/design decisions.

## Completion criteria

- [ ] #184 and #185 findings are sufficiently frozen before Concept comparison;
- [ ] primary findings remain traceable and unchanged in meaning;
- [ ] cross-competence, cross-fixture and cross-source evidence strength are not conflated;
- [ ] Requirement existence and efficacy remain distinct;
- [ ] transdisciplinary dependency patterns are analysed without prescribing a fixed interaction workflow;
- [ ] Concept Candidate hypotheses are challenged individually rather than accepted/rejected as one bundle;
- [ ] unsupported solution detail is identified as such;
- [ ] remaining uncertainty and missing evidence are explicit;
- [ ] the output stops before normative Requirement/capability promotion and design selection.

## Downstream

Any later Requirements/Capability/Solution-Synthesis work requires a separate explicit admission after this Research integration is complete. Closing this Issue does not create that admission.
