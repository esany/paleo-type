## Governing principle

**Keep role/chat contexts epistemically clean; make settled process/state mechanics deterministic where possible.**

A role context should be able to answer:

1. What role/stage am I executing now?
2. What is the first/next bounded action?
3. Which prerequisites are PASS/FAIL/UNKNOWN, and what event can invalidate a PASS?
4. What evidence is required and is it accessible now?
5. What is the current execution cursor / completion condition?
6. What is outside my competence/authority?
7. What must I persist before handoff?
8. Which role/owner receives the result and what question must it answer?

The system should derive stable facts from canonical state rather than asking chats/users to restate them.

## Generic deterministic building blocks to evaluate

### A. Work-context contract

Minimum semantics, preferably derived where possible:

- `ROLE / RESPONSIBILITY`
- `TASK / ISSUE OWNER`
- `CURRENT EXECUTABLE STAGE`
- `FIRST / NEXT BOUNDED ACTION`
- `PREREQUISITES` with explicit `unknown|pass|fail` and invalidation trigger
- `EVIDENCE REQUIRED / ACCESSIBLE NOW / IDENTITY VERIFICATION`
- `EXECUTION CURSOR`
- `COMPLETION CONDITION`
- `OUT-OF-SCOPE / NOT-AUTHORIZED`
- `HANDOFF TARGET / RETURN CONDITION`

Do not freeze labels before testing the minimum representation against real fixtures.

### B. Sticky-precondition + circuit-breaker semantics

Candidate deterministic invariant:

```text
prerequisite PASS
→ remains PASS for the current work context
→ until an explicit invalidation event occurs
```

Examples of valid invalidation: actual retrieval failure, checksum/identity contradiction, rights/authority change, canonical source-state change that makes the earlier test stale.

Re-entering an already-PASS prerequisite **without an invalidation event** is not progress and should be classified as a work-context execution fault.

Candidate circuit-breaker:

1. first invalid re-entry → redirect once to current cursor;
2. recurrence after explicit correction / unchanged prerequisite state → retire the execution context and resume the same role from canonical state in a fresh context;
3. persisted scholarly evidence remains valid unless separately contradicted.

Do not use the circuit-breaker to suppress legitimate scholarly iteration. It applies to repeated process/prerequisite branches whose state is already deterministically established.

### C. Progress / delta contract

A repeated delegation or action is legitimate only when at least one of the following changes:

- new evidence is inspected;
- uncertainty/decision state changes;
- exact bounded question becomes narrower;
- canonical state advances;
- a stated prerequisite is invalidated;
- escalation level changes for a justified reason.

A return that merely repeats the same task/question with no new evidence/state delta should be flagged as `no-progress / delegation-loop candidate` and routed to the process/technical owner rather than bounced indefinitely between domain contexts.

### D. Issue work contract

Every consequential implementation/process Issue should make the following reconstructable, deriving fields from canonical state where safe rather than duplicating truth:

- demonstrated problem / evidence fixture;
- canonical owner / authority;
- current state and dependencies/prerequisites;
- bounded scope;
- explicit non-goals;
- deterministic acceptance criteria;
- scholarly/domain/human acceptance criteria where applicable;
- persistence/restartability obligation;
- required review lenses;
- return/close condition.

An Issue is not ready for Dev merely because it describes a problem. For material technical work it must also satisfy the existing #73→#74 and D-016 boundaries.

### E. Handoff contract

A role-to-role result handoff should preserve only information that cannot safely be re-derived:

- `FROM / TO / TRIGGER`;
- evidence pointers actually inspected;
- established findings;
- unresolved / not investigated / negative findings;
- exact request to receiver;
- scope/non-goals;
- acceptance/review question;
- canonical persistence pointer;
- return condition.

Stable Source/File/Project/owner facts should be resolved from canonical state rather than manually copied where possible.

### F. Canonical-state freshness check

A completed stage/handoff is not restartable if the canonical restart surface still points to the old stage.

Evaluate the smallest check ensuring that when a consequential stage changes:

- the owning result is persisted;
- `STATUS.md`/canonical NEXT ACTION is synchronized where it is the owner;
- the handoff points to current canonical state;
- stale prior handoff/state prose is not treated as current authority.

This is a structural freshness check; it does not decide whether a scholarly gate is scientifically satisfied.

## Cross-role hard review model

"Hard review" means **a triggered review that cannot be silently skipped**, not a permanent new role or approval bureaucracy. Use independent/fresh contexts where consequence or self-review risk warrants it.

### 1. Role / authority review

Checks:
- correct executable role/stage;
- correct owner;
- no unauthorized downstream work;
- material-change admission present if required;
- return path identified.

Deterministic where owner/stage/admission state is explicit; authority semantics remain governed by existing canonical rules.

### 2. Evidence / provenance / availability review

Checks:
- exact evidence identity;
- actual accessibility when the task requires inspection;
- transformation/provenance integrity;
- rights/storage boundary;
- no metadata-as-source substitution.

Technical/provenance checks may be deterministic; scholarly adequacy of evidence remains domain judgement.

### 3. Technical assurance review

Checks:
- requirement traceability;
- smallest adequate mechanism;
- referential integrity;
- deterministic tests;
- migration/loss/rebuildability;
- no parallel truth;
- security/rights leakage;
- scope/non-goal preservation.

For routine low-risk work this may be ordinary Dev tests/review. Independent technical review becomes mandatory only on a demonstrated trigger under #79.

### 4. Scholarly adequacy review

Owned by #73 (and #76 where independent specialist judgement is triggered), not Dev.

Checks whether an implementation/result preserves required scholarly meaning, uncertainty, evidence layers, provenance and research usability. CI cannot satisfy this review.

### 5. Human / restartability / challengeability review

Checks:
- current result/next action understandable without chat;
- user is not made repository operator;
- consequential action explainable as `problem → requirement/evidence → owner → change → deterministic vs judgement → consequences/open points`;
- fresh capable context can resume from canonical state + authorized evidence.

### 6. Governance / purpose review

Human Owner only where existing rules reserve the decision: research purpose/priorities, unresolved rights/authority facts, new project creation/scope, consequential publication/use, material change admission, Governing Objective amendment.

## Review points in the flow

Use consequence-scaled reviews at real transition points rather than continuously:

```text
ROLE/TASK START
→ role/authority + evidence-availability check

WORK / ITERATION
→ progress delta + circuit-breaker only when triggered

RESULT HANDOFF
→ persistence + unresolved/non-result + request completeness review

PRE-DEV
→ requirement/scope/admission review

DEV / PRE-MERGE
→ technical assurance + loss/provenance/rebuild checks

DEV RETURN
→ Domain Review scholarly adequacy

STATE TRANSITION
→ STATUS/NEXT ACTION freshness + restartability
```

## Context-purity rule

Domain/research chats should not become generic workflow engineers.

When a domain context encounters a repeatable process/tool/context failure outside its competence:

```text
observe failure
→ preserve exact reproduction/evidence
→ identify affected research consequence
→ state what the domain role cannot/should not decide
→ create/update bounded technical Issue or handoff
→ stop generic process repair in the domain context
```

Conversely Dev must not use the technical Issue to re-adjudicate the source/domain finding.

## Kommentar 5480633411 · 2026-08-31T15:34:54Z · esany

## Falsification refinement — state-token ambiguity + anti-formular review

Review of the live `63r-L05–L11` start handoff exposed two distinct effects that should not be conflated.

### A. Real generic interface defect: `EVIDENCE STAGED` was overloaded

The current assurance pattern correctly distinguishes:

```text
RETRIEVABLE
STAGED
VISION-INSPECTABLE
```

but some #85/#86 wording then reused `EVIDENCE STAGED = PASS` as the *composite executable gate* after both target-object presence and pixel inspectability had been verified. This overload is unsafe across heterogeneous models because `STAGED` can mean either the raw presence state or the derived research-ready state.

Refined invariant:

```text
STAGED = PASS
  means: required evidence object is present in this target context

VISION-INSPECTABLE = PASS
  means: this target context can actually inspect the required visual evidence

VISUAL EVIDENCE READY = PASS
  iff STAGED = PASS AND VISION-INSPECTABLE = PASS
  for the same evidence + same target context
```

`RETRIEVABLE` never implies either downstream state.

If a start handoff asserts only `STAGED = PASS`, the target context may perform one local inspectability preflight as its first action. If that fails, it returns `VISUAL EVIDENCE READY = FAIL` / `EVIDENCE NOT READY` to the staging owner and performs no retrieval diagnosis.

This is a terminology/state-typing correction, not a new workflow engine or state machine.

### B. Review false positive: semantic contract was mistaken for mandatory field syntax

The live handoff already made its completion semantics reconstructable (`63r-L05–L11` complete, persist, synchronize state, return #64). Requiring an explicit literal `COMPLETION CONDITION:` label would violate the existing #77/#86 principle that work-context semantics are required but labels/serialization are not.

Add review invariant:

> Handoff assurance checks semantic reconstructability, not lexical/template conformance. Do not demand a field label when the required role/stage/prerequisite/cursor/completion/return meaning is already unambiguous.

This protects against a second model-heterogeneity failure mode: **assurance formalism drift**, where a reviewer turns a lean semantic contract into form-filling bureaucracy.

### Consequence

The original live handoff was operationally safe because it already contained a local fail-safe: if the attached image was not visually inspectable, stop without retrieval. The generic fix is therefore to clarify the state vocabulary and the review criterion, not to retroactively declare that handoff invalid.
