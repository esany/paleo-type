## Governing requirement
`paleo-type` exists to help a non-specialist reliably unlock early-modern handwritten sources. A future structure is unacceptable if scholarly validity improves only by making the research state harder for a human project owner or reviewing scholar to understand.

Human usability here means **epistemic transparency**, not a polished UI.

## Review criteria
Verify that a non-specialist project owner can determine, without reading implementation internals:
- what source/locus is being worked on;
- what the current diplomatic text says in physical/source order;
- what is secure, uncertain, illegible, supplied or interpreted;
- what evidence supports consequential readings/identifications;
- which claims are archival, textual/palaeographic or historical;
- which gate/research state is active and what remains missing;
- what the exact next meaningful research action is;
- what has and has not received independent qualified human review;
- how to navigate from a result back to source/provenance/decision history;
- where future/deferred work is visible without confusing it with current research truth.

Verify that GitHub/other interfaces provide navigation rather than introducing duplicate status or truth stores.

## Human-in-the-loop quality criteria
- The user controls purpose, priority, source access/rights facts and consequential use/publication decisions.
- The user is not made responsible for specialist adjudication they cannot validate.
- Expert-review surfaces expose exact source loci, alternatives and evidence rather than requiring trust in AI summaries.
- Uncertainty is visible in the primary human-facing research output, not hidden in metadata.
- Human-readable outputs are derived from canonical research data where practical and do not require manual duplicate maintenance.

## Measures if a gap is demonstrated
Possible minimal measures:
- shorten the human reading path to README → active project/status → human-readable source view;
- add direct repository links/navigation instead of requiring path knowledge;
- generate deterministic diplomatic/review views from canonical data;
- simplify or consolidate methodology that a human must currently traverse without losing AI-facing rules;
- use GitHub labels/PRs/releases as presentation/navigation where useful, while keeping canonical truth in repository records;
- create targeted expert-review packets/views;
- introduce a dedicated UI only if repository-native views demonstrably fail the research-use case.

## Trigger
Review before a major structural refactor, when users/reviewers repeatedly need chat explanations to understand repository state, before bringing in external expert reviewers/collaborators, or before a public scholarly release.

## Definition of Done
- a new human can reach the active research result and understand its epistemic status with a short documented path;
- manuscript/source output is readable without understanding TSV schemas or agent prompts;
- uncertainty, editorial intervention and validation status are visible;
- a specialist can drill down to evidence/decision detail without losing source context;
- no human-facing view becomes a competing manual truth store;
- user decisions remain appropriate to the user's role rather than shifted specialist QA.

## Do not
Do not equate usability with dashboards, frontend frameworks or visual polish. Do not solve poor information architecture by creating another copy of the research state.

### User journeys to test in the vertical slice

**Owner:** `README/project → STATUS → source/locus → readable diplomatic witness → visible uncertainty → next action`.

**Historian/editor:** `witness line/span → source phenomenon/reading → provenance/evidence → decision/revision → related claim/variant if any`.

**Specialist reviewer:** `review queue/packet → exact locus/image reference → candidate alternatives → evidence/tests → unresolved limits → review status/result`.

### Interface decision

Repository-native Markdown/TSV + deterministic Markdown/HTML derived views are sufficient as the current target. There is no demonstrated need for a React/web application/dashboard. A dedicated UI may be reconsidered only if the vertical slice shows that these user journeys remain materially difficult after the derived views exist.

Overall: information architecture is **mostly sound**, but the missing derived witness and evidence drill-down are blocking the human-usability Definition of Done.
