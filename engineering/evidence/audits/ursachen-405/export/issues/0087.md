## Trigger

A parallel project/repository (`pflege-Arnshaugk`) uses a project system prompt to reduce quality variation caused by model/session/chat heterogeneity.

The question for `paleo-type` is whether a **small stable AI bootstrap layer** would add useful anti-drift / context-loading protection on top of the current canonical repository architecture, while avoiding a second truth store or stale master prompt.

Current working hypothesis:

```text
canonical repo truth
(GOVERNING_OBJECTIVE + AGENTS + applicable REQ-* + METHOD + PROJECT/STATUS + active Issue/evidence)
        ↓
small stable AI bootstrap
        ↓
#77/#86 bounded task/work-context assembly
        ↓
replaceable model / chat / session
```

The bootstrap, if justified, should govern **how a context rehydrates, respects boundaries, persists and hands off work**. It should not carry current project truth that already has a canonical owner.

## Analysis TODO once the fixture is available

Review the Arnshaugk prompt clause-by-clause against current `paleo-type` canonical owners and classify each substantive instruction as one of:

1. **already canonical here** — existing `GOVERNING_OBJECTIVE.md`, `AGENTS.md`, METHOD, REQ-* or maintenance rule already owns it;
2. **useful bootstrap invariant** — a short stable runtime/AI behavior rule that protects against model/session heterogeneity without duplicating project truth;
3. **derive/compose instead of copy** — task/role/project/evidence information that should be assembled from canonical state by #77/#86 rather than frozen in a static prompt;
4. **project-specific to Arnshaugk** — not transferable to `paleo-type`;
5. **problematic duplication / drift risk** — would create a second normative truth store, stale workflow state or hidden authority;
6. **genuine uncovered gap** — not currently protected by existing owners and worth routing through the existing requirement/governance process.

## Candidate bootstrap responsibilities to test

Do not assume these all survive the comparison. Test whether the minimum useful bootstrap needs to state only stable execution invariants such as:

- scholarly purpose/evidence precedes tooling convenience;
- repo/canonical state, not chat memory, owns consequential durable truth;
- load current applicable context before action;
- identify current role, authority and stop boundary;
- use deterministic tools for settled deterministic questions;
- do not force unresolved scholarly judgement into deterministic truth;
- do not make the human user a repository/process courier for deterministically retrievable state;
- when a repeatable problem lies outside the current role's competence, persist evidence and hand it to the correct Issue/owner rather than turning the domain chat into a generic process engineer;
- persist consequential work before handoff;
- do not self-certify another role's scholarly/specialist/human acceptance.
