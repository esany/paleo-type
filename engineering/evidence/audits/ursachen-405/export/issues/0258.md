## Human-Owner clarification — visible current work must be an explicit claim, not an opaque cursor token

Fresh basis: `main@ddf289fdf69f3827f287665a2a8c8e4d137fcbba`; `GOVERNING_OBJECTIVE.md`, `AGENTS.md`, `methodology/maintenance.md`, current #258, completed #257 result/current-state handoff, and the #247 context design were re-read before this write.

This is a **Human-facing context/UX requirement clarification inside the already admitted WP3 surface**, not a new D-016 admission and not a change to scholarly Project priority/state.

### Owner requirement

A generic control phrase such as `START CURRENT CURSOR` may be useful as an invocation, and the underlying currentness may legitimately be **relative to the active work context** rather than repository-global. However, the Human-facing resolved result must not remain a generic token, internal status code, Issue number, or unexplained shorthand.

The current/next work must be shown as a **clear, meaningful claim/action statement** that tells the Human what will actually be done and in which scope. Otherwise the user is effectively asked to work against a black box.

Required property:

```text
invocation may be generic
→ resolution may be context-relative
→ visible resolved cursor must be semantically explicit
```

Examples of the desired distinction:

```text
INSUFFICIENT
CURRENT CURSOR = WP3
CURRENT CURSOR = #258
CURRENT CURSOR = RESEARCH-02

ADEQUATE
Current work: Implement the Human/developer/Agent context views so the active work,
next action, authority boundary and deeper provenance are visible without Issue/audit replay.

or, in a scholarly context:
Current work: Test the Wolkenburg form/transmission and relationship questions against
real archival fixtures before proposing any shared model change.
```

The exact wording need not be stored as a second canonical truth. It may be a **derived human-readable rendering** of the actual bounded work owner/state, but it must expose enough semantics that the Human can understand the action before starting it.

### Context-relative, not opaque

Different chats/work contexts may resolve different current work at the same time. That is acceptable and desirable. The important distinction is:

```text
relative/scoped currentness = acceptable
opaque generic label = not acceptable as the Human-facing result
```

If the active work context is ambiguous, the resolver/view should expose that ambiguity rather than silently selecting one repository-global cursor.

### Generic-Fit with existing #247 design

This clarifies rather than replaces the existing #247 design. That design already requires the Human view to show `ACTIVE bounded work and next activity`, forbids making the Human decode unexplained internal status abbreviations, and separates Human strategic understanding from Agent execution packets.

WP3 acceptance should therefore include a Human-journey check that a generic current/start affordance resolves to an intelligible claim/action with scope and authority provenance, not merely an ID/status token. No new master command language or global `CURRENT_CURSOR` singleton is implied.
