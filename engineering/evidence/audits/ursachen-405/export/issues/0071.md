## Status / authority

**P1 planning / governance clarification only. No implementation, agent framework, orchestration layer, prompt registry or repository-wide role migration is authorized by this Issue.**

This Issue defines the smallest reusable role-charter and handoff pattern for AI-assisted chats/work contexts in `paleo-type` so that different conversations can specialize without fragmenting scholarly authority, canonical state, or development responsibility.

The immediate motivating case is the useful separation between:

- direct manuscript/source work;
- cross-disciplinary scholarly domain review and research sequencing;
- development / repository implementation;
- governance / material-change admission.

The solution must be generic and reusable for future comparable source projects and work contexts. It must not encode Knau-specific roles as universal architecture.

## Demonstrated problem

The repository already defines strong general AI guardrails, Human–AI division of labour, operational ownership, expertise routing, canonical ownership and material-change admission. However, when work is deliberately split across several chats or task contexts, the **specific role, authority boundary, required inputs, handoff target, return path and stop conditions of each context are not yet expressed through one reusable charter pattern**.

Without that pattern, a new chat/session may legitimately read the repository but still reconstruct its own role differently, for example:

- a source-work chat may drift into architecture design;
- a development chat may infer scholarly requirements from technical convenience;
- a domain-review chat may be treated as independent specialist validation when it is not;
- two chats may both assume canonical ownership of the same decision;
- implementation may pass tests without returning for scholarly adequacy review;
- a specialized chat may become dependent on remembered conversational instructions rather than durable repository rules.

This is a restartability / responsibility-routing gap, not evidence that a multi-agent system is needed.

## Governing principle

Different chats/work contexts may specialize, but they do **not** become independent authorities or truth stores.

Use the general pattern:

```text
GOVERNING OBJECTIVE + applicable requirements + canonical project/source state
        ↓
explicit role charter for current work context
        ↓
bounded work
        ↓
explicit handoff when another competence/authority is required
        ↓
return to canonical owner / project NEXT ACTION
```

A role charter must clarify responsibility without replacing the repository's canonical precedence hierarchy.

## Role-charter blueprint to derive

Derive the smallest reusable charter structure. It should cover only fields/questions that materially reduce ambiguity or session variance.

Candidate elements to test:

1. **Role / purpose** — what this work context exists to accomplish.
2. **Governing authority** — which canonical repository owners constrain it.
3. **Required context** — minimum repository/project/source/evidence state that must be loaded before acting.
4. **Primary competencies** — scholarly/technical domains this context is expected to apply proactively.
5. **Scope** — work it may perform directly.
6. **Decision / sequencing authority** — what it may determine from evidence and method without owner micromanagement.
7. **Write authority** — what classes of state it may update and what requires separate admission/review.
8. **Hard boundaries / non-goals** — especially where another role/domain remains authoritative.
9. **Stop / escalation conditions** — missing evidence, specialist uncertainty, rights/access, material architecture choice, publication consequence, etc.
10. **Handoff output** — minimum information the receiving context needs.
11. **Return handoff / acceptance** — how completed downstream work is checked and returned to research.
12. **Canonical-state rule** — chat/session state never becomes the sole durable owner.
13. **Validation status** — AI-assisted domain review vs independent qualified specialist validation remain distinct.
14. **Restartability test** — another capable session can reconstruct the role and continue from repository state without the old chat.

Do not freeze these as a schema until the analysis shows which are actually needed.

## Role / handoff concept — derived execution structure

The role-blueprint work now has real fixtures and should proceed as a **model-independent procedural scaffold**, not as an agent architecture.

### Governing principle

> **Standardize the path, not the scholarly outcome.**

Different capable models/researchers may reach different evidence-constrained scholarly judgements. The aim is to make the *route* less session/model dependent:

`canonical governing context → explicit role → bounded task → required checks → stop/escalation boundary → structured handoff → receiving role → return/review → canonical persistence / project NEXT ACTION`

No rule here implies `same evidence → same scholarly judgement`.

### Current role fixtures

- **#72 — Source Research**: direct manuscript/source work; establishes evidence-bound observations, readings/candidates, uncertainty and representation-loss findings; hands material cross-role questions to Domain Review.
- **#73 — Domain Review**: cross-disciplinary scholarly review, research sequencing, finding classification, generic requirement derivation, scholarship→Dev handoff and scholarly acceptance of returned technical work.
- **#74 — Development / Implementation**: implements only a bounded/admitted technical target, preserves the supplied scholarly/epistemic boundary, and returns implementation + tests/loss evidence to Domain Review.
- **#75 — Human Owner / Governance**: controls research purpose/priorities, owner-only access/rights facts, consequential publication/use, Governing Objective change and explicit material-change admission; is not a substitute specialist or Dev supervisor.
- **#76 — Qualified Independent Specialist Review**: consequence-scaled independent specialist validation from exact-source evidence; returns judgement/limits without silently mutating canonical state.

These are **functions**, not software agents or new truth owners. A chat/session may instantiate a function, but responsibility must be reconstructable from repository state without the old prompt.

### Procedural scaffold owner

- **#77 — model-independent work-context / handoff fragments** derives the smallest reusable procedural contract from the real role fixtures.

Candidate fragment family under test:

1. `ROLE CONTEXT`
2. `TASK START / RESUME`
3. `HANDOFF`
4. separate `RETURN / REVIEW` only if real use proves it materially distinct
5. owner-decision and specialist-review packets remain role-specific unless repeated use proves generic value.

No master prompt, prompt registry, workflow engine or agent runtime is presumed.

### Mandatory handoff logic

A role hands off when the next material action crosses its authority/competence boundary. The receiver must not need the sender's old chat to act correctly.

A material handoff should preserve, proportionally to consequence:

`FROM/TO role → trigger → canonical task/owner → evidence/input → established state → unresolved/not-investigated → exact request → may/must-not boundary → acceptance/return condition → canonical persistence`.

### Owner routing rule

Do **not** use the human owner as fallback when AI is uncertain.

Ask the owner only when the choice is genuinely owner-reserved. Technical ambiguity returns to Domain Review/Dev; specialist uncertainty returns to Source Research/Domain Review/Specialist Review as appropriate.

### Canonical-state rule

Chats and handoff fragments are transient work context. Durable consequential state remains in existing canonical owners. Templates, if later persisted, must instantiate current state rather than become parallel truth.

### Derivation / implementation sequence

The role/handoff work should now proceed in this order:

1. **Map existing canonical coverage** across Governing Objective, AGENTS, maintenance, AI governance and scholarly workflow; do not duplicate existing rules.
2. **Test role boundaries** using #72–#76 and remove fields/rules that add no material protection.
3. **Test real handoffs** across the directed interfaces defined in #77.

7. **Consider structural completeness checking only after repeated real use**. Any check may validate presence/routing/completeness fields, never scientific correctness.
8. If the resulting proposal materially changes research-system governance/automation semantics, use the existing D-016 admission path before implementation.

### Falsification criteria

This concept is too heavy or wrongly designed if it causes form-filling to displace source work, duplicates methodology, requires every role to live in its own chat, turns prompts into canonical state, routes routine work through governance, forces scholarly convergence, or still requires old-chat reconstruction for a receiving role to understand authority and next action.

## Generic blueprint refinement — evidence identity, reproducibility and actual availability are distinct

The Reg. Ii 5 Source Research handoff has now produced a real cross-session falsification finding for the role/handoff blueprint.

The generic procedural model must distinguish:

```text
IDENTIFIABILITY
what exact evidence object is intended

REPRODUCIBILITY
whether a derivative/working representation can be recreated from a verified parent

RESEARCH-READY AVAILABILITY
whether the current authorized role can actually open the evidence required for its next action
```

A role charter / handoff is incomplete for evidence-dependent work if it establishes only the first two while the third is silently assumed.

### Generic role-safe rule

When a role's current task requires direct evidence inspection, the work context must not infer `evidence available` merely because it has identifiers, provenance or a reconstruction recipe.

The current role either:

- can actually inspect the required evidence and proceeds; or
- records an evidence-access block and routes the access problem to the appropriate owner.

It must not substitute downstream data, previous transcriptions or contextual plausibility for missing direct evidence.

### Human-visible evidence principle

For visual source scholarship:

> **Identifiers secure reference; accessible images secure the work. Both are required.**

This principle is compatible with source images remaining outside the public repository where rights require it. The blueprint should standardize the required access state and handoff information, not prescribe one storage technology.

### Relationship to #78

#78 owns the generic source-intake / controlled evidence-availability derivation. #71 should absorb only the role/handoff invariant that a specialized context must know whether its required evidence is actually accessible now and where to route a block.

This further supports the governing principle `standardize the path, not the scholarly outcome`: evidence-access checks can be more model/session independent without constraining the resulting scholarly judgement.

## Clarification: no chat may become a knowledge monopoly

The role/handoff blueprint should make one project-level principle explicit:

> **No specialized chat/work context may become the sole holder of consequential research knowledge, workflow state, authority, or restart instructions.**

The target is the highest practical degree of **AI/model/session independence** compatible with evidence-constrained scholarship. Specialized chats are replaceable work contexts, not durable knowledge owners.

Operational consequences:

- every role must be reconstructable from canonical repository state + controlled evidence + its durable role/task instructions;
- consequential findings, uncertainty, decisions, blockers, next actions and handoff state must return to their canonical repository owners rather than remain only in conversation history;
- a replacement chat must not require replay of an old chat to know what to do;
- handoff prompts may accelerate resumption, but must not be the sole source of truth;
- different capable models/sessions may reach different legitimate scholarly judgements, but none acquires canonical mutation authority merely by being the active chat;
- role separation such as `#72 Source Research → #73 Domain Review` is for context/competence purity, not to create isolated knowledge silos;
- downstream roles should retrieve persisted upstream results themselves instead of making the human user manually shuttle already-canonical knowledge between chats;
- if a consequential result cannot be reconstructed without the originating chat, that is a restartability/governance defect to be corrected in the canonical workflow.

This operationalizes the existing restartability and canonical-state requirements; it is not a new agent architecture or prompt registry.
