## Central bug hypothesis

Repeated work has shown a dangerous pattern:

```text
large real system problem
→ valuable audit / diagnosis
→ strong pressure toward "smallest", "lean", "minimal" correction
→ narrow local fix
→ local PASS / apparent closure
→ underlying integration / maintainability problem remains
→ new audit
→ another narrow correction
→ repeated gap between stated quality bar and operational reality
```

The suspected bug is **not** that lean engineering is wrong.

The suspected bug is that **minimality has too often been treated as an input constraint on solution design instead of a post-sufficiency optimization criterion**.

Required correction of the reasoning order:

```text
1. understand the demonstrated problem completely
2. derive all necessary solution properties
3. determine the architecture / process / repository structure that satisfies them
4. prove that the problem is actually closed
5. only then remove complexity that is demonstrably unnecessary
```

Not:

```text
1. search for the smallest intervention
2. accept whatever subset of the problem it can cover
```

Working principle to test:

> **Sufficient architecture first; simplify without loss second.**
>
> Quality, completeness, maintainability, provenance and epistemic safety are constraints. Complexity is a cost function, not a hard size limit.

---

## Coupled lifecycle / closability concern

A second symptom may belong to the same root cause: some system/planning/audit Issues can accumulate current state, history, decisions, evidence and successor concerns over long periods instead of reaching a bounded completion and handing off cleanly.

This creates risks of:

- current state mixed with historical layers;
- Issue chronology becoming part of the runtime/context contract;
- ever-growing owner surfaces that a Fresh Reader must replay;
- inability to distinguish active work from retained evidence;
- hidden continuation semantics;
- repeated extension of an old owner because creating/closing the right bounded owner is unclear;
- "finished locally but never finished structurally" work.

`paleo-type` #225 is an important internal fixture because it has an explicit whole-system Definition of Done and can in principle close. `Wissensarbeit` #7 is relevant only as **comparative evidence**, not authority over this repository: it is a long-lived audit/planning owner that has been reused and extended across later work. The audit must determine which owner/lifecycle pattern actually supports maintainability and closure, rather than assuming either model is correct.

## Questions to answer

### 1. Is this one structural bug or several independent defects?

Test at least two competing hypotheses:

**H1 — Local-fix hypothesis**

The observed problems are mostly independent. Repairing stale/current pointers, decision records, supersession, derived views and specific owner surfaces is sufficient; no larger repository-architecture change is required.

**H2 — Structural-architecture hypothesis**

The observed problems are coupled symptoms of a missing or under-operationalized repository knowledge/lifecycle architecture. Local fixes would merely move integration/reconstruction work to another AI/human context.

Do not prefer H1 because it is smaller. Do not prefer H2 because it is more comprehensive. Prefer the hypothesis that explains the evidence and closes the demonstrated failure families.

### 2. Where has "lean / smallest / minimal" caused under-solving?

Inspect historical and current cases where:

- an audit found a broad failure;
- the response deliberately narrowed to a minimal correction;
- the correction passed locally;
- the same root burden later reappeared under another surface.

Distinguish legitimate scope control from solution truncation.

### 3. What does an adequate solution actually need?

Derive necessary properties **before** choosing solution size or artifact count.

Potential properties to test, not pre-authorized design decisions:

- explicit context/lifecycle layers;
- current-vs-historical separation;
- durable decision records / ADR-grade rationale where needed;
- explicit supersession/current pointers;
- provenance relations across decision/evidence/review/implementation/result;
- rebuildable operational read models;
- typed owner roles;
- bounded planning/execution state;
- event/history vs current-state separation;
- generated indexes / derived views;
- repository reorganization or migration;
- stronger executable contracts/tests;
- larger architectural change if the evidence requires it.

A larger solution is not a failure if it is required. A smaller solution is not a success if it leaves the root problem for AI/human reconstruction.

### 4. Which work-owner structures are allowed to be long-lived?

Classify owner types and expected lifecycle, for example:

- durable constitutional/normative owner;
- durable accepted decision log;
- bounded analysis/audit issue;
- bounded work package;
- programme owner;
- current execution cursor;
- historical evidence;
- derived navigation/read model.

For each relevant type determine:

- what makes it legitimately long-lived;
- what completion means;
- what must happen before closure;
- where history goes after closure;
- how a successor is selected without silently extending the old owner;
- how current state is found without replaying all history.

The result must make it possible for bounded structures to **finish and close** without losing provenance or continuity.

### 5. Does #225 itself satisfy the desired lifecycle model?

Audit #225 as a fixture, not as presumed best practice:

- Can its Definition of Done be evaluated against current evidence?
- Which parts are complete, open, or superseded?
- Is the Issue still the appropriate active owner for the unresolved system problem?
- Can it close cleanly when its acceptance condition is met?
- What durable decision/history remains after closure?
- Would a Fresh Reader still understand the system without treating the closed Issue thread as an active state store?

Do **not** close or rewrite #225 as part of this Issue without separate evidence/authority.

### 6. Does an ever-growing planning owner create a second failure mode?

Use `Wissensarbeit` #7 only as comparator evidence:

- what information has accumulated there;
- which later work still depends on reading its history;
- whether current planning authority is cleanly separated from historical audit evidence;
- whether bounded child/work issues can close while #7 remains a durable owner;
- whether that pattern is actually sustainable or merely shifts the knowledge monopoly into one permanent Issue.

No cross-repo mechanism is imported by analogy alone.

---

## Anti-truncation rule

For every proposed correction or architecture class, explicitly answer:

1. Which root failure(s) does it close?
2. Which demonstrated failure(s) remain?
3. Does the remaining burden disappear, or is it merely transferred to AI/human reconstruction?
4. What evidence shows that the solution is sufficient?
5. What complexity can be removed **after** sufficiency is shown?

A proposal that is attractive mainly because it is smaller is insufficient evidence.

---

## Anti-overengineering rule

Adequacy-first does **not** authorize speculative infrastructure.

Do not build a registry, ontology, event store, workflow engine, planner, new state database, directory hierarchy, ADR framework or other structure merely because it could model the problem.

Each component must trace to a demonstrated failure or required solution property.

The burden of proof is symmetric:

- **too small** must not leave the problem unresolved;
- **too large** must not add unsupported machinery.

---

## Required analysis output

Produce a repository-backed audit/decision surface with at least:

1. **Failure-family map** — recurring symptoms and concrete evidence.
2. **Causal model** — which symptoms share a root cause and which do not.
3. **Owner/lifecycle map** — current owner types, clocks, completion/closure semantics, history/current separation.
4. **Adequacy requirements** — properties any acceptable solution must satisfy, independent of size.
5. **Competing architecture classes** — including local repair and larger structural options where justified.
6. **Falsification matrix** — evidence for/against each class.
7. **Closure model** — how programmes/audits/work packages finish, preserve history and hand off without immortal owner growth.
8. **Fresh-context test** — can a capable maintainer reconstruct current authority/state/decision history without old chat or issue archaeology?
9. **Complexity justification** — every retained component has a demonstrated purpose; every removed component is proven unnecessary.
10. **D-016 disposition surface if material change is warranted** — exact scope, affected owners, migration, tests, non-goals and acceptance criteria.

## Definition of Done

This Issue may close when all of the following are true:

- the central causal hypothesis has been explicitly dispositioned (`local defects`, `structural architecture gap`, or a bounded mixed result);
- the "minimality / lean" bias has been tested against concrete repository history rather than asserted abstractly;
- owner/lifecycle/closability semantics are explicit enough to distinguish durable owners from bounded work owners;
- the analysis identifies how current state and historical evidence remain separately recoverable after work closes;
- any proposed solution class is shown to be **problem-adequate**, not merely small;
- unnecessary complexity is identified only after adequacy is established;
- if material repository/METHOD/owner changes are warranted, a precise D-016 decision surface exists for separate Human-Owner admission;
- no new scholarly Project priority or manuscript `NEXT ACTION` has been manufactured.

At closure, preserve the accepted causal result/decision in its durable canonical owner as appropriate. Do not keep this Issue open merely as a permanent memory store.
