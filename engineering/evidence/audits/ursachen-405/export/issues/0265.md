# Issue #265: [BUG] active_scope cannot represent “no selected scope” without prose sentinel

## Status / authority

**BUG / ANALYSIS RECORD ONLY. No Project-scope contract change is authorized by this Issue.**

## Demonstrated inconsistency

`methodology/project-lifecycle.md` explicitly allows a Project's current scope to remain **unset** until an owner-grounded question activates it.

At the same time:

- `templates/project/project.yml` marks `active_scope` as required;
- `corpus/source-contract.json` requires a non-empty `active_scope` key;
- current Projects therefore encode “no scope selected” as natural-language text such as `No owner-selected active scholarly scope is currently recorded ...`.

The model is therefore using a prose sentence as a sentinel for a structured absence/state.

## Why this is a bug

The following states are semantically different but currently share one free-text field:

1. no current scholarly scope selected;
2. whole Project root is the current scope;
3. one bounded locus/section is current scope;
4. previous scope completed but retained as history;
5. scope exists but is temporarily blocked;
6. descriptive prose about prior work while current scope is none.

For a human reader this can be understood. For deterministic tooling, migration, restart logic and AI context, the distinction depends on parsing English prose.

That creates several risks:

- a future agent treats a sentence describing “no scope” as an active scope;
- a stale completed scope remains embedded in the field and appears current;
- changes in wording break derived tooling/tests;
- a new Project is forced to invent text solely to satisfy non-empty validation;
- whole-source survey and “no selected research target” cannot be cleanly distinguished.

The Wolkenburg fixture makes the last distinction material: an archival item may be 50–300 pages and require an initial whole-root survey because relevant sections cannot be identified in advance. That is **not** the same state as “no current scope selected.”

## Kommentar 5984950521 · 2026-10-04T22:08:02Z · esany

## Analysis result — separate scope state from scope description

Fresh comparison of `project-lifecycle.md`, the Project template, current Project YAMLs, `project_context.py` and its regression tests confirms that this is not only a wording problem. Current tests explicitly look for English prose such as `No owner-selected active scholarly scope is currently recorded`, and Reg. Ii 4/5 currently mix completed historical work, research results, non-goals and the absence of a current scope into the same `active_scope` scalar.

### Stable semantic distinction

The Project model needs to distinguish at least these three **current** states without parsing prose:

1. **none** — Project exists, but no current scholarly scope/target has been selected;
2. **whole-root** — the entire `project_source_id` Source root is the current working/survey scope;
3. **bounded** — a narrower Source/locus is the current working scope.

Historical/completed scopes, prior findings and non-goals are not current scope state. They belong in the Project's research/history/STATUS surfaces as applicable.

For Wolkenburg this resolves the immediate ambiguity: when a 50–300 page independent Archivale must be examined end-to-end because relevant sections are unknown, the truthful state is **whole-root active survey scope**, not `none`.

### Smallest target representation

The current single free-text `active_scope` scalar should not carry both state and description. The smallest robust target is a separate simple machine-readable scope-state distinction plus a scope description/locus only when needed. A lean implementation can keep this in scalar Project metadata; no workflow engine or nested schema is required.

Conceptually:

- `scope state = none` → no active scope description required;
- `scope state = whole-root` → current scope derives from `project_source_id`; do not duplicate the root as prose;
- `scope state = bounded` → explicit bounded scope/locus is required.

Exact field/token names are implementation detail and are **not admitted by this comment**.

### Consequences for existing behavior

- `NEXT ACTION` remains separate and owned by `STATUS.md`; an active scope does not manufacture a next action.
- research functions remain separate; neither `project_source_id` nor scope state creates `principal`/comparison/etc.
- gate claims remain scope-bound under `research-gates.md`.
- `project_context.py` should expose the structured state rather than tests inferring `none` from a specific English sentence.
- existing Reg. Ii 3/4/5 scope/history wording would require a loss-checked migration: preserve historical work/result text, but remove it from current-scope semantics.

### Relation to #267

`whole-root` says **what is currently in scope**. It does not say **which portions have actually been inspected**. That progress/evidence fact is separately owned by the inspection-coverage concept in #267.

### Admission classification

Unlike #264's title drift, this changes a shared Project state invariant and requires coordinated changes to contract/template/context/tests plus migration of current Projects. It is therefore a **D-016 material concept**, to be admitted together with #267 rather than patched independently.

**Disposition:** semantic analysis resolved; implementation remains blocked on the combined #265/#267 material admission.

## Kommentar 5985664898 · 2026-10-04T23:38:44Z · esany

## Scope correction — `whole-root` is inspection domain, not Wolkenburg research scope

The Human-Owner clarification recorded in #270 falsifies one part of my previous analysis in this Issue: the initial Wolkenburg state must **not** be described as `whole-root active survey scope` merely because the whole archival unit may need to be inspected for relevance.

### Correct requirement

Keep these independent:

1. **Project root** — the independent Archivale referenced by `project_source_id`;
2. **discovery/inspection domain** — what must be examined to discover relevant material; this may cover the whole root;
3. **active scholarly research scope** — the currently relevant Sources/loci, potentially **multiple, disjoint and evolving** as inspection proceeds;
4. historical/completed scope;
5. `NEXT ACTION`.

A truthful state can therefore be:

```text
root: Archivale X
inspection: images/pages 1–80 examined, 81–135 open
research scope: Document A + Document C/section 2 + Transcript D + Register E/entries x–z
excluded after inspection: Document B
unresolved: Document G
```

So the previous conceptual enum `none | whole-root | bounded` is **withdrawn as the preferred target model**. It collapses two axes: breadth of inspection and scholarly selection. `bounded` is also too easily read as one contiguous range, whereas the real scope can be a set of Sources/loci distributed through several levels of the documentary structure.

This does **not** resolve the physical representation. Do not choose a replacement enum, YAML shape or table yet. The durable requirement is that current scholarly scope be representable without being confused with Project root, inspection coverage, history or work cursor.

Any shared Project-contract/schema change remains material under D-016. #267 owns the independent inspection-coverage side; #270 owns the integrated concept.
