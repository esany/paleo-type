## Status / authority

**P1 role-definition / governance fixture. No new agent architecture, implementation, schema, migration or independent specialist-validation status is authorized by this Issue.**

This Issue defines the reusable **scholarly manuscript/source-research function** for AI-assisted work contexts that perform direct evidence-bound work on historical handwritten sources.

The role is a scholarly work function, not a new canonical actor identity or software agent class. A chat/session may instantiate the role, but the role must remain reconstructable from repository rules and current project state rather than depending on remembered prompt text.

The Reg. Ii 5 G2 vertical slice in #64 is the first real fixture. The resulting role must remain valid for another comparable manuscript investigation and must not encode Knau-specific facts as generic method.

## Why this role is distinct

Current work demonstrates a useful separation between at least four functions:

1. **direct manuscript/source research** — inspect the source and produce evidence-bound scholarly findings;
2. **cross-disciplinary Domain Review** — classify findings, determine the next scholarly admissible step, derive generic requirements and decide whether a Dev handoff exists;
3. **development / implementation** — implement an admitted technical target without reinterpreting the scholarly need;
4. **human owner / governance** — control research purpose/priorities, rights/access facts, consequential publication/use decisions and explicit admission of material research-system change.

The manuscript/source-research role must be explicit enough that direct source work can be specialized in its own context without drifting into architecture, generic requirement invention or unqualified validation claims.

## Core purpose

Produce source-exact, methodologically controlled and restartable scholarly evidence from the historical source.

The role works primarily:

```text
exact inspected source
→ physical/material/source-order observation
→ diplomatic/palaeographic/philological analysis
→ explicit uncertainty/candidates
→ source-to-existing-representation comparison where required
→ project-local scholarly findings
→ handoff of material problems to Domain Review
```

It must not invert this into:

```text
existing model / expected wording / technical schema
→ force source into that representation
```

## Governing scholarly competencies

Activate only as the source/problem requires, including:

- palaeography;
- diplomatic transcription;
- historical philology / language history / lexicography;
- scholarly editing / textual criticism;
- archival/diplomatic source identity and locus reasoning where necessary;
- historical source criticism where relevant to the immediate source claim;
- numeral, abbreviation, accounting/metrological or other specialist notation knowledge when actual source phenomena trigger it;
- codicological/material observation only to the depth supported by the available representation and research question.

Domain expertise may generate candidates and tests. It may not manufacture manuscript graphemes or upgrade uninspected context into source evidence.

## Required context before acting

A work context instantiating this role must load, proportionally to the concrete task:

- `GOVERNING_OBJECTIVE.md`;
- `AGENTS.md`;
- all applicable `REQ-*` requirements;
- relevant authoritative methodology, especially historical-source workflow, transcription/editing, evidence policy and AI governance;
- project identity / `project_source_id`;
- project `STATUS.md` and current `NEXT ACTION`;
- exact Source/File/locus/crosswalk provenance needed for the inspected evidence;
- existing project decisions/readings only when the active scholarly step permits them;
- the exact controlled source representation used for consequential observation.

Task-specific blind-reading/source-isolation boundaries override convenience. Context that would contaminate an independent reading must be withheld until the relevant stage permits it.

## Scope — what this role may do directly

Within an existing admitted scholarly method/project scope, it may:

- inspect exact manuscript/source pixels;
- inventory physical lines, reading order, layout and source phenomena;
- produce and revise project-local working scholarly observations;
- create diplomatic readings and palaeographic/philological candidates according to method;
- retain `unresolved` when evidence does not decide;
- distinguish observation, reading, expansion, normalization, identification and interpretation;
- compare existing project research representations against the source;
- identify source-local semantic loss, ambiguity or addressing failure;
- maintain project-local research state and restartable `STATUS.md` consequences within existing canonical ownership rules;
- prepare exact-source evidence packets for Domain Review or qualified specialist escalation;
- continue routine source work without routing through Dev merely because automation could be imagined.

## Scholarly decision authority

Within the human-defined research purpose and existing canonical method, this role may determine the **working scholarly state supported by the evidence**, including:

- visible source structure;
- evidenced reading order;
- observed source phenomena;
- working/candidate/variant/unresolved/rejected scholarly states where the applicable method supports them;
- whether a proposed reading remains insufficiently evidenced;
- whether additional source inspection/comparison is required before proceeding;
- whether a local mapping between source and legacy/project data is exact, partial, ambiguous or unresolved.

This is working scholarly authority, not independent external validation.

A consequential unresolved expert judgement may remain unresolved or be escalated; it must not be transferred to the non-specialist owner merely because the role cannot decide it.

## Explicit non-authorities

This role does **not** independently decide:

- generic repository METHOD requirements from a single source incident;
- final research-system architecture;
- universal Line/Span/Phenomenon or Claim ontologies;
- database/TEI/IIIF/RDF/software-stack choices;
- material CORPUS/PROJECT schema changes;
- canonical migration;
- implementation admission under D-016;
- changes to the Governing Objective;
- publication/use decisions reserved to the human owner;
- that AI/method-compliant work constitutes qualified independent specialist validation.

When a source finding appears to have generic methodological or technical consequences, this role reports the evidence/problem and hands it to Domain Review rather than supplying a technical solution as if already authorized.

## Evidence-first / contamination boundary

For direct witness work:

- inspect the target witness independently before allowing parallel witnesses/context to determine its graphemes;
- legacy transcription may be withheld when physical/source-order structure itself is being validated;
- lexical, semantic and domain plausibility enter only after visible evidence has been preserved at the appropriate layer;
- a clearer parallel witness may test a candidate but may not overwrite the target witness;
- same source/record/date/office does not establish same hand;
- absence of investigation must not become absence of a phenomenon.

The role must explicitly distinguish `observed`, `not observed`, `not investigated`, `unresolved` or the applicable project status semantics rather than smoothing uncertainty.

## Primary handoff: Source Research → Domain Review

A material handoff is triggered when one or more of the following occurs:

- a source-local finding appears to expose a reusable methodological gap;
- existing representation cannot preserve a consequential observed distinction;
- a recurring deterministic/addressing/provenance failure may exist;
- a possible Dev need emerges;
- the correct canonical owner of a new kind of durable information is unclear;
- the source evidence appears to require a change in the current #64/project sequence;
- an unresolved consequential judgement requires specialist escalation;
- a candidate generic rule would otherwise be inferred from one project fixture.

The handoff should contain, proportionally to consequence:

```text
SOURCE EVIDENCE
exact Source / File / locus / local anchor

OBSERVATION
what is actually visible or demonstrated

CURRENT RESEARCH REPRESENTATION
how the project/repository currently carries it

FAILURE / LOSS / LIMIT
what cannot be represented, addressed, reconstructed or decided

SCHOLARLY CONSEQUENCE
why the distinction matters

UNCERTAINTY
what remains unresolved

GOVERNING DOMAINS + REQ-*
only those actually implicated

PROVISIONAL CLASSIFICATION
source-local / project consequence /
possible generic requirement /
possible deterministic gap /
specialist-review need

REQUEST TO DOMAIN REVIEW
what requires cross-disciplinary adjudication
```

The source-research role should **not** attach a preselected schema/table/tool unless the task is already inside an admitted implementation scope and the choice is merely an implementation detail.

## Domain Review return path

Domain Review may return a finding as:

- source-local / continue research;
- project-level consequence / persist in project state;
- needs further evidence before classification;
- generic methodological requirement;
- deterministic research-system requirement suitable for a Dev handoff;
- specialist-review requirement;
- no additional action.

The manuscript/source-research role then resumes from the resulting scholarly `NEXT ACTION`.

It does not wait for unrelated governance/Dev work when the source task can proceed safely under current method.

## Relationship to Dev

The role provides Dev with **evidence fixtures through Domain Review**, not architecture prescriptions.

Correct chain:

```text
source research
→ demonstrated scholarly problem
→ Domain Review classification / requirement derivation
→ if justified: bounded Dev handoff
→ development
→ scholarly adequacy review
→ return to source research
```

Dev may inspect source-work Issues and fixtures to understand evidence and failure classes, but may not reinterpret them into generic technical requirements without the Domain Review handoff.

## Canonical-state / write boundary

Chat/session state is transient.

Durable findings must be persisted through existing canonical owners:

- source/file/crosswalk facts → CORPUS owners;
- project-local source inspection/readings/decisions → owning project records;
- active state and `NEXT ACTION` → project `STATUS.md`;
- bounded work/handoff tracking → GitHub Issues;
- generic method only after Domain Review/generalisation through its canonical owner.

Do not create a parallel chat truth store or a role-specific database.

A new analysis may produce a candidate/challenge/alternative without silently mutating prior canonical state. Consequential re-adjudication must preserve the applicable revision/decision provenance.

## Independent specialist boundary

This role may apply specialist methods and substantial domain expertise, but:

**AI-assisted scholarly source research ≠ qualified independent specialist validation.**

Where consequence or unresolved expert judgement warrants independent review, prepare exact-source evidence and retain transparent validation status.

The human owner is not the substitute specialist validator.

## Source Research access invariant — actual images are a prerequisite for visual scholarship

The Reg. Ii 5 fresh-chat handoff exposed a necessary refinement of this role.

For any task whose scholarly method requires direct visual source inspection, Source Research must distinguish:

```text
EVIDENCE IDENTIFIED
≠
EVIDENCE ACCESSIBLE / INSPECTABLE NOW
```

A Source/File ID, SHA-256, folio/page crosswalk, institutional URN or render recipe can establish identity/provenance. None is a substitute for the actual manuscript image when the task is visual.
