## Korrektur nach Human-Owner-Einwand: lokale Minimalreparatur ist **nicht** das Lösungsziel

Der Human Owner weist zu Recht auf ein bekanntes Bugmuster hin: Wenn nach einer systemischen Fehleranalyse wieder auf die „kleinste lokale Lösung“ optimiert wird, kann genau die bekannte Kette reproduziert werden:

`systemischer Fehler → lokaler Patch → lokaler PASS → gemeinsame Ursache bleibt → nächster Incident`.

Die Formulierung im vorigen Result-Kommentar („smallest concept“, „acquisition-local repair appears capable“) ist deshalb **als Lösungsdisposition zu schwach**. Sie bleibt als Befund über einen möglichen Implementierungsbaustein erhalten, darf aber nicht als Abschluss der Root-Cause-Lösung gelesen werden.

### Reframed solution objective

Für die Execution/Control/Runtime-Familie (#276/#277, mit #271 als konkretem Fixture) ist der Zielzustand nicht „`savesax` läuft wieder“, sondern eine **outcome-preserving execution contract**-Semantik, die den gemeinsamen Fehlermechanismus an der Stelle verhindert, an der er entsteht.

Die Lösung muss mindestens folgende Eigenschaften **zusammen** herstellen:

1. **Human intent / outcome remains controlling.** Technische Zerlegung in Tool, Modus, Runtime, Storage oder Retry darf den autorisierten Outcome-Cursor nicht ersetzen.
2. **Read/mutation boundary is explicit.** Informations-/Statusabfragen sind nicht mutierend. Ein neuer Top-Level-Run nach terminalem Zustand ist eine neue Konsequenz, nicht impliziter Retry.
3. **Capability routing is internal but bounded by authority.** Der Human wird nicht zum Tool-/Runtime-Orchestrator; fehlende Capability bleibt action-local und erzeugt keine neue Aufgabe oder Priorität.
4. **Execution fitness is proven before consequential side effects.** Runtime-Auswahl muss für den konkreten Vorgang Persistenz, Recovery/Resume, Failure containment, Observability und relevante Stop/Cancel-Kontrolle erfüllen; bloße technische Verfügbarkeit genügt nicht.
5. **Long-running operations have reconstructable durable control state.** Für einen consequential external operation muss ein frischer Kontext feststellen können: welches Outcome autorisiert ihn, welcher Vorgang läuft/ist terminal, welche Side Effects sind bereits erfolgt, wo liegt restartbarer Fortschritt, welche Kontrolle ist verfügbar, was bedeutet `complete`.
6. **Failure returns to the same authorized outcome.** Ein lokaler Tool-/Netz-/Runtimefehler führt zum kleinsten Reparaturpfad bzw. Resume derselben Operation; er autorisiert weder einen neuen Run noch Infrastrukturarbeit als Ersatz-Outome.
7. **Truthful status is mechanically/semantically separated.** `planned`, `running`, `partial/restartable`, `failed`, `cancelled`, `technically complete`, `preserved/secured` und scholarly/owner acceptance dürfen nicht ineinander gelaundert werden.
8. **Start/control semantics are consequence-scaled.** Eine langlebige externe Aktion darf nicht still aus einem Kontext gestartet werden, dessen relevante Stop-/Containment-Grenzen unbekannt sind. Perfekte universelle Symmetrie ist nicht verlangt; die reale Kontrollgrenze muss aber vor Start Teil der Fit-Entscheidung sein.
9. **Assurance tests the composition, not only the adapter.** Regressionen müssen mindestens status→no-mutation, terminal-failure→no implicit rerun, interruption→durable/restartable progress, control-limit reporting und einen materially different non-SStA fixture abdecken.
10. **Owner-local implementation remains subordinate to the shared contract.** `savesax`/PR #273 kann ein Implementierungsfixture sein; ein lokaler Fix gilt aber erst dann als systemisch ausreichend, wenn die gemeinsamen Eigenschaften am relevanten shared owner operationalisiert und cross-fixture falsifiziert sind.

## Bugfix whole-system control contract — parent mode

Human-Owner feedback: Bugfixing itself must operate from an **overordinate whole-system mode** so that it does not reproduce the same failure pattern it is meant to repair. In particular, `smallest fix` is not the governing optimization target. The governing target is the **smallest complete solution that demonstrably removes the failure family while preserving authority, restartability and the Human outcome**.

This comment refines #280 as the parent control surface for the execution/control/runtime bug family. It is work/audit metadata only; it does not itself amend METHOD or admit implementation.

### Parent target image

A bugfix programme is successful only when the demonstrated failure mechanism is no longer able to recur silently within the admitted scope:

- Human intent / desired outcome remains the governing cursor through technical decomposition;
- support infrastructure cannot gain task authority merely because it is available;
- read/status actions cannot become new top-level mutations without authority;
- resource/capability failures remain action-local unless a real dependency authority says otherwise;
- long-running consequential actions execute only in a runtime fit for their persistence/restart/control needs;
- partial/technical/CI states cannot be laundered into stronger completion/secured/scholarly states;
- a fresh context can reconstruct the operation/fix/result without old chat;
- local fixes return to the parent failure family and are not treated as whole-system closure by themselves.

### Definition of Ready — every thematic bugfix package

A child package is ready to enter implementation/admission only when all applicable meanings are explicit and evidenced:

- [ ] **demonstrated failure** and reproduction/evidence pointers are linked;
- [ ] **failure family / root-cause relation** is stated, including whether the item is cause, symptom, amplifier or unrelated;
- [ ] **existing canonical/system owner** and applicable Requirements/decisions are freshly resolved;
- [ ] **clear target image** states what behaviour will be true after the fix, independent of implementation choice;
- [ ] **bounded scope and non-goals** prevent local convenience from expanding architecture;
- [ ] **dependencies/prerequisites** and their actual authority are explicit;
- [ ] **fix locus** is chosen only after Generic-Fit against existing owners (`fuse | refine | reframe | supersede | conflict | reject | defer`);
- [ ] **D-016/admission state** is explicit for any material shared-system change;
- [ ] **regression/falsification fixtures** test the failure mechanism, not just the selected implementation;
- [ ] **cross-fixture strategy** exists where genericity is claimed;
- [ ] **whole-system return path** to #280 and any existing programme owner (#244 where applicable) is defined;
- [ ] **completion semantics** distinguish local technical PASS from package DoD and parent closure.

If these are not true, the package is not ready for implementation even if a plausible patch is obvious.

### Definition of Done — every thematic bugfix package

A child package is done only when:

- [ ] the implemented change satisfies the package target image, not merely the immediate incident;
- [ ] all deterministic regressions/falsification fixtures pass for the intended reason;
- [ ] at least one materially different fixture supports Generic-Fit when the fix is promoted as generic, or the result remains explicitly owner-local;

- [ ] no new parallel truth store, Human orchestration burden or hidden platform dependency was introduced;
- [ ] fresh-context restart can reconstruct the changed behaviour, authority, limits and remaining residuals;

- [ ] the result is returned to #280 and to #244/#270/other existing owner only where actually applicable;
- [ ] any local PASS is explicitly checked for whole-system consequence before closure;
- [ ] no unresolved in-scope root cause is silently converted into a non-goal;
- [ ] Human/technical/scholarly acceptance boundaries remain separate.

### Bugfix anti-regression mode

Before selecting or implementing a fix, explicitly test the fix process itself against the known bugwave:

1. **Local-patch trap:** are we fixing the visible incident while leaving the demonstrated parent mechanism intact?
2. **Tool-first trap:** did a currently available tool/runtime become the design merely because it is available?
3. **Smallest-mechanism trap:** are we minimizing code/structure at the expense of a complete solution to the Requirement?
4. **Infrastructure drift:** did the support mechanism displace the Human/research outcome?
5. **PASS laundering:** are CI/unit/local results being presented as package or parent completion?
6. **Owner duplication:** are we creating a new owner/bugwave instead of using the established one?
7. **Scope laundering:** are we smuggling a material new architecture into an already admitted package?
8. **Human-burden regression:** does the fix make the Human choose routing, sequencing, internal tools or technical recovery steps that should be derivable?
9. **Restartability regression:** can a fresh context tell exactly what changed, why, what is complete and what remains?
10. **Cross-fixture falsification:** if the fix is claimed generic, would it still work when the original `savesax` fixture disappears?

A negative answer on an applicable point blocks package closure and may require re-entering analysis/requirements/concept rather than layering another local patch.

Parent closure requires evidence that the execution/control/runtime failure family is reduced at the system level: child DoDs passed, incident dispositions are explicit, cross-fixture evidence supports every generic claim, no compatible residual was orphaned from #244, and the Human can observe/control/restart the resulting behaviour without understanding internal runtime/tool topology.
