## Purpose

Evaluate whether HTR can restore **candidate-generation breadth** for difficult handwritten loci without weakening the repository's evidential rule that a diplomatic promotion must be carried by the target witness itself.

This is a tooling/research-support spike, **not** authority to change the current #123 reading method, canonical transcription owners, Project scope, gates, or source relationships.

## Why this is needed

Current #123 has become deliberately narrow after earlier failures from silhouette guessing, semantic completion and cross-witness contamination. That protection is valid, but the next Reg. Ii 5 work on `62v` contains long unresolved spans where a target-first graphical discriminator can be hard to formulate from unaided inspection alone.

Desired separation:

```text
broad machine candidate generation
→ human/AI palaeographic testing against exact target pixels
→ promotion only if target graph carries the reading
```

HTR output is therefore **hypothesis/test input**, never transcription evidence by itself.

## Benchmark design

Use a small, bounded set of exact Reg. Ii 5 controls rather than immediately processing the full source.

Include:

- already resolved or partially resolved difficult controls from #123, so performance can be evaluated against target-supported outcomes;
- examples such as `62r-L17` (`sonsten`), `62r-L19` (`wolff`), `62r-L20` (`dem gemeinswalde`), and `62v-L11` (`acker / zu seinem steinbruch gemacht`) where useful and available;
- unresolved F1 material `62v-L01`–`L06` only after exact File/SHA/crosswalk and current-context pixels are available;
- a mix of prose, abbreviations/signs and difficult line conditions rather than only easy words.

For every tested engine/model record:

- exact software/model/version and license;
- exact source/file/locus input;
- whether line segmentation was supplied or generated;
- raw output without silent normalization;
- whether the target-supported control reading appears among useful candidates;
- false fluent completions / normalization errors;
- runtime and local resource burden;
- any external upload/data-rights consequence.

## Evaluation criterion

The useful metric is **candidate utility**, not page-level OCR vanity accuracy.

A tool is useful if it repeatedly proposes graphically testable candidates or partial sequences that help formulate a discriminator for difficult loci while leaving final reading authority with the manuscript pixels.

Prefer measures such as:

- control-reading recall / top-k usefulness;
- useful partial grapheme recovery;
- hallucinated fluent completions;
- segmentation failure rate;
- effort saved versus manual candidate generation.

Do not promote an HTR reading merely because multiple models agree. Multiple machine runs are not automatically independent scholarly confirmation.

## Cost / deployment policy

Preferred path is **zero recurring service cost**:

```text
local images/crops
→ local Kraken inference
→ optional local helper code
```

Transkribus is comparison-only under the free allowance unless a later explicit owner decision justifies spending money.

No new platform, database or general HTR architecture is authorized by this issue.

## Deliverable / Definition of Done

- bounded benchmark results are persisted in the repo;
- at least one already-known difficult control set and one unresolved target set have been tested;
- tool/model/version/license and data-rights implications are explicit;
- a keep/drop decision is recorded separately for Kraken and any optional external comparator;
- no canonical diplomatic row is changed solely from HTR output;
- if no tool materially improves candidate generation, record the negative result and stop rather than expanding infrastructure.

## Execution contract + capability preflight — 2026-09-10

Phase #140 is now sufficiently specified for execution. The benchmark will preserve the epistemic order for known controls:

`raw HTR output → discriminator/question derivable from that output → target-pixel check → only then compare against known control reading`

A `useful discriminator` is therefore judged before using the expected control string as the scoring target. Fluency is not rewarded; fragmentary outputs such as partial grapheme sequences may be more useful than a fluent but graphically unsupported word.

The isolated Generator-B comparison will persist four dimensions rather than one aggregate score:

1. useful-candidate yield among a small inspected top-k/output set;
2. rank/time to first useful discriminator;
3. failure character (segmentation failure, fluent hallucination/normalization, partial grapheme loss, unusable output, etc.);
4. complementarity to Generator A (#141), especially whether B contributes on variable/allographic or sign-ambiguous cases where exact-template retrieval failed.

Additional effort/setup/adjudication cost must be weighed against complementarity. No combined A+B run is authorized before the isolated #140 result exists. F1 remains untouched.

Useful candidate/discriminator material appeared for `62v-L11` (`steinbruch`) and fragment-level on unresolved `62r-L09` and `62r-L23`; `62r-L19` localized the sign/vowel ambiguity but emitted `8o` / `walff` and did **not** generate the missing `So` alternative. `62r-L20` (`gemeinswalde`) was not recovered, and `62r-L06` produced the fluent but target-incompatible candidate `taschen` despite mostly high model confidence.

Primary failure learning: fluent/word-like HTR output can be scientifically worse than fragmentary uncertain output when the former is not target-supported. Raw output, a predeclared low-confidence attention rule, target inspection, and only then control comparison are kept separate in the evaluation record. The record also states that this procedural separation is not claimed as independent cognitive blinding because the executing context had prior access to known controls.

Decision: **KEEP CONDITIONALLY** as a bounded Generator-B candidate source for the next A-vs-B problem-type comparison. Do not integrate HTR into the default Evidence Packet; do not add a second model or broader HTR infrastructure from this result.

F1 remains untouched. Next Phase-2 step is the isolated-results comparison `problem type × useful candidate/discriminator × effort × failure character × complementarity`, without a total score and before any A+B trial.
