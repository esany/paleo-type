## Analysis → requirements → concept result

Fresh inspection of the current PR implementation changes the diagnosis in an important way.

### What the existing `savesax` code already does correctly

On PR #273, `tools/archival_source_acquisition.py` already:

- writes each successfully downloaded JPEG atomically into the configured `output_root` package directory before moving to the next image;
- removes only the current `.part` file on failure;
- never silently overwrites a differing existing file;
- on rerun, downloads an existing image again, compares SHA-256, and reports `already-present` when identical;
- writes the final manifest / `SHA256SUMS.txt` only after the full image sequence completes.

The `savesax` skill also already requires a configured **external destination**, forbids repository/worktree fallback, performs a dry run first and distinguishes partial/failing results from complete acquisition.

Therefore the failed GitHub Actions run does **not** prove that the acquisition core itself lacks all restart semantics. The decisive defect was that the chosen runner pointed `output_root` at disposable `/tmp`, defeating the persistence assumptions the CLI already makes.

### Selected smallest concept for the concrete `savesax` case

**Option A — acquisition-local execution repair, not a generic runtime platform.**

For productive acquisition:

`SStA → existing Python acquisition script → real configured persistent external source root`

Use GitHub Actions for deterministic/offline CI unless a future case demonstrates a real need and a persistent controlled destination is actually mounted/available there.

The first correction is therefore **runtime selection**, not a new checkpoint service.

### Minimal implementation delta to verify before another live run

Inside #271/PR #273, add deterministic interruption/resume coverage using the same persistent test directory:

1. multi-image plan;
2. first run successfully writes several JPEGs, then a mocked network failure terminates the operation;
3. verify completed JPEGs remain and no false `complete` manifest exists;
4. second run against the same directory completes the package without overwriting differing data;
5. final manifest/checksum set covers the complete provider list.

The current implementation will re-download existing images to compare their hashes. That is inefficient but **correctness-preserving**. Strong network-free no-op/idempotence is therefore an optimization/follow-up unless real workload proves it necessary; it should not block the smallest reliable repair.

Current evidence is enough to falsify `available runtime = suitable runtime`, but one SStA case is not enough to justify a shared runtime framework or new canonical execution schema.

- shared METHOD/Requirement change: **not yet justified** solely by this case.
