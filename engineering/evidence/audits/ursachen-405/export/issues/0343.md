## Status / authority

**BUG / ANALYSIS RECORD ONLY. No shared contract change is authorized by this Issue.**

## Demonstrated gap

The current crosswalk contract advertises independent digital locator fields:

- `export_image`
- `pdf_page`
- `stable_image_urn`

but the validator requires every crosswalk row to have a non-empty unique `archival_folio`.

For SStA Best. 20578 Nr. 632, provider-image identity is exact (`0001.jpg`–`0135.jpg`) while archival foliation is explicitly unresolved. A controlled full PDF can therefore be visually usable and page-addressable, but the repository currently cannot canonically record a simple observed mapping such as:

`provider image 0094 ↔ PDF page N`

without inventing an archival folio.

That blocks a practical scholarly workflow in which the PDF is used for comfortable visual inspection while exact JPEG/File identity remains the primary digital evidence locator.

## Why this matters

The repository already requires these locator meanings to remain distinct:

`provider image ≠ PDF page ≠ archival folio`

but the current crosswalk physical schema makes `archival_folio` the mandatory row key. This means the model cannot represent a digital-to-digital mapping when archival foliation is unknown.

For Nr. 632 this is not hypothetical: the Project currently has exact provider-image Files and unresolved archival foliation. The Human Owner proposes making the controlled PDF available in ChatGPT/Project so visual review can use PDF pages while scholarly results continue to cite exact provider-image/File IDs.

## Current evidence

- `corpus/source-contract.json`: crosswalk `locator_fields` include `export_image`, `pdf_page`, `stable_image_urn`.
- `tools/source_contract.py`: every crosswalk row fails unless `archival_folio` is non-empty and unique.
- existing Reg. Ii crosswalk fixtures work because archival folios are already known; they do not exercise a digital-only mapping.
- Nr. 632 `STATUS.md` explicitly says provider image IDs, PDF pages and archival folios remain distinct unless an evidenced crosswalk is established.

## Required semantic capability

Permit a source-relative crosswalk to record **observed mappings among digital locator domains without asserting an archival folio**, while preserving:

- distinct locator semantics;
- explicit mapping status/evidence;
- exact Source/File provenance;
- later addition of archival folio when genuinely observed;
- no fabricated foliation;
- existing Reg. Ii mappings without semantic loss.

Example required case:

`SSTA-ARCHIVIALE-EDD69AA1 : provider-image 0094 ↔ PDF page 95`

with `archival_folio = unresolved/not asserted`, not a synthetic folio token.

## Acceptance criteria

- [ ] provider-image ↔ PDF-page mapping can be represented before archival foliation is known;
- [ ] unknown archival foliation is not encoded as a fake folio string;
- [ ] mapping evidence/status remains explicit;
- [ ] existing folio-centred Reg. Ii crosswalks remain valid;
- [ ] resolver/research contexts can recover both locator forms and their relation;
- [ ] no automatic assumption of 1:1 PDF/image sequence;
- [ ] no Source/document boundary is inferred from locator mapping;
- [ ] any material shared contract implementation receives D-016 admission.

## Non-goals

- no universal locator graph;
- no requirement to canonicalize every working derivative;
- no automatic foliation;
- no automatic document segmentation;
- no change to Project priority or G2 state.

## Immediate workaround ceiling

Until the contract is corrected, a PDF↔JPEG mapping may be kept as a **Project research working table** with explicit evidence and claim ceiling, but it must not masquerade as an archival-folio crosswalk. This workaround should be used only if the Human supplies/authorizes the PDF for current source work.

## Scope clarification after full structure/history audit — **case extension, not replacement**

Human-Owner direction: when a real case requires a distinction because one locator/source layer is not yet available, treat it as a **case extension**. Do not overwrite or weaken the already valid case.

Fresh audit covered the relevant current and historical representation approaches: `corpus/files.tsv`, source-level `source-data/*/crosswalk.tsv`, `corpus/relationships.tsv`, Project `source-uses.tsv`, Project `research/use-evidence.tsv`, source-entry inspection coverage, legacy Project inspection logs/transcription page IDs, DigiRef/context evidence, and the historical decisions/issues #59/#61/#65/#66/#69 plus current #267/#268/#269.

### Existing case remains valid

The Reg.-Ii. crosswalk model is a proven case:

`archival folio ↔ export/provider image ↔ PDF page ↔ optional stable URN`

with explicit mapping status/evidence. Existing Reg.-Ii. rows and resolver semantics must remain losslessly valid. No migration or weakening is justified merely because Nr. 632 lacks foliation.

### New real case

Nr. 632 adds a materially different state:

`exact Source + exact digital instantiations + observed provider-image/PDF-page correspondence + archival folio not yet established`.

This requires representing:

`provider image ↔ PDF page`

without asserting an archival folio. If archival foliation is later directly established, that is **new mapping evidence added to the existing digital mapping**, not a reinterpretation that pretends the folio was known earlier.

### Owner comparison / why not repurpose another table

- `corpus/files.tsv` owns byte-exact instantiation identity/coverage/rights, not page-to-page correspondence.
- Project `research/use-evidence.tsv:evidence_locator` can locate evidence inside one concrete File for one Project use, but is Project-relative and must not become the reusable Source-wide digital crosswalk.
- `source-entry/inspection-coverage.tsv` owns inspection activity/depth/claim ceiling and #267 explicitly forbids repurposing crosswalk/File tables as progress stores; the converse also holds: coverage must not become a locator crosswalk.
- `corpus/relationships.tsv` owns Source→Source scholarly/structural claims and source-relative loci (#61); PDF-page↔JPEG-image is not a Source relationship.
- `source-uses.tsv:relevant_locus` is scholarly use/scope, not an instantiation locator.
- legacy inspection logs/page IDs are historical precedents and must not be revived as parallel canonical owners.
- a Project research table is an acceptable temporary evidence/working representation while the shared crosswalk contract cannot encode this real case, but it is not the desired reusable canonical owner.

### Required extension invariant

Any future concept must support at least these **coexisting** cases:

1. **folio-known crosswalk** — current Reg.-Ii. behavior unchanged;
2. **folio-unknown digital crosswalk** — observed mapping among digital locator domains with folio absent/unasserted;
3. **later enrichment** — an existing digital mapping may gain an observed/inferred folio mapping with its own evidence/status, without erasing the earlier evidence state;
4. **partial mappings** — no assumption that all locator domains are available for every row;
5. **no synthetic placeholder** — `unknown`, provider number, PDF page or object candidate must never be smuggled into `archival_folio` merely to satisfy validation.

Do not redesign this as a universal locator graph unless later real fixtures demonstrate that the extended crosswalk cannot carry the required cases. The aim is preservation of distinctions and cumulative evidence, not replacement of the existing model.

## Additional real-case dimension — digital locator must be instantiation-specific when several Files exist

The same audit exposes a second dimension of the #343 case, still within this Issue rather than a new bug.

Current crosswalk rows have `source_id`, `export_image`, `pdf_page`, `stable_image_urn`, etc., but **no explicit File/instantiation identity**. In the existing Reg.-Ii. fixtures this works because the mapping was reconstructed against one known exact export and the surrounding Project/research records identify that export.

Nr. 632 may have more than one controlled PDF representation (`full PDF` and `compact PDF` are already mentioned in Project STATUS). If both are retained/used, a bare locator such as `pdf_page = 95` is not necessarily unambiguous across those Files.

Therefore the extension analysis must also preserve:

`Source identity ≠ File/instantiation identity ≠ locator within that File`.

Required real-case capability:
- the same Source may have several exact File instantiations/derivatives;
- each File may have its own page/image locator sequence;
- a provider-image↔PDF-page mapping must be attributable to the exact PDF/File (or another equivalently unambiguous instantiation namespace);
- no assumption that Full-PDF page N equals Compact-PDF page N unless verified;
- existing Reg.-Ii. crosswalks must remain valid and need no artificial migration merely because their historical mapping basis was a single unambiguous export.

This is still a **case extension** of the reusable locator/crosswalk semantics, not a replacement of File identity, use-evidence or the existing folio-centred mappings. Do not preselect a `file_id` column versus another representation until the actual Nr. 632 PDF fixture is available and the smallest lossless representation can be tested.
