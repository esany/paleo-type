## Candidate minimal physical/contract concept for D-016 review

The Block-1 semantics can now be reduced to a concrete repository-native design without introducing a new platform. This is a **candidate concept**, not implementation admission.

### A. Project current-scope contract (#265)

Keep Project YAML scalar/simple. Add one controlled scalar state and stop using prose as the state token:

```yaml
active_scope_state: "none"        # none | whole-root | bounded
active_scope: ""                  # required only when state=bounded
```

Validation semantics:

- `none` → `active_scope` empty; Project exists but has no current scholarly scope;
- `whole-root` → `active_scope` empty; effective scope derives from `project_source_id`;
- `bounded` → `active_scope` non-empty and human-readable/source-relative enough for the Project state;
- historical/completed scope text is not stored in current scope fields.

`title` becomes a required Project key under the independent #264 drift repair.

This avoids nested YAML/schema machinery and works with the existing simple scalar parser after a small contract/validator extension.

### B. Project-local inspection coverage (#267)

Standardize one optional canonical Project table, preferably under the existing research-state namespace rather than reviving Project-local Source identity:

`projects/<id>/research/inspection-coverage.tsv`

Candidate minimum columns:

```text
inspection_id | source_id | source_locus | file_id | evidence_locator |
inspection_kind | coverage_state | inspected_on | evidence_basis |
limitations | notes
```

Semantics:

- one row = one evidenced inspection/coverage claim for one canonical Source/range;
- `inspection_kind` remains lean/open (e.g. `relevance-survey`, `structural-survey`, `diplomatic-inspection`) rather than a universal ontology;
- `coverage_state` needs only the stable distinction necessary to avoid false completion (`inspected`, `partial`, `unresolved`, `unavailable` or equivalent — exact tokens to be fixed in implementation design);
- `source_locus` and `evidence_locator` preserve their distinct identifier domains; an unfoliated source may initially be covered by exact image/File locators;
- `file_id` is used when exact canonical File evidence is established; missing File identity must not be hidden by a prose locator;
- STATUS summarizes/links; it is not the granular owner;
- crosswalks remain identifier mappings, not work-progress tables.

The existing Reg. Ii 5 `sources/inspection-log.tsv` is the migration/Generic-Fit fixture. Its material evidence must be loss-checked into the chosen owner; no duplicate log should survive as parallel current truth.

### C. Reusable contained-Source ↔ File mapping (#268)

Do **not** weaken `corpus/files.tsv` into multiple owners for identical bytes and do not put reusable correspondence only in Project use-evidence.

Add a narrow reusable Source-data mapping per contained Source, conceptually:

`corpus/source-data/<source_id>/file-coverage.tsv`

Candidate minimum columns:

```text
mapping_id | file_id | source_locus | evidence_locator |
mapping_status | evidence_basis | notes
```

Semantics/validation:

- directory Source and File must both resolve canonically;
- if the File's owning `source_id` differs from the mapped Source, the mapped Source must be structurally within that File-owning Source (`part_of*`) for this initial case;
- mapping records exact correspondence/coverage, not Project use or automatic Source segmentation;
- one File identity remains one File identity.

Extend Project `research/use-evidence.tsv` with an optional mapping reference, conceptually `source_file_mapping_id`:

- same-Source File use may continue under the current simple rule;
- cross-Source/ancestor-File use is allowed only through a canonical mapping whose `source_id` equals the use Source and whose `file_id` equals the evidence File;
- the Project record then means “this use actually used that already-established exact evidence”, while CORPUS owns the reusable Source↔File correspondence.

This is preferable to overloading the current `crosswalk.tsv`, because that table currently requires non-empty unique `archival_folio` and at least one export/PDF/URN locator. The real Wolkenburg image sets may be unfoliated at intake and may consist of many individual Files; forcing them into the folio crosswalk would create another semantic collapse.

### D. CORPUS Source-set selection (#263) + #12 coverage

Add two lean global CORPUS registries (names are candidate but semantics are the key):

`corpus/source-selections.tsv`

```text
selection_id | title | archive | fonds | selector |
selection_basis | snapshot_date | evidence_basis | notes
```

`corpus/source-selection-members.tsv`

```text
selection_id | source_id | membership_basis | notes
```

Rules:

- selection is not a Source and never participates in `part_of`;
- membership references Source IDs, never Files and not primarily Projects;
- selection membership does not create a Project;
