## Text

## Status / authority

**P1 planning / quality-assurance design only. No prompt framework, agent runtime, workflow engine, validator, template file or repository-wide migration is authorized by this Issue.**

This Issue defines the smallest reusable **procedural scaffold** that makes specialized AI-assisted work less dependent on a particular model/session while preserving non-deterministic scholarly judgement.

The goal is not `same evidence → same result`.

The goal is:

```text
variable model / variable legitimate scholarly judgement
        ↓
stable governing context
stable role boundary
stable required checks
stable stop/escalation rules
stable handoff contents
stable canonical ownership
stable return/review path
        ↓
more restartable, auditable and role-safe work
```

## Governing principle

**Standardize the path, not the scholarly outcome.**

The scaffold should constrain procedural omissions and authority drift while leaving evidence-constrained scholarship open to legitimate disagreement.

It must not become a giant master prompt or a second methodology store.

## Problem demonstrated by current chats

Specialized chats are useful because Source Research, Domain Review and Dev benefit from narrower task context. But specialization creates predictable session risks:

- role/authority drift;
- missing governing context;
- a new session reconstructing its mandate differently;
- source work drifting into architecture;
- Dev reinterpreting scholarly need;
- owner being asked technical/specialist questions that belong elsewhere;
- independent review being confused with AI self-review;
- handoffs losing uncertainty, evidence identity or non-goals;
- returned work failing to re-enter the active scholarly NEXT ACTION;
- old-chat prompts becoming de facto governance.

The solution should make the **minimum procedural contract explicit and reusable**.

## Design constraints

1. Canonical rules remain in existing owners (`GOVERNING_OBJECTIVE.md`, `AGENTS.md`, methodology, project/corpus state).
2. Fragments reference/instantiate canonical rules; they do not replace them.
3. Role/task prompts are generated/composed from current repo state rather than treated as truth stores.
4. The scaffold is modular: use only fragments relevant to the current handoff/task.
5. Required fields may be structurally checkable; their scholarly content remains judgement-based.
6. No requirement for identical prose across chats.
7. No prompt registry/database.
8. No automatic agent orchestration.
9. No requirement that every activity use a separate chat.

## Proposed minimal fragment family

Test the need for the following small fragments. Do not add more unless a real fixture exposes a gap.

### Fragment A — ROLE CONTEXT

Purpose: establish what the current work context is and is not before action.

Candidate required elements:

```text
ROLE
PURPOSE
GOVERNING AUTHORITY
CURRENT CANONICAL TASK / OWNER
REQUIRED CONTEXT
MAY DECIDE / DO
MUST NOT DECIDE / DO
STOP / ESCALATE WHEN
PRIMARY HANDOFF TARGET
CANONICAL-STATE RULE
VALIDATION STATUS
RESTART TEST
```

### Fragment B — TASK START / RESUME

Purpose: ensure a new session resumes from canonical state rather than old-chat narrative.

Candidate elements:

```text
CURRENT PROJECT / SOURCE / ISSUE
CURRENT STATUS / NEXT ACTION
EXACT EVIDENCE / INPUT AVAILABLE
PREREQUISITES SATISFIED
KNOWN OPEN QUESTIONS
STAGE-SPECIFIC CONTEXT BOUNDARY
FIRST BOUNDED ACTION
COMPLETION / STOP CONDITION
```

This fragment is especially important where blind/source-independent reading requires some existing context to be withheld.

### Fragment C — HANDOFF

Purpose: transfer work across roles without forcing the receiver to reconstruct the prior chat.

Candidate elements:

```text
FROM ROLE
TO ROLE
TRIGGER
CANONICAL TASK / OWNER
EVIDENCE / INPUT
ESTABLISHED
UNRESOLVED / NOT INVESTIGATED
REQUEST
MAY
MUST NOT
ACCEPTANCE / RETURN CONDITION
CANONICAL PERSISTENCE
```

### Fragment D — RETURN / REVIEW

First test whether Fragment C is sufficient bidirectionally. Add a separate Return fragment only if real Dev→Domain Review or Specialist→Domain Review cases show that the semantics differ materially.

Do not create a separate template merely for symmetry.

### Fragment E — OWNER DECISION REQUEST

Use the minimal contract derived in #75 only for genuinely owner-reserved decisions:

```text

WHY OWNER-RESERVED
CURRENT STATE
OPTIONS / CONSEQUENCES
RECOMMENDATION (where justified)
WHAT IS NOT BEING ASKED
RESULTING NEXT ACTION
```

Test whether this is best kept as a role-specific fragment or whether it belongs in the generic fragment family.

### Fragment F — SPECIALIST REVIEW PACKET

Use #76 as fixture. It may remain role-specific unless repeated across disciplines demonstrates generic reuse.

Core candidate elements:

```text
REVIEW QUESTION
SOURCE IDENTITY
EVIDENCE
CURRENT OBSERVATION / READING
ALTERNATIVES
RELEVANT CONTEXT
KNOWN LIMITS
REQUESTED VALIDATION LEVEL
```

## Procedural invariants to derive

Determine which of these should become generic mandatory guardrails in `AGENTS.md` versus optional template assistance:

1. specialized work context declares one primary role/function;
2. role authority is derived from canonical repository rules, not old chat;
3. current canonical task/owner and NEXT ACTION are identified before acting;
4. applicable context must be loaded; irrelevant context may be excluded;
5. stage-specific contamination/blind-reading constraints are honored;
6. uncertainty/not-investigated state survives handoff;
7. a role crossing its authority boundary must hand off rather than silently expand scope;
8. material handoff identifies evidence, established state, unresolved state, request and return condition;
9. owner decisions are requested only for owner-reserved matters;
10. Dev implementation carrying scholarly requirements returns for scholarly adequacy review;
11. independent specialist review remains separately labelled;
12. durable consequential state returns to canonical repository owners;
13. old chat/prompt is never the sole restart source.

## What may become deterministically/structurally checkable

The scaffold may later support a **lightweight completeness check** only for stable procedural structure, such as:

- primary role present;
- canonical task/owner identified;
- required handoff FROM/TO present;
- evidence/input identified where material;
- unresolved/not-investigated field present where applicable;
- request present;
- authority/non-goal boundary present;
- return condition present;
- canonical persistence target present.

This does **not** validate that the scholarly content in those fields is correct.

Do not implement such checking until repeated real usage demonstrates enough value to justify it.

## Explicitly non-deterministic content

The scaffold must never require mechanical agreement on:

- manuscript reading;
- interpretation;
- historical identification;
- hand attribution;
- whether a finding is ultimately generic;
- whether specialist review agrees with prior AI work;
- exact implementation design where several solutions satisfy the admitted requirement.

## Fixture finding — prevent role-stage ambiguity in composed start/handoff prompts

The first review of the planned Source Research handoff exposed a concrete model/session ambiguity: a receiver can correctly understand the later Domain Review description yet mistakenly treat that downstream review as the task that should execute now.

This should become a real falsification fixture for the procedural scaffold.

### New requirement for ROLE CONTEXT / TASK START

A composed work-context prompt should distinguish explicitly between:

- **current executable role/stage**;
- **current first bounded action**;
- **downstream role/stage**;
- **downstream gate not yet satisfied**, where applicable.

Candidate minimal additions to `TASK START / RESUME`:

```text
CURRENT EXECUTABLE ROLE / STAGE
FIRST BOUNDED ACTION
DOWNSTREAM HANDOFF TARGET
DOWNSTREAM GATE / NOT-YET-AUTHORIZED WORK
```

Do not add these as permanent fields if the same protection can be achieved more simply from existing fields. Test against the #72/#64 fixture first.

### Handoff interpretation invariant

A handoff/start packet must make it possible for a new session to answer independently:

1. What may I execute **now**?
2. What evidence must I produce before handoff?
3. What am I explicitly **not** authorized to execute yet?
4. Which later role receives the result?

The existence of a downstream blocked role must not be misread as a blocker on the upstream evidence-producing role.

### Domain-classification guardrail confirmed

The Source Research→Domain Review handoff should preserve evidence and uncertainty but must not require Source Research to pre-decide whether the consequence is generic or technical.

A `PROVISIONAL CLASSIFICATION`, if retained, must be read as routing aid only. It must not mutate into:

`possible representation problem → Dev requirement`.

The receiving Domain Review must explicitly test:

- incomplete research vs established information;
- existing canonical owner adequate vs inadequate;
- project-local consequence vs reusable requirement;
- actual research-system gap vs no technical action.

### Completeness checking implication

If structural completeness checking is ever justified, a useful check may be whether the packet distinguishes current executable work from downstream gated work.

Such a check validates **procedural clarity only**. It does not decide whether the gate is scientifically satisfied or whether the scholarly classification is correct.

### Falsification criterion added

The scaffold fails if a competent new session can read a composed handoff and reasonably execute the wrong role/stage because current work and downstream review are not explicitly separated.

## Real-fixture finding: distinguish session-start handoff from later role-result handoff

The replacement #73 Domain Review chat exposed a user-facing ambiguity in the proposed handoff language.

The chat had already received a complete replacement/start-resume handoff and successfully reconstructed its role from canonical repo state. However, wording such as `wait for / accept the Source Research handoff` was interpreted as though the human user still needed to provide another handoff prompt or packet.

That interpretation is procedurally wrong and can materially undermine user confidence because it makes a successfully restored work context appear incomplete.

### Distinction demonstrated by the fixture

A specialized continuation can involve two different handoff events:

```text
A. SESSION / ROLE CONTINUATION HANDOFF
old context → replacement context
purpose: establish role, canonical task, boundaries and restart state

B. WORKFLOW / RESULT HANDOFF
upstream scholarly role → downstream scholarly role
purpose: transfer newly produced evidence/findings for the next stage
```

If A is complete but B is still pending, the receiving chat is **not waiting for the user to establish the role again**. It is already the valid continuation context. It should retrieve B from canonical repository/Issue state when B is produced, unless the user is genuinely the owner of missing evidence/access.

### Candidate generic clarification for the handoff scaffold

Any eventual Task Start / Resume or HANDOFF fragment should make clear:

- whether the current session/role continuation handoff is already complete;
- whether a later upstream **result handoff** is still pending;
- who owns producing that pending input;
- whether any human-user action is actually required.

A receiver must not phrase an internally pending role/result handoff as a request for the user to re-supply an already completed session handoff or replay the previous chat.

Potential compact invariant:

> **Do not confuse `this work context has been handed off` with `an upstream work result has not yet reached this role`. If the former is complete, continue in-role; obtain the latter from its canonical owner when produced. Ask the user only when the missing input is genuinely user-owned.**

This is a procedural/restartability clarification only. It adds no workflow engine, truth store, or deterministic scholarly outcome.

The immediate #73 fixture comment was updated accordingly.

## Real fixture rule: maximize model/session independence; prevent chat knowledge monopolies

Current #72/#73 use exposed a generic restartability requirement that should govern the scaffold:

> A specialized chat is an execution context, never the sole durable owner of consequential knowledge.

The scaffold should therefore be evaluated against the stronger restart test:

```text
old chat unavailable
+ capable replacement model/session
+ canonical repository state
+ controlled evidence/input
+ durable role/task context
        ↓
role and current task can be reconstructed
material prior findings/uncertainty/handoff state can be recovered
work can continue without asking the human to replay conversation history
```

Desired property: **maximum practical AI/model/session independence**, not dependence on one model's memory or one conversation transcript.

Consequences for fragment design:

1. ROLE/TASK/HANDOFF fragments may bootstrap a session but must not become truth stores.
2. Material findings, uncertainty, decisions, blockers and NEXT ACTION must persist to canonical owners when they become consequential.
3. A receiver should retrieve persisted upstream results directly; the human should not act as a courier for knowledge already stored in the project workflow.
4. Replacement-session handoff and later role-result handoff are distinct; neither may create dependence on a particular prior chat.
5. If another capable model cannot resume without old-chat narrative, treat that as a scaffold/canonical-state failure.
6. Scholarly non-determinism remains intact: model independence means independence of the work process/state from a specific model, not forced agreement of scholarly judgement.

This is a real #72/#73 fixture for the existing acceptance criterion `another capable model/session can resume ... without old chat`; no new framework or orchestration layer is implied.

## Real-fixture execution finding — prevent evidence-access retry loops

The Reg. Ii 5 #72 run exposed a restartability/execution failure that belongs in the model-independent work-context scaffold.

### Failure observed

A visual Source Research context successfully established access to the active source images, but then repeatedly re-ran the same access/retrieval path instead of advancing the scholarly task. The instructions were individually reasonable (`verify actual image access before visual work`) but lacked scope: a cautious model could interpret the check as required before every downstream source action.

### Candidate generic invariant

**Gate once; re-open only on a falsifying trigger.**

For any prerequisite such as evidence access:

```text
prerequisite state = UNKNOWN
→ verify for the current work context + active evidence set
→ PASS
→ downstream execution proceeds without re-verifying the prerequisite
```

Re-verification is allowed only when a concrete trigger invalidates the prior pass, e.g. actual retrieval failure, changed evidence set, new session/context lacking a current pass, or identity/provenance uncertainty.

### Work-cursor requirement

Long-running AI tasks should expose a monotonic executable cursor independent of chat memory:

- current unit;
- last completed unit;
- next bounded action;
- real blocker, if any.

A prerequisite PASS must not displace that cursor. Repeating a passed gate without a falsifying trigger should be treated as an execution-loop defect.

This supports the project goal of model/session independence: another capable model should resume the substantive task rather than rediscover already-passed prerequisites. It is procedural only; scholarly outcomes remain non-deterministic.

## Generic circuit-breaker for looping AI work contexts

Add a restartability rule for model/session independence:

A work context that repeatedly re-enters an already-passed prerequisite branch after an explicit correction should not be treated as indefinitely repairable. After repeated failure to advance the declared execution cursor, retire that context and restart the same role from canonical state in a fresh context.

Key distinction:

`task/state failure ≠ context/session failure`

If canonical state and evidence remain valid, replace only the failing context. Do not restart settled upstream work.

A replacement context should receive the **smallest executable next action**, not the entire historical debugging conversation. It should be able to reconstruct broader context from canonical owners when later needed.

For source work specifically, once access is PASS, the replacement context begins at the source cursor. Access/provenance is reopened only on a concrete retrieval/identity failure.

This circuit-breaker prevents repeated prompt patching from becoming a new chat-level knowledge monopoly and supports model/session independence.
