## Changed structures

### Project→Source use
Target project use rows are represented as:

`use_id | source_id | research_function | relevant_locus | status | evidence_basis | notes`

- one row = one concrete Project-relative research function;
- multiple Uses/functions for the same Source are allowed;
- `research_function` is open vocabulary with syntax control only;
- no automatic function inference;
- `principal` is a research function, not a Project boundary anchor.

### Owner Variant B — Use-Evidence
Concrete digital evidence is represented separately as:

`evidence_id | use_id | file_id | evidence_locator | status | evidence_basis | notes`

- `corpus/files.tsv` remains the sole canonical File identity/provenance owner;
- one Use may have 0..n Evidence rows;
- one File may support 0..n Uses of its canonical Source;
- no evidence is inferred automatically;
- no redundant `source_id` is stored in Use-Evidence;
- validator requires `use.source_id == corpus/files.tsv[file_id].source_id`, preserving the legacy `primary_file_id` source/file provenance invariant.

### Legacy compatibility
The current `projects/ega-reg-ii-5-knau/` Project remains on its existing legacy representation. The resolver exposes legacy state separately from target Uses/Evidence; no legacy `primary_file_id` is automatically materialized as target Use-Evidence.
