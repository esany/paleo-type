## Demonstrated structural problem

The current canonical model assumes:

- one `corpus/files.tsv` row has exactly one `source_id`;
- exact byte identity is unique (current tests reject duplicate canonical File rows for the same SHA-256);
- Project `research/use-evidence.tsv` may bind a File only when that File's canonical `source_id` equals the `source_id` of the referenced Project use.

That combination works for the current Reg. Ii fixture because the canonical exports are already bounded to the relevant source groups.

The Wolkenburg fixture introduces a materially different real case:

1. one archival item is the Project/documentary root;
2. the archive may provide one 50–300 page PDF/export for that whole archival unit;
3. only after full-source inspection do internal sections/documents/copies become separately identified canonical Sources;
4. later Project research may use one internal Source/locus while the exact inspected bytes remain the same whole-unit PDF.

Under the current contract, if the whole PDF is owned by the root Source, an internal-Source use cannot bind that exact File because the source IDs differ.

## Why obvious workarounds are unsafe

### Duplicate the same exact PDF once per internal Source

Conflicts with the current exact-SHA uniqueness invariant and creates multiple canonical File identities for one byte sequence.

### Reassign the whole PDF to one internal Source

Falsifies what the File materially instantiates and loses whole-unit coverage/provenance.

### Create crops/excerpts solely to satisfy same-Source binding

May create unnecessary derivative proliferation and makes exact original evidence secondary even when the original whole-unit PDF was what was actually inspected.

### Avoid internal Source identity

Collapses documentary distinctions precisely when a chapter, copy, attachment or other bounded record needs stable identity/provenance/citation.

## Analysis refinement — the bug is broader than “one large PDF”

Fresh comparison with #271 corrects one over-specific premise in the original Issue body. The current Wolkenburg/Sächsisches-Staatsarchiv fixture is not necessarily one giant PDF: Nr. 632 is represented by **135 Fullsize JPEGs**, and Nr. 754 by **61 viewer images**. #271 still has an open decision about whether each JPEG becomes a canonical File and whether an external package/manifest is represented separately.

The Issue title has therefore been generalized. The actual failure class is:

> exact File(s) are initially associated with a broader/root Source; later inspection discovers a contained canonical Source; the same exact original evidence is needed for that child Source, but current use-evidence requires exact equality between `File.source_id` and `Use.source_id`.

This applies to a single whole-unit PDF **and** to a sequence of root-level image Files.

### Current executable facts

- `corpus/files.tsv` gives each File exactly one `source_id`.
- `tools/source_contract.py` rejects Project use-evidence when the File's `source_id` differs from the use Source's `source_id`.
- `source_intake.py` expects exact SHA lookup to resolve to one canonical File and errors if several File rows carry the same exact SHA.
- `tests/test_source_intake.py` protects the current no-duplicate-SHA state.

So duplicating identical bytes under every discovered child Source is not a viable workaround.

### Options compared

**A. Duplicate/reassign Files** — reject. It either destroys exact identity/provenance or makes exact SHA resolution ambiguous.

**B. Project-local exception only:** permit a child-Source use to bind an ancestor-owned File when `child part_of* ancestor`, with an exact locator in `use-evidence`. This is small, but it would make reusable Source↔File correspondence Project-local and repeatedly encode the same mapping in every Project use.

**C. Reusable source-wide evidence/coverage mapping:** retain one canonical File identity at the Source level it truthfully instantiates, and record that a contained Source is evidenced/instantiated within that File at an exact digital/source locator. Project use-evidence can then reference the already-established Source↔File/locus correspondence rather than inventing File ownership.

**D. General File↔Source many-to-many registry:** expressive but broader than currently demonstrated and risks turning the File layer into a generic asset graph.

### Current preferred concept

Option **C**, or the smallest representation semantically equivalent to it, is the strongest fit with existing ownership rules:

- one exact byte sequence keeps one canonical File identity;
- File provenance/coverage stays truthful at the broader Source;
- internal Source identity remains independent;
- a reusable, source-wide mapping owns `contained Source ↔ exact File ↔ exact locator/coverage`;
- Project `use-evidence` remains about **this Project use actually using this evidence**, not the only owner of the underlying Source↔File correspondence.

The existing `corpus/source-data/<source_id>/crosswalk.tsv` proves that reusable Source↔digital-locator mapping is already a canonical concept, but its current schema has no `file_id` and is source-directory-specific. It must **not** simply be overloaded without checking the multi-File / child-Source case. Whether the smallest solution is a compatible crosswalk extension or a narrowly separate instantiation/coverage relation remains a material design choice.

### Deterministic rule to preserve

A broader/root File may support a contained Source only when:

1. the child→ancestor containment is canonically established (`part_of*`), or another explicit evidenced relation makes the coverage truthful;
2. the exact File is identified;
3. the supporting locator/range is explicit and evidence-bearing;
4. no child Source identity is inferred merely from File coverage.

### Relation to #271

#271 should remain provider/download focused. Its decision about JPG registration/package manifests supplies the real File granularity fixture, but the skill must not solve this scholarly Source↔File model internally or invent child Sources.

### Admission classification

Changing File/Source/use-evidence semantics is a **material CORPUS/Project-evidence change under D-016**. The problem and preferred semantic direction are now bounded; physical representation should be decided together with #263/#265/#267 so we do not create a second correspondence owner.

**Disposition:** analysis/concept narrowed and ready for material design/admission; keep open.

## Kommentar 5985670141 · 2026-10-04T23:39:30Z · esany

## Recursive-depth refinement — File evidence must not assume one flat internal-Source level

#270 now makes explicit that a Wolkenburg Archivale can have several evidenced documentary levels: document complex → document → section/attachment/register/accounting unit → locus, with canonical Source nodes introduced only where identity/provenance/relation/citation/research requires them.

The failure in this Issue therefore has to be solved **level-agnostically**:

`root/broader Source owns exact File(s) → one or more contained Sources may be discovered at arbitrary evidenced depth → the same exact File(s) + precise locator/coverage must be reusable as evidence for those contained Sources without duplicate bytes or false File ownership`.

The mapping must not:

- assume every internal Source corresponds to its own JPG/PDF;
- assume only one child level below the Project root;
- infer Source boundaries merely from image/file coverage;
- require duplicate File rows for the same bytes;
- turn project-relative research scope into Source/File provenance.

The previous preferred semantic direction — reusable contained-Source ↔ exact File ↔ exact locator/coverage correspondence, with Project use-evidence recording actual project use separately — remains valid as a candidate. Its physical representation is still not admitted and must be tested against multi-image Wolkenburg fixtures plus existing Reg. Ii crosswalk/use-evidence behavior under D-016.
