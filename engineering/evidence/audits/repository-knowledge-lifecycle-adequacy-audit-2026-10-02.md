## 1. Purpose

This artifact removes a concrete chat-knowledge monopoly by preserving the holistic 2026-10-02 audit of repository maintainability, knowledge persistence, current-vs-historical state, decision provenance, work-owner lifecycle/closability, active-context composition and the repeated `lean/minimal` correction pattern.

The audit was requested after several earlier repository and cross-repository audits had produced valuable evidence but also exposed a recurring risk: large real problems can be followed by increasingly narrow local corrections whose local `PASS` is valid while the underlying integration/maintainability burden remains. Issue #230 was created as a bounded analysis owner for that suspected failure family and explicitly requires an adequacy-first disposition rather than a size-first architecture choice.

This audit therefore asks two distinct questions together:

1. **What knowledge from the accumulated audit/chat history must become repository-recoverable without the originating conversation?**
2. **What common causal structure, if any, connects current/history drift, issue archaeology, decision reconstruction, non-closable owners, active-context growth, AI integration burden and repeated minimal-fix cycles?**

The result is evidence for #230 and for a separate D-016 decision surface. It does not itself admit the material lifecycle/architecture changes discussed below.

## 4. Executive system finding

The evidence rejects both extreme explanations.

### H1 — local-defects-only

> README staleness, Phase-2 staleness, issue chronology, decision reconstruction, requirements-artifact heterogeneity and current/history overlap are largely independent defects; local repairs are sufficient.

**Disposition: insufficient as a whole-system explanation.**

Several defects recur with the same operational consequence: a fresh maintainer must temporally and semantically compile current state from history, issue comments, accepted decisions, generated/derived surfaces and canonical owners. Fixing one stale sentence does not close that family.

### H2 — one monolithic structural architecture defect

> Most observed failures are manifestations of one missing repository platform/state architecture.

**Disposition: too strong.**

Many core separations are already healthy and should not be rebuilt: Source/File/Project boundaries, Project authority, Candidate≠Canonical, Derived≠Owner, resource-state≠task-authority, S1–S9, C1R's negative authority cases and local-PASS containment. Some remaining problems are scholarly/epistemic and deliberately cannot be compiled into a deterministic control platform.

### H3 — bounded mixed result

**Disposition: best supported.**

There is a real coupled structural gap in:

> **Repository Knowledge Lifecycle + Work/Programme Lifecycle + Operational Context Composition.**

This gap explains a substantial part of:

- current/history/supersession drift;
- issue chronology becoming part of restart/context reconstruction;
- accepted-decision rationale remaining distributed across programme comments and artifacts;
- bounded work that risks remaining operationally active because closure would otherwise hide useful history;
- persisted evidence remaining too close to the default active reading surface;
- AI reconstruction debt and fresh-maintainer context tax;
- repeated pressure toward narrowly scoped local fixes after governance/audit accretion.

It does **not** fully explain:

- Review Premise Inheritance / evidence-basis independence;
- scholarly selection of appropriate analysis units;
- open historical interpretation;
- #225's still-missing positive owner-authorized scholarly vertical fixture.

Those remain distinct or partially coupled problems.

## 5. Chronology of learning relevant to the causal result

### 5.1 Source/Witness/Project recovery

Earlier work exposed unsafe coupling between text, witness attribution, source structure and project organization. The current repository now separates Source, File, Project, research function, current work, diplomatic reading and interpretation. These are necessary epistemic distinctions, not incidental bureaucracy.

### 5.2 Reg. Ii 5 analysis-unit failure

The Reg. Ii 5 sequence around #161/#165/#171/#166 is the strongest scholarly falsification fixture.

A higher-level synthesis corrected excessive local fragmentation but then contributed to an overcorrection: a cross-witness/cross-folio comparison range was promoted into a stronger source/analysis-unit claim. The first repair was internally coherent and received a local technical/repository `PASS`; a subsequent fresh review still inherited the same underlying premise. Only renewed direct source inspection established that the relevant blocks were two separately initialled adjacent decrees/rules.

The important generic lesson is not merely "review again". It is:

> **Fresh context is not equivalent to an independent evidential basis.**

A reviewer can be independent of the originating chat yet still inherit the contested premise from the same derived research owners.

### 5.3 Resource state → task authority failure

A separate failure class occurred when unavailable source pixels were promoted from an action-local resource fact into `REAL BLOCKER → STOP`, then synchronized into restart state and regressions. #169 corrected the generic transition: resource availability is descriptive; it does not manufacture roadmap/task authority without an authoritative dependency.

This case demonstrates that restartability/reconciliation are amplifiers. They can preserve good state or preserve an unauthorized state very reliably.

### 5.4 #225 systemic operationalization

#225 correctly reframed the next system problem as composition rather than missing rules. Its anti-fragmentation guard is important existing evidence: a bounded child may close without implying parent success; each child needs a reconstructable parent contribution, bounded result, non-achievement boundary and return/reconciliation condition.

### 5.5 C1R

Phase 2 reduced the architecture to C1R — a read-only/rebuildable Outcome Control Context over existing owners. A generic deterministic planner was rejected as an independent architecture because readiness/gate state cannot create scholarly priority. Human Owner D-016 admission authorized only the bounded read-only slice. Implementation/result review then correctly recorded a local technical/semantic-loss `PASS` while keeping #225 open.

### 5.6 Cross-repository falsification

`Wissensarbeit` provided a particularly useful real counterexample to unnecessary persistent state: an additional planning snapshot was implemented as a candidate and then rejected by independent review because the relevant planning authority already existed and the real defect was cursor synchronization. The corrected design compiled existing authority into a thin current cursor rather than adding a second clock.

This falsifies "every integration problem needs a persistent integration state". It does **not** establish "every adequate solution must be small".

### 5.7 Adequacy-first correction

The accumulated audit history exposed a second-order design bias: repository rules strongly protect against overengineering, but `smallest`, `minimal` and `lean` can become an input constraint before the necessary solution properties have been established.

#230 therefore correctly reframes the reasoning order:

1. understand the demonstrated problem;
2. derive all necessary solution properties;
3. determine what architecture/process/repository structure satisfies them;
4. prove the failure family is actually closed;
5. only then remove demonstrably unnecessary complexity.

`Lean` remains a cost/quality discipline, not permission to truncate required functionality.

## 7. Failure-family map

### FF1 — Knowledge Currentness & Supersession

Symptoms:

- current and historical assertions share obvious reading surfaces;
- stale status text remains semantically active to a fresh reader;
- long-lived issue bodies/comments require temporal reconstruction;
- supersession/current pointers are inconsistent across artifact classes.

Concrete fixtures include the current README programme-navigation drift and the historical `ACTIVE CONCEPT ANALYSIS` header on the completed Phase-2 artifact.

### FF2 — Owner Lifecycle & Closability

Symptoms:

- a work/programme/audit issue can accumulate current state, decisions, evidence and history;
- useful history creates pressure to keep the work owner operationally alive;
- successor/current-state semantics become entangled with the old owner thread.

The failure is not "long-lived owner = bad". Constitutional/normative owners and accepted decision logs may be durably long-lived. The problem is a bounded work owner that cannot become historical without losing operationally needed meaning.

### FF3 — Decision & Provenance Promotion

Symptoms:

- accepted material rationale may remain distributed across issue comment, concept artifact, admission comment, implementation and result review;
- a maintainer must reconstruct the accepted decision rather than read its durable decision owner;
- scientific review provenance can inherit a derived premise without showing its actual direct evidence basis.

Work-decision promotion and scholarly-premise provenance are related by relationship visibility but are not assumed to be one technical model.

### FF4 — Active Context & Operational Composition

Symptoms:

- canonical owners are individually strong but a fresh context must integrate many roles/clocks;
- hand-maintained orientation prose drifts;
- full-context loading activates historical evidence that is not necessary for current work;
- a strong model can hide the repository cost by successfully compiling the state mentally.

### FF5 — Qualification / Local vs Global

Symptoms:

- local task/CI/implementation success may look like higher-level success;
- earlier assurance becomes stale after later semantic mutation;
- restartability can preserve an incorrect premise.

#225's anti-fragmentation guard and the repository's multi-dimensional quality model already provide strong semantics; positive vertical qualification remains necessary.

### FF6 — Scholarly Framing & Evidence Independence

Symptoms:

- correspondence range, physical block, functional grouping and research analysis unit can be conflated;
- a reviewer can inherit exactly the premise supposedly under review.

This is not safely solved by generic workflow automation. Direct evidence, question-relative scholarly framing and specialist/domain judgement remain essential.

### FF7 — Adequacy vs Premature Minimalization

Symptoms:

- architecture options are discarded primarily because they look large rather than because evidence makes them unnecessary;
- a local bounded solution is mistaken for an adequate solution to the parent failure family;
- audit → narrow fix → local pass → repeated audit becomes a self-reinforcing pattern.

The corrective rule is symmetric: insufficiently small and unsupportedly large solutions both fail.

## 8. New causal relations from the holistic audit

### 8.1 Closability is a bridge between persistence and active-context control

A bounded work owner can leave the default active context only if the durable meaning it produced has moved to the correct persistent owner(s). Therefore closure is not merely issue hygiene. It is a knowledge-lifecycle operation:

```text
working/current work
→ bounded result
→ review/disposition
→ accepted meaning promoted to durable owner(s)
→ parent consequence reconciled
→ work owner closes
→ work history remains discoverable
→ history leaves the default active surface
```

Without this bridge, useful history creates pressure to keep the work owner current forever.

### 8.2 Decision promotion reduces immortal programme owners

`DECISIONS.md` already exists specifically for consequential cross-project rationale that would otherwise need rediscovery. If an accepted architecture decision remains understandable only through a programme's comment chronology, the programme issue is forced to serve as both work owner and durable decision record.

This is not a demand for a new ADR framework. It is a Generic-Fit question about consistent use of the existing decision owner.

### 8.3 Context tax and minimal-fix pressure form a feedback loop

The combined evidence supports this loop:

```text
real failure
→ safeguard/audit/evidence retained
→ more correct but distributed protective complexity
→ weak current/history composition
→ larger fresh-context/meta-work burden
→ pressure to be "lean/minimal"
→ narrow local correction
→ residual structural burden
→ another failure/audit/safeguard
```

Necessary protective distinctions must not be removed. The architectural target is to reduce **avoidable access/integration complexity**, not scholarly nuance.

### 8.4 Derived views are downstream, not root authority repair

A generated dashboard or bounded context is useful only when the source owners and lifecycle semantics are sufficiently clear. If source artifacts disagree about currentness, a derived view either reproduces the disagreement or silently decides which source wins and becomes a new authority.

Therefore source/currentness/decision-lifecycle defects must be repaired or explicitly modeled before a view can safely compile them.

### 8.5 #225 already contains a programme-local Proto-DoR/DoD model

The #225 child admission test functions as a programme-local Definition of Ready; its bounded-result/return-reconciliation/local-PASS rules function as a child Definition of Done; T11 functions as the parent Definition of Done.

The open question is Generic-Fit and operationalization, not invention from zero.

### 8.6 Review-premise provenance is related but not reducible to work lifecycle

Work lifecycle asks which state is current/historical/done and where accepted results go.

Consequential scholarly review asks which claim/premise was reviewed, which evidence the reviewer inspected directly, what was inherited and through which derivation.

A later architecture may share relationship primitives, but this audit does not pre-authorize one shared schema.

## 9. Stronger repo-first persistence model

The audit supports the following definition:

> **Repo-first = durable + semantically typed + canonically owned + provenance-preserving + lifecycle-aware + current/superseded-aware + discoverable + operationally composable.**

`Persisted somewhere in Git` is necessary but insufficient.

At minimum the repository must be able to distinguish these roles:

- canonical durable truth;
- accepted cross-project decision/rationale;
- current programme/work state;
- audit/analysis evidence;
- candidate explanation/architecture;
- historical work evidence;
- qualification/review evidence;
- derived operational/read view.

This is a semantic requirement. It does not imply one schema/file type per role.

## 10. Active vs persisted knowledge model

The central operational principle is:

> **Persisted knowledge may grow; the default active work context should not grow proportionally.**

A useful target shape is:

```text
PERSISTED KNOWLEDGE
  canonical truth
  accepted decisions
  audit evidence
  historical work
  rejected/superseded candidates
  qualification evidence
        |
        | current-owner / dependency / task-relative selection
        v
ACTIVE KNOWLEDGE SURFACE
  governing purpose/authority
  current programme/work
  applicable decisions/requirements
  current evidence pointers
  authority/decision boundary
  completion/exit condition
        |
        v
ON-DEMAND EXPANSION
  rationale
  direct evidence
  provenance/derivation
  historical disputes
  forensic history
```

Token economy follows from better relevance selection, not from deleting valuable provenance or writing shorter prompts at the expense of meaning.

## 12. Closure model

For bounded work, adequate closure requires more than `PR merged` or `Issue closed`.

Candidate semantic transition:

```text
work owner
→ bounded result
→ applicable review/assurance
→ durable accepted meaning placed in the correct owner(s)
→ candidate/superseded state dispositioned
→ parent impact reconciled
→ fresh restart succeeds
→ work closes
→ history remains discoverable but inactive by default
```

A closed Issue must not be the only place where still-current cross-project architecture rationale can be understood.

An open Issue must not remain open merely so that its history remains findable.

## 13. DoR / DoD — Generic-Fit candidate

The following is derived from #225 plus the current audit. It requires separate Generic-Fit/D-016 disposition before becoming general METHOD.

### Programme / revision DoR

Before activation, reconstructable meaning should include:

- authorized problem/outcome;
- governing/parent authority;
- demonstrated failure/need;
- scope and non-goals;
- invariants;
- dependencies;
- exit/qualification criteria;
- material-change/D-016 state where applicable.

### Programme / revision DoD

Completion should require, as applicable:

- all necessary bounded results dispositioned;
- accepted cross-project decisions promoted to their durable owner;
- canonical state coherent;
- residual/open ceilings explicit;
- qualification against the original outcome, not proxy metrics;
- fresh-context restart;
- historical evidence retained and discoverable;
- no implicit successor priority/programme manufactured.

### Bounded work-package DoR

- parent outcome/contribution;
- input/canonical owners;
- bounded result;
- explicit non-goals;
- dependencies/prerequisites;
- acceptance criteria;
- return/reconciliation condition.

### Bounded work-package DoD

- result persisted in the correct owner/artifact role;
- required review/assurance complete at its real authority level;
- no later semantic mutation hidden behind earlier assurance;
- parent consequence dispositioned;
- local PASS not promoted to global acceptance;
- candidate/superseded state handled;
- fresh restart possible;
- work can become historical without loss of current durable meaning.

## 14. Adequacy requirements

These IDs belong to this audit only unless later promoted through D-016.

- **AR-01 Canonical ownership:** durable current meaning has a determinable owner.
- **AR-02 Currentness:** current state can be found without replaying issue/artifact chronology.
- **AR-03 History preservation:** closure does not destroy falsification/provenance/rationale history.
- **AR-04 Inactive history:** preserved history does not remain mandatory default work context.
- **AR-05 Decision durability:** consequential accepted cross-project rationale is recoverable without programme archaeology.
- **AR-06 Closability:** bounded audit/work/programme owners have real exit semantics.
- **AR-07 Parent reconciliation:** child completion affects a parent only through explicit disposition/reconciliation.
- **AR-08 Derived-not-owned:** human/agent read models remain rebuildable and non-authoritative.
- **AR-09 Bounded context:** fresh work context is task-relative rather than a full repository dump.
- **AR-10 On-demand provenance:** rationale/history/evidence can be expanded when challenged without being default active context.
- **AR-11 Review-basis visibility:** consequential review can distinguish direct evidence inspection from inherited premise/derivative.
- **AR-12 Qualification separation:** technical, scholarly, specialist, Human/governance and restartability dimensions do not collapse into one `PASS`.
- **AR-13 Exact-state assurance:** material mutation after a check invalidates that check as assurance for the new state.
- **AR-14 Open semantics remain open:** software/structure must not manufacture analysis units, interpretation, applicability or priority.
- **AR-15 Adequacy first:** necessary solution properties determine architecture size; size is not an input constraint.
- **AR-16 Simplify after proof:** remove complexity only after sufficiency is demonstrated.

## 15. Architecture classes — no implementation admission

### A. Local maintenance only

Examples: README repair, stale status labels, individual current pointers and isolated decision-log repair.

**Strength:** appropriate for real local drift and necessary regardless of larger architecture.

**Weakness:** does not by itself establish general closure/current-history/active-context semantics. It is not adequate as the full #230 disposition.

### B. Lifecycle + derived operational surface

Preserve existing canonical owners, but establish sufficient generic semantics for bounded work/programme closure, accepted-decision promotion, current/history/supersession and bounded derived context/read models.

**Current evidence:** strongest problem fit.

This class can be modest or substantial depending on the exact semantics proven necessary. It is not defined as "small".

### C. Larger repository knowledge/control restructuring

Potentially includes stronger structured relationships, event/transition representations, larger directory/owner reorganization or other persistent control structures.

**Current evidence:** not required yet, but no longer rejected merely because it is larger. It remains in the solution space if class B cannot satisfy the adequacy requirements without transferring the unresolved burden back to AI/human reconstruction.
