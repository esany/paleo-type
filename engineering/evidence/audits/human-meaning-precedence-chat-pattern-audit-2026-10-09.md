## 1. Executive finding

The Human correction

> “Du redest nur in zahlen”

is not an isolated style complaint.

Inspection of the conversation shows a **repeated structural inversion**: correct repository, workflow and assurance information repeatedly becomes the primary Human-facing explanation, while the scientific, developmental or decision meaning is delayed, compressed or left for the Human to reconstruct.

The same interaction family already appears in the durable chat-end audit as Human loss of orientation (“ich blick nicht mehr durch”). The current conversation supplies multiple fresh examples after the relevant #292/#308 rules already existed.

The demonstrated problem is therefore:

```text
correct internal state
+ correct traceability
+ often correct claim ceiling
!= effective Human-facing meaning
```

This is a central **operative-fidelity / semantic-interface** failure source in the inspected conversation because it recurs across research explanation, development explanation, coordination, currentness recovery and result review.

This analytical label does **not** create a new canonical failure family, METHOD rule or architecture.

## 4. Root-cause model

### 4.1 Demonstrated cause: traceability is being used as explanation

The repository is strong at exact identity, owners, branches, CI, claim ceilings and restartability.

The assistance layer repeatedly treats those reliable internal representations as if surfacing them accurately is itself an adequate Human explanation.

That is false at the interaction level:

```text
traceable != understandable
auditable != usable
precise identifier != semantic explanation
technical currentness != Human decision relevance
```

### 4.2 Demonstrated cause: lower-layer state outranks the higher-order outcome in presentation

The repository precedence is intentionally top-down:

```text
Human/research purpose
→ scholarly/domain requirements
→ METHOD
→ information model
→ workflow/AI/software
```

The problematic answers present the inverse order:

```text
PR / SHA / CI / Issue / branch / row count
→ process status
→ eventual domain meaning
```

This is a **presentation-level precedence inversion**.

### 4.3 Strong contributing factor: tool-output salience

GitHub/CI tools return compact, definitive-looking identifiers and states. They are easy to summarize and appear objective.

Domain meaning requires synthesis:

- what changed for the research or product;
- what is still uncertain;
- why it matters;
- what a Human needs to decide.

The assistant repeatedly defaults to the easier machine-state projection.

This is a plausible model-behavior mechanism supported by the response pattern; it is **not** proof of a platform implementation cause.

### 4.4 Strong contributing factor: context gravity

A long sequence of repository recovery, PR review, CI and owner routing makes the infrastructure layer dominate the immediate context.

The assistant then answers the next Human question in the language of the preceding support work rather than re-anchoring to the Human outcome.

This is the same family as local/support work displacing the higher-order cursor, but expressed in the **communication/meaning channel**.

### 4.5 Missing operative control: no reliably enforced Human-facing projection gate

The semantic rules exist, but fresh real use still violates them.

Therefore “the rule is documented” is not evidence that the interaction behavior is operationally reliable.

A response-level check equivalent in meaning to the following is not reliably occurring:

```text
Can the Human understand:
1. what changed / what was learned?
2. why it matters?
3. what remains unresolved?
4. what decision/action follows?
without decoding repository identifiers?
```

This audit does not decide whether that check should be implemented as prompt discipline, derived view, skill, eval, interface behavior or another mechanism.

## 5. Why this is a central error source in the inspected work

The pattern is cross-cutting.

It degrades:

### Research steering
The Human sees stage codes, image IDs, coverage state and Issues before the scientific question and evidence meaning.

### Development steering
The Human sees PR/SHA/CI/tests before “what problem was fixed, how behavior changed, what remains risky”.

### Acceptance
A technical PASS becomes the natural narrative endpoint even when the Human needs a domain/result judgement.

### Coordination
Owner IDs and return mechanics become a vocabulary the Human must operate.

### Context economy
Opaque status causes follow-up questions (“what does that mean?”, “what next?”, “I no longer follow”), which creates more meta-work and more context pressure.

### Authority
When the Human cannot readily see the meaning of the work, meaningful steering becomes harder even if formal authority is preserved.

### Drift risk
Repeated machine-first framing can make the work that is easiest to represent or verify appear to be the work that matters most.

The last point is a risk mechanism; a machine-first answer does not by itself prove actual scope drift.

## 6. Wirknetz

### Healthy path

```text
Human need / question
→ domain meaning
→ evidence/current state
→ method / capability
→ bounded work
→ result
→ uncertainty / validation
→ Human-relevant consequence / decision
→ subordinate technical traceability
```

### Observed failure loop

```text
Human need
→ technically successful work
→ machine state is easiest to rehydrate
→ machine state becomes answer backbone
→ Human meaning is compressed/late
→ Human asks for translation/orientation
→ more meta/process conversation
→ machine/workflow context becomes even more salient
→ next answer is even more machine-shaped
```

This is a reinforcing loop. It explains why the problem can become a **central error source** even when every individual technical statement is accurate.

## 8. Corrective interaction invariant derived from existing rules

For a consequential Human-facing response, the primary narrative should answer:

```text
WHAT DOES THIS MEAN FOR THE HUMAN'S PROBLEM?
→ WHAT CHANGED / WHAT WAS LEARNED?
→ WHAT REMAINS UNCERTAIN OR NOT ACCEPTED?
→ WHY DOES THAT MATTER?
→ WHAT REAL DECISION OR ACTION FOLLOWS?
→ only then: internal codes, Issues, PRs, SHAs, CI, row counts, file paths
```

For research, “meaning” is scholarly/disciplinary meaning.

For development, “meaning” is product/system behavior, user impact, risk and remaining acceptance.

For operations, “meaning” is service/control consequence and what the Human actually needs to know or decide.

This is not a ban on identifiers or technical precision. It establishes their proper role as **traceability and assurance after meaning**.

## 9. Acceptance implication

The inspected conversation falsifies any claim that #292/#308 Human-facing behavior is already reliably accepted merely because:

- the rules are documented;
- a prior implementation merged;
- repository state is correct;
- CI passes;
- one corrected answer can be produced after Human feedback.

Fresh use still produced repeated violations.

A meaningful acceptance fixture must therefore evaluate the **whole Human-facing response**, not only whether the correct internal state/code/owner can be recovered.

A PASS response should remain understandable if PR numbers, SHAs, issue IDs and internal stage codes are temporarily hidden.

## 11. Claim ceiling

This audit establishes a repeated pattern in the inspected conversation and links it to prior durable real-use evidence.

It does **not** establish:

- frequency across all ChatGPT conversations;
- a specific platform/runtime implementation cause;
- that every use of a number, code or identifier is defective;
- that repository traceability should be hidden;
- a new canonical failure family;
- a new workflow engine, schema, ontology, UI or deterministic natural-language validator;
- future compliance merely because the pattern is now documented.

The demonstrated current conclusion is narrower and stronger:

> The system repeatedly has correct internal state while failing to present the Human meaning first. In the inspected work, that inversion is a recurring cross-cutting source of confusion, extra meta-work and steering burden, and existing Human-facing rules have not yet proven reliable operative efficacy.
