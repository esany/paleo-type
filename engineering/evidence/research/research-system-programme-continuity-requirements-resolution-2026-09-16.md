## 2. Terminal disposition

**`existing-owner refinement warranted`**

The evidence does **not** support a new programme state store, registry, state machine, dashboard, mandatory Milestone, new agent/workflow layer or new formal Requirement family.

The evidence also does **not** support `no generic change`: the same transition class has recurred across materially different repository situations, and the current generic rules do not positively require the whole-programme consequence to be dispositioned at the point where a bounded stage/result closes.

The gap is therefore narrower than missing governance structure and narrower than a new Capability object. It is a **positive lifecycle/feedback operationalization gap in existing owners**.

## 3. Existing coverage is strong but incomplete at this boundary

### Governing Objective

The existing objective already requires human auditability and canonical/restartable durable state. It establishes the higher-order outcome; it does not prescribe a programme state machine or planning architecture.

### `requirements/domain-requirements.tsv`

`REQ-GWP-008` already requires research state to be restartable without old chat. This is sufficient higher-level requirement coverage for restartability; no new formal Requirement row is justified by the present evidence.

### `methodology/maintenance.md`

Maintenance already owns one-fact/one-owner propagation, event-driven consistency, affected planning-metadata audit, restartability checking and deliberate non-change recording after material change.

Its current rules are strongest where an owning truth or known dependent state has changed. They do not yet state the positive programme-level transition obligation narrowly enough to guarantee that a local `PASS`, `STOP`, closeout or phase result is explicitly reconciled against the current whole-programme cursor when no Project scholarly `NEXT ACTION` or canonical research truth changes.

### `methodology/workflow.md`

Workflow already requires reconstructable task owner/stage/cursor/handoff/return semantics and a canonical-freshness pass at consequential stage transitions.

That is sufficient for bounded task continuity, but it does not by itself require the material consequence of a local result to be returned to and explicitly dispositioned by the current programme/process navigation owner. The #208 finding demonstrates that bounded restartability can therefore coexist with a stale or missing programme cursor.

### #206

#206 is the correct current programme-specific repair: it owns the programme cursor, distinguishes local arc completion from programme completion and requires selected-route results to return for programme-completion review.

#206 is an instance of the needed behaviour, not a generic normative substitute for future material phase/result transitions.

## 5. Requirements-level property that survives P2

At a **material programme/phase/result transition** whose result can affect whole-programme completion/maturity, selectable/current work, or materially affected restart/navigation state:

1. identify the existing owner of the relevant programme/planning cursor or decision surface;
2. explicitly disposition the material consequence for that owner and materially affected restart/navigation surfaces as **changed**, **unchanged**, or **needs decision** (or semantically equivalent existing vocabulary), with enough rationale to reconstruct the consequence without old chat;
3. preserve the scope of local results: local `PASS`, `STOP`, closeout or `no further local change` does not establish whole-programme completion unless the programme owner explicitly reaches that conclusion;
4. preserve Human-Owner authority: reconciliation may expose selectable work or a needed decision but must not manufacture priority, Project scholarly `NEXT ACTION`, Concept admission or implementation authority;
5. preserve canonical boundaries: planning/navigation metadata must not become a second owner for Research, Requirements, METHOD, Project truth or accepted decisions;
6. permit **unchanged** as a valid outcome, but do not treat silence as evidence that the programme consequence was considered;
7. add no separate state store, registry, dashboard, state machine, mandatory Milestone or standing review bureaucracy merely to satisfy this property.

This is a Requirements-level property, not proposed final METHOD wording or mechanism design.
