# SD-KA-01 problem

The repository's scholarly/source contracts are comparatively disciplined, while the engineering-development surface has required chronology-heavy reconstruction of current configuration, material findings, decision rationale, applicability and bounded work state. `requirements/` remains a mixed brownfield namespace and a local technical PASS can still be mistaken for whole-system closure.

WP1 established the in-place semantic owners, stable engineering identities, F01–F45 coverage, admitted change state and deterministic structural validation. It deliberately did not make the admitted SD-KA-01 target an accepted current architecture baseline.

## WP2 problem slice

The remaining currentness gap is narrower and executable: a fresh context can read `engineering/configuration.json`, the change state and catalogs, but current engineering meaning is not yet compiled/queryable with explicit applicability provenance. The system must make accepted baseline, admitted/active change, bounded current focus and explicit absence directly derivable without turning Git recency, Issue/PR state, CI success or the newest proposal into semantic currentness.

WP2 therefore implements current configuration/query derivation and the current-first/applicability primitives already designed under #246/#247. It does not implement the WP3 Human/Agent role products, WP4 full engineering-fitness suite, WP5 physical migration or WP6 terminal qualification/Result Review.
