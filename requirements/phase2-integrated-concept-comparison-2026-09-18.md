### Concept variants to compare

At minimum compare these as serious alternatives; refine/split/merge only when evidence warrants it:

#### C0 — Existing-owner + AI composition baseline

No new executable integration surface. A capable AI continues to assemble R-1…R-4 from current owners, with improved prompt/context discipline only.

Purpose: provide the **minimal/no-change baseline**. It must not be rejected merely because implementation is absent; reject it only if demonstrated failures remain unresolved.

#### C1 — Derived control surface over existing owners

A read-only/rebuildable derived control view resolves existing canonical owners into one restartable system-facing surface for the current authorized outcome:

```text
authorized outcome / absence
+ Project purpose/scope
+ current evidence/maturity
+ applicable requirements
+ responsibility/validation metadata
→ derived current control surface
```

No independent canonical state, no automatic scholarly interpretation, no workflow engine.

#### C2 — Deterministic requirement/gate resolver + bounded execution-plan derivation

Build on existing structured requirements/gates/context inputs to derive stable parts of:
- outcome binding where authority is explicit;
- applicable/unmet requirements where formal dependencies are stable;
- capability/responsibility routing from requirement metadata;
- bounded execution prerequisites/return conditions;
- outcome disposition where formal acceptance/ceiling semantics are stable.

Open scholarly applicability/interpretation remains AI/specialist/Human-owned.

This is stronger than C1 because it derives decisions, not only aggregates state.

#### C3 — Hybrid thin integration core

Use a minimal deterministic core for stable owner resolution / requirement applicability / responsibility / restart state, plus an explicit AI reasoning boundary for semantic mapping and open scholarly applicability.

Conceptually:

```text
canonical owners
→ deterministic context + stable rule derivation
→ AI only for unresolved semantic/applicability reasoning
→ specialist/Human only where triggered
→ derived outcome/work/ceiling surface
```

The core must remain small enough that it does not become a workflow engine or new research ontology.

### Required challenge dimensions

For each concept, explicitly test:

1. **R-1 coverage**
   - ordinary-language desired outcome → authorized Project purpose/scope/result meaning;
   - explicit `NO AUTHORIZED OUTCOME` without generating work;
   - no semantic laundering.

2. **R-2 coverage**
   - can it derive/expose unmet requirements from S1–S9, G1–G6 and domain requirements?
   - which applicability rules are stable enough to formalize?
   - which require AI/specialist judgement?

3. **R-3 coverage**
   - dynamic competence activation without fixed role topology;
   - deterministic vs AI vs specialist vs Human boundary;
   - smallest coherent vertical slice rather than smallest local defect;
   - reuse current workflow cursor/handoff/return semantics.

4. **R-4 coverage**
   - outcome completion vs work remaining vs evidence ceiling vs specialist dependency vs Human decision vs action-local technical inability;
   - local PASS/STOP/CI cannot establish whole outcome;
   - no universal status enum unless independently justified.

5. **AI-independence**
   - which repeated inference moves out of model memory?
   - does the concept merely repackage prose for AI?

6. **Single-source ownership**
   - every derived field must reference/resolve an existing owner where one exists;
   - no manually maintained duplicate outcome/gate/evidence state.

7. **Human usability**
   - non-specialist owner states scholarly need and receives only genuinely non-derivable decisions;
   - no repository/schema/gate/architecture operation burden.

8. **Genericity / counter-fixtures**
   - Reg. Ii 3: valid Project/evidence with no current authorized outcome;
   - Corpus-only: no Project;
   - #69 intake/routing: thin deterministic operationalization over distributed semantics;
   - at least one actual scholarly execution fixture materially different from Reg. Ii 5.

9. **Continuity preservation**
   - consume #226 as an acceptance property, not a new component;
   - decomposition/repair must return to current valid cursor;
   - no parent/outcome may be manufactured.

10. **Lean / technological proportionality**
    - smallest new mechanism that removes demonstrated burden;
    - no database/API/service/agent topology merely for architectural neatness;
    - prefer derived/rebuildable read-only surfaces before canonical writers.

### Comparative decision rules

Reject a concept if any are true:
- it cannot support explicit absence of authorized outcome;
- it invents Project scope/priority/NEXT ACTION;
- it duplicates canonical state;
- it hard-codes Reg. Ii 5 or visitation structure;
- it introduces a fixed discipline/agent topology;
- it makes a local support/technical result look like scholarly completion;
- it increases Human technical burden;
- its stable repeated semantics still rely on model memory without reason;
- it formalizes open scholarly judgement as deterministic;
- its complexity is not tied to a demonstrated R-1…R-4 failure.

Prefer the smallest concept that:
- satisfies R-1…R-4 together;
- reuses current owners/executable components;
- improves fresh-context equivalence;
- reduces AI/Human reconstruction burden;
- preserves legitimate uncertainty/ceiling;
- can be vertically tested on real scholarship.

### 4.2 C0 — existing-owner + AI composition baseline

**First-pass result: retained as comparison baseline; currently insufficient as the Phase-2 solution.**

The system-operationalization audit explicitly finds that today much of Human need → evidence/maturity → unmet requirements → competence/work allocation is reconstructed by AI from prose and Project state. project_context deliberately stops before those integrations.

C0 therefore leaves the demonstrated fresh-context/model-dependence failure materially unchanged. It would become viable only if later fresh-context evidence falsifies that audit finding.

### 4.3 C1 — read-only derived control surface

**First-pass result: viable partial concept, but not yet sufficient alone.**

It strongly fits current architecture because project_context/source_intake already demonstrate rebuildable, non-authoritative derived views. C1 could improve R-1 visibility/restartability and expose gate/evidence/requirement metadata without duplicating truth.

However, a pure aggregator leaves R-2/R-3 to AI. Its survival question is whether stable resolver semantics can live inside the derived surface without turning C1 into C2 under another name.

### 4.4 C2 — deterministic requirement/gate resolver + bounded plan derivation

**First-pass result: serious surviving concept; semantic-overreach risk must be falsified.**

Support:
- G1–G6 have stable scope-bound requirements and completion/reopen semantics;
- domain-requirements.tsv has structured domain/validation/specialist-trigger metadata;
- Source/Project/evidence structure is already deterministic;
- the audit identifies outcome+state→unmet requirements and unmet requirements→bounded work as major gaps.

Risk:
- S1–S9 and G1–G6 are explicitly complementary, not a rigid workflow;
- applicability and consequence remain partly scholarly;
- C2 must be able to return “requires scholarly/AI applicability judgement” rather than force a deterministic answer.

### 4.5 C3 — hybrid thin integration core

**First-pass result: serious surviving concept; broadest coverage but highest vagueness/bloat risk.**

Potentially it can combine deterministic owner/state/requirement resolution with an explicit AI boundary for unresolved semantic applicability, while preserving specialist/Human triggers.

It is not selected because “hybrid” is not yet an architecture. C3 survives only if the deterministic core can be stated as a small exact contract and its AI boundary is materially narrower/more testable than C0.
