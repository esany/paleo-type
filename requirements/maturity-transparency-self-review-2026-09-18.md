## 4. What the correct object is now

Do **not** design another maturity mechanism.

The object to validate is a **derived Project-level maturity/progress decision surface** over existing owners.

It must combine without collapsing:

### Project topology / coverage
Which source groups/loci/parts have what historical/current/reopened/not-activated state?

### Scholarly activity coverage
Which existing METHOD activities were actually performed, for what scope, with what result?

### Scope-bound scholarly maturity
Which existing gate/acceptance states are evidenced for each evaluated scope?

### Cross-cutting scholarly quality
Evidence adequacy, completeness for scope, claim-layer separation, uncertainty, independent challenge, source criticism, outcome usefulness/evidence ceiling.

### Dynamic disciplinary adequacy
Which disciplinary requirements were applicable, which were activated, with what result/gap, and which were correctly not activated?

### Specialist-validation state
Where independent qualified validation exists/is required/is not triggered.

### Research-infrastructure assurance
Provenance, exact evidence access, reproducibility, restartability, semantic/data integrity, deterministic checks, AI/Human/specialist boundaries.

### Human auditability/usability
Can a capable human understand and challenge the state and move from result → basis → consequence without internal machine jargon?

### Iteration delta
For a bounded work block:
- before;
- exact work scope;
- scholarly/support delta;
- which profile dimensions changed;
- which did not;
- after;
- reopened claims/new ceilings;
- newly enabled or unnecessary work.

### Possible next work
Locate each possible work block in the existing profile:
- what gap/dimension/scope it addresses;
- prerequisites;
- expected scholarly delta;
- likely quality/maturity/coverage effect;
- what remains unchanged;
- dependencies/ceilings;
- later options enabled/removed.

This is contextualization, not automatic priority selection.
