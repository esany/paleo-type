## 1. Purpose and boundary

This file preserves a **problem landscape** exposed by the two 2026-09-14 audits and the preceding Reg. Ii 5 research history.

Its purpose is to keep multiple partially interacting failure modes visible **before** they are compressed into one diagnosis or one solution programme.

It therefore intentionally does **not**:

- select one root cause;
- merge overlapping problems merely because they co-occurred;
- define a new workflow or role topology;
- prescribe a mandatory research-framing form;
- decide which corrective mechanism should be implemented;
- create a new Project or `NEXT ACTION`;
- generalize Knau/visitational structures into universal source architecture;
- treat this repository fixture as proof that every other Project/repository has the same defects.

For another Project or repository, this landscape is a **review aid**: use the categories to ask whether analogous evidence exists locally. Do not import the diagnosis without local evidence.

## 2. Analytical maturity scale used here

The maturity labels below are descriptive only and are not repository gates.

```text
R0  trace / observation only
R1  problem clearly diagnosed
R2  governing principle / boundary formulated
R3  concrete mechanism, counterexample or fixture demonstrated
R4  mechanism currently operationalized in canonical workflow/state and regression-tested where applicable
```

A high maturity rating for one local safeguard does not imply the larger research-system problem is solved.

## 6. Interaction patterns currently visible

The following are **interaction patterns**, not yet canonical root causes.

### 6.1 Addressability loop

```text
available/localized backlog item
→ easy bounded task
→ strong evidence/assurance
→ clean completion
→ next readily addressable item
```

This may be productive, but it can also reproduce A2 when scientific leverage is not separately compared.

### 6.2 Representation loop

```text
existing mapping/artifact/address
→ convenient work object
→ silently treated as scientific unit
→ downstream work assumes the unit
→ review/assurance stabilizes the inherited premise
```

A3, C1, B3 and D2 can participate in this loop.

### 6.3 Support loop

```text
scholarly scope
→ legitimate support need
→ further support/assurance need
→ support becomes visible progress
→ first/next scholarly action is delayed
```

This is the A8 family. It is partly controlled now, but remains analytically distinct from A1.

### 6.4 Authority-laundering loop

```text
local fact/state
→ semantic boundary crossed without explicit translation/authority check
→ statement gains stronger task/scholarly/planning meaning
→ canonical persistence
→ tests/restart state make the derived statement internally consistent
```

The former `resource unavailable → STOP` chain is the clearest demonstrated example.

### 6.5 Lean-down / function-loss loop

```text
complex structure contains both bad semantics and useful function
→ simplification removes bad semantics
→ useful review/cognitive surface disappears with it
→ later work lacks the function even though the original complexity was correctly rejected
```

The source-unit Project migration is a demonstrated example. The #71–#79 absorption is a current audit hypothesis/analogy that requires careful local evaluation rather than automatic reversal.

### 6.6 Contamination-protection loop

```text
context/domain knowledge could bias direct reading
→ isolate context
→ source-only evidence quality improves
→ context remains isolated after the contamination-sensitive stage
→ historical question generation may become impoverished
```

The first three steps are established and desirable. The final step is an audit risk, not yet a universal proven failure.

### 6.7 Competence-compression loop

```text
explicit roles/hand-offs expose authority boundaries
→ role/process structure becomes too heavy
→ semantics are absorbed into lean workflow
→ boundary rules remain
→ active disciplinary arbitration/research sequencing becomes less visible
```

This captures the current B1/C2 concern without implying that the old role programme should be restored.

## 7. Corrections that produced or exposed secondary risks

The history repeatedly shows that a scientifically justified correction can create a new overcorrection if its scope is not bounded.

- Microanalysis/addressability pressure was countered by #161 higher-level source-understanding work. This produced real scholarly gain, but later risked `larger unit = better analysis`.
- Source-as-Project semantics were correctly removed, but the migration lost useful visible STATUS/audit surfaces.
- Legacy palaeography/apparatus authority was correctly demoted, but useful comparison/decision history must remain discoverable without becoming current truth.
- Context contamination is correctly prohibited, but post-observation context/domain expertise may still need a constructive research-framing role.
- Heavy role/handoff structure was correctly absorbed into lean METHOD, but the earlier transdisciplinary Domain Review/research-sequencing function may now be less salient.
- Support-dominance controls improved execution economy, but process efficiency still does not validate scope correctness.

This repeated shape is itself worth monitoring, but this landscape deliberately does not promote it to a single master explanation.

## 9. Distinctions that must remain open during further analysis

Do not collapse the following pairs yet:

- Research Selection ≠ transdisciplinary competency synthesis.
- Semantic/authority laundering ≠ addressability bias.
- Support dominance ≠ poor research framing.
- Artifact topology ≠ artifact uselessness.
- Lean-down function loss ≠ evidence that lean-down was wrong.
- Human-Owner authority ≠ scholarly sequencing/adjudication authority.
- source-understanding synthesis ≠ next-scope selection.
- Project-specific Knau findings ≠ generic research architecture.
- fresh-context independence ≠ evidence-basis independence.
- technical/process correctness ≠ scholarly scope correctness.

Keeping these distinctions visible is part of the purpose of this file.

## 10. Cross-project / cross-repository portability note

This landscape is intended to be discoverable by future Project and repository work because the failure patterns are potentially portable. Portability must be evidence-driven.

For another Project/repository, use it as a set of inspection questions, for example:

- Is task selection driven by scientific purpose or by what is already easy to address?
- Are source-native structure, working address and analysis unit being distinguished?
- Which disciplinary competence owns the actual claim being made?
- Is a semantic translation adding authority or certainty?
- Is technical/support work protecting a scope that has not recently been scientifically reviewed?
- Was a useful review/cognitive function lost when a previous structure was simplified?
- Are historical/contextual resources correctly staged rather than either contaminating source evidence or being permanently excluded?
- Is the Human Owner receiving a research decision surface or being asked to substitute for specialist/technical judgement?
- Does independent review actually trace contested premises to direct evidence?

A positive answer to one risk question is not proof of the full failure chain. Record local evidence and consequence before deriving a requirement or change.

## 12. Second-level needs / requirements audit — 2026-09-14

### 12.1 Audit question and evidence discipline

This second-level pass asks a different question from the first landscape:

> For each construction site, what underlying scientific/human need is affected, which requirement should protect it, what is already present in the repository, and what kind of gap remains?

The pass deliberately distinguishes:

```text
missing requirement
activation failure
sequencing failure
mechanism gap
visibility/discoverability gap
freshness/propagation gap
function loss after simplification
technical enforcement gap
insufficient evidence to promote a requirement
```

The existing concept candidate `requirements/executable-transdisciplinary-research-system-concept-idea-2026-09-14.md` was inspected for repository context but **not used as evidence that a requirement or solution is necessary**. A solution hypothesis must not prove the need it proposes to solve.

The main fresh cross-check covered `GOVERNING_OBJECTIVE.md`, `historical-source-workflow.md`, `workflow.md`, `maintenance.md`, #25/#30–#39, #71–#79, G2 Domain Review, #123, #129, #158, #161, #165/#166/#169, #171/#162, the Project context/palaeography/apparatus owners and L021–L025.

### 12.2 Principal cross-cutting finding

The strongest finding is negative but consequential:

> **For surprisingly many construction sites, the primary scholarly principle is already present. The remaining problem is more often activation, sequencing, connection between existing functions, visibility/freshness or technical enforcement than absence of a new Requirement family.**

G2 Domain Review is an important historical counterexample to a simple `missing requirements` diagnosis. It already applied the sequence:

```text
source-bound finding
→ is the scholarly information established?
→ which existing disciplinary requirements apply?
→ can an existing canonical owner preserve the distinction?
→ what actual gap remains?
→ source / Project / generic / system / specialist / no-action consequence
→ smallest justified action
```

That operation successfully admitted some deterministic system consequences while rejecting many others as research, specialist or no-action outcomes.

## 15. Intrinsic challenges behind the construction sites

These are research-system properties, not root causes and not proposed solutions.

### 15.1 Scientific value is only partly formalizable

`Which question is worth asking next?` depends on Project purpose, current understanding, rival hypotheses, evidence availability, discipline-specific consequence and sometimes unexpected source findings. A future system may expose these dimensions; this audit gives no basis for a single automatic scientific score.

### 15.2 Competence is distributed

No one scholarly discipline, software role or AI model owns all relevant claim types. Merely adding roles also does not produce transdisciplinary judgement. The difficult operations are leadership, translation, conflict handling and return across boundaries.

### 15.3 Knowledge has stage-dependent evidential use

The same contextual knowledge can contaminate an initial graphematic reading and later become useful for hypothesis generation or historical testing. The system therefore needs temporal/stage sensitivity, not a simple `context allowed/forbidden` global rule.

### 15.4 Persistence strengthens both correct and incorrect semantics

Canonical persistence, tests and restartability prevent knowledge loss. L025 also demonstrates that an unauthorized inference can become highly stable once persisted and regression-protected. Persistence quality therefore cannot substitute for epistemic correctness.

### 15.5 Visible artifacts attract work

Issues, rows, mappings, directories and comparator candidates are cognitively and operationally easier to act on than unarticulated historical questions. This is simultaneously an information-architecture and human-research problem.

### 15.6 Scientific and technical assurance validate different objects

CI can verify that an implementation conforms to established semantics. It cannot prove that the scientifically most consequential research question was selected.

## 17. Important interactions between construction sites

### 17.1 A1 ↔ A2 ↔ C1

Without strong positive framing, visible/addressable artifacts can acquire practical priority. This is not reducible to either artifact authority or research selection alone.

### 17.2 A3 ↔ B3 ↔ D2

A wrongly promoted analysis unit can be created in synthesis, acquire stronger authority during semantic translation and then be repeated by an allegedly independent review that never reaches the direct evidence owner.

### 17.3 A1 ↔ B1 ↔ B4 ↔ B5

A strong candidate question may require source structure, contextual/domain expertise, synthesis across disciplines and finally an owner priority decision. None of those operations substitutes for the others.

### 17.4 A8 ↔ D3

A scope may be impeccably supported while remaining scientifically weak. Execution-economy controls therefore cannot be used as validation of scope quality.

### 17.5 C2 ↔ C3 ↔ C5 ↔ D1

Simplification, historical memory, stale surfaces and restartability must be balanced:

- too much retained state increases orientation burden;
- too little retained state loses evidence/review function;
- stale retained state creates false present orientation;
- overaggressive rewriting can erase revision history.

This establishes an information-architecture problem, but not a demonstrated need for an audit registry or lifecycle engine.

### 17.6 C4 constrains every generic response

Any future response to A1/B1/B4 must demonstrate usefulness beyond the Reg. Ii 5/visitation fixture. Otherwise it is a more elaborate Knau method, not a generic research-system capability.

### 17.7 F1 is largely orthogonal

Branch/protection mechanics can improve canonical promotion integrity. They do not solve research selection, semantic laundering, context activation or analysis-unit formation and must not be included in a scientific causal explanation merely because they are a real open implementation gap.

## 18. Requirement-state types to preserve in later analysis

A later design/review phase should not use only `requirement present / absent`. At least these states are now evidenced:

### Type I — requirement and mechanism already strong

Examples: A9 resource/task-authority separation, much of B6 Domain↔Dev, large parts of D1 restartability and C4 Generic-Fit.

Default response: avoid duplication; test regressions and actual use.

### Type II — requirement present, decisive activation weak

Examples: A3 analysis-unit distinction, B4 post-observation context use, D2 evidence-depth review, C5 stale derived surfaces.

Default analytical question: why was the existing safeguard not operative at the relevant transition?

### Type III — need clear, requirement distributed/implicit, operative function incomplete

Examples: A1/A5, B1/B2 and B5.

Open question: does the future need require new normative wording, or can existing method/authority semantics be connected and activated without a new Requirement family?

### Type IV — requirement clear, technical enforcement absent

Current strongest example: F1 canonical Git promotion protection.

This class must not be confused with the scientific framing gaps.

### Type V — risk/hypothesis observed, evidence insufficient for promotion

Examples: a universal audit-supersession system, full restoration of #73 as a standing role, or a claim that context is systematically underused across Projects.

Default response: obtain a real fixture before changing architecture.

## 20. Open evidence questions before any root-cause or solution synthesis

### 20.1 Research-framing fixture

There is still no real end-to-end fixture in which rich but unprioritized source understanding is used to generate several serious competing questions, reviewed by the actually implicated competencies, compared for scholarly consequence and then presented for a Human-Owner priority decision.

Until that exists, it remains unclear:

- which information is actually necessary;
- which fields would be form-bloat;
- which competencies materially contribute;
- where conflict arbitration is needed;
- which information can be derived from canonical state;
- what decision representation genuinely helps the owner.

### 20.2 Scientific consequentiality / information gain

The project has good evidence that local questions can differ sharply in scholarly leverage. It does not yet have a sufficiently tested account of:

- which criteria historians/specialists actually use to compare consequence;
- which criteria should remain qualitative/incommensurable;
- when tractability/cost legitimately matters;
- how to expose expected information value without creating a pseudo-precise automatic score.

### 20.3 Question-relative leadership

Claim-relative authority is well supported conceptually, but needs a real mixed problem in which diplomatic, philological, institutional/economic and perhaps technical subquestions interact. The system has not yet demonstrated how competing equally legitimate specialist perspectives are reconciled or when independent specialist escalation becomes necessary.

### 20.4 Context reactivation

It is established that contextual knowledge must not determine source graphemes. Still unresolved:

- what exact transition permits post-observation contextual activation;
- whether different source types need different contamination boundaries;
- how context claims preserve provenance when used only as question/hypothesis generators.

### 20.5 Lean-down / function loss

Direct evidence exists for source-unit STATUS/audit-surface loss. The degree to which #71–#79 absorption specifically removed research-sequencing capability rather than merely making it less visible remains an audit hypothesis and should not be reconstructed from present dissatisfaction alone.

### 20.6 Audit layer

README now improves orientation to the cross-project analytical files. It is still not established that audit-premise stacking recurs often enough to justify a registry, supersession state machine or dedicated audit infrastructure.

### 20.7 Cross-source Generic-Fit

The current fixture remains source-type rich but homogeneous. Any generic research-framing/competency mechanism needs at least one materially different Project/source type, preferably a case where the highest-value next question does not originate in an unresolved transcription locus.
